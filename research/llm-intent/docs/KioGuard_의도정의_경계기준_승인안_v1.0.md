# KioGuard 의도 정의·경계 기준 승인안

작성일: 2026-09-27 · 문서 v1.0 · 의도 체계 V2의 **승인 전 제안**

## 1. 이번에 승인받을 내용

LLM·PTQ·QAT를 비교하기 전에, 무엇을 정답으로 판단할지 같은 기준을 적용하기 위한 문서다. 기존 8개 의도를 그대로 고/저 우선순위로 나누지 않고, **요청 종류 14개 + 주제·대상·값 + 부정·대화 문맥**으로 구분하는 안을 제안한다. 14개가 최적이라는 실험 결과는 없다. 경계 검수 결과에 따라 병합하거나 수정할 수 있다.

이번 범위는 기존 명세와 48발화의 재검토, 정의·경계·라벨링 기준 작성이다. 앱 구현, 모델 실행, PTQ/QAT, 성능 측정, 신규 정답셋 확정은 수행하지 않았다. 이 문서는 사용자 승인과 사람 간 라벨 검수 전이므로 학습·최종 평가용 gold가 아니다.

함께 검토할 자료: [48발화 재라벨링 승인안](KioGuard_48발화_재라벨링_승인안_v1.0.md). 이전 [상세 명세서 v0.2](KioGuard_상세명세서_v0.2.md)와 [48발화 검토 v0.2](KioGuard_기존48발화_의도검토_v0.2.md)는 보존했다. 이번 승인안이 확정되면 관련 절을 이후 버전에 반영한다.

## 2. v0.2에서 추가로 바로잡을 부분

| 문제 | 이번 수정 제안 | 이유 |
|---|---|---|
| 옵션을 처음 정하는 경우가 SELECT/MODIFY 사이에 남음 | I02를 ‘선택 내용 **설정·변경**’으로 정의. 상품 요청에 딸린 옵션은 I01의 값으로 기록 | 최초 옵션 선택과 이후 변경 모두 평가 가능하게 함 |
| INFO의 ‘절차’와 GUIDE의 ‘방법’이 중복됨 | 행동 순서·버튼·동선은 GUIDE, 지원 여부·자격·가격·운영 사실은 INFO | ‘어떻게 해야 하나’와 ‘무엇이 사실인가’를 구분 |
| 외부 화면을 키워 달라는 요청을 GUIDE로 바꿀 가능성 | I11을 ‘표시·음성 제어 UI_CONTROL’로 확장하고 제어 대상을 별도 기록 | 사용자가 원하는 일과 앱의 실행 능력을 분리 |
| 문맥이 없으면 의도까지 미분류로 취급할 가능성 | 의도 판정, 대상 해소, 답변 근거, 직접 실행 가능 여부를 별도 기록 | ‘민원서류 떼러왔어요’는 요청 종류를 알지만 서류 종류가 없음 |
| ‘이거 어떻게 해요’를 GUIDE/HELP 모두로 허용 | 구체적인 방법·위치 문의는 대상이 없어도 GUIDE, 일반적인 도움·직원 요청은 HELP | 대상 누락을 다른 의도로 바꾸지 않음 |
| C1을 검증된 Rule 패턴과 동일시함 | 복잡도는 언어·문맥 특성으로 먼저 부여. Rule 검증 여부는 별도 속성 | Rule이 늘어도 동일 발화의 의미 복잡도가 바뀌지 않음 |
| 결제 단어가 있으면 영향도 H로 고정할 가능성 | 실제 안내 결과의 영향도와 결제 관련 보호 정책을 분리 | 결제수단 선택·지원 질문·최종 승인 안내의 위험이 다름 |

I11의 코드명 변경은 호환성 변경 제안이다. 승인 시 기존 `APP_CONTROL`을 새 `UI_CONTROL`로 버전별 매핑하고, 한 평가 버전에서 두 이름을 임의 혼용하지 않는다. I01~I14의 식별 번호는 유지한다.

## 3. 의도 목록과 포함·제외 기준

아래 의도는 **사용자가 원하는 일**이다. 결제·발급 등의 의도를 인식해도 KioGuard가 외부 키오스크를 자동 조작한다는 뜻은 아니다. 현재 제품 범위는 사용자가 직접 조작하도록 안내하는 것이다.

| ID / 코드 | 정의·포함 기준 | 핵심 값 | 경계·제외 |
|---|---|---|---|
| I01 SELECT | 새 상품·서비스·서류를 선택하거나 요청. 상품과 옵션을 한꺼번에 말한 새 요청 포함 | 대상 종류·명칭, 수량, 부가 옵션 | 명시적 정정·교체는 I02. 가능 여부는 I10 |
| I02 MODIFY | 선택 대상의 속성을 설정·변경하거나 기존/제안된 선택을 정정·교체 | 대상, 속성, 새 값, 배제한 값 | ‘라떼 뜨겁게 한 잔 주세요’가 새 요청이면 I01 하나. ‘사이즈는 큰 걸로’처럼 속성만 정하면 I02 |
| I03 FULFILLMENT | 매장·포장·수령 방식을 선택하거나 바꿈 | 방식, 상품별 수량 배분 | 가능 여부는 I10. 방식의 변경도 전문 의도 I03 유지 |
| I04 PAYMENT_METHOD | 사용할 결제수단을 선택하거나 바꿈 | 카드·현금·간편결제 등 수단 | 결제 완료·최종 승인과 다름. 지원 질문은 I10, 최종 진행은 I13 |
| I05 RECEIPT | 영수증 발급·출력·재발급을 원함 | 영수증 종류, 해당 거래 | 출력 방법·위치 질문은 I09. 결제수단 선택과 분리 |
| I06 BENEFIT_APPLY | 쿠폰·할인·적립 등 혜택을 적용하려 함 | 혜택 종류, 적용 대상 | 지원·자격 질문은 I10, 사용 방법·위치는 I09 |
| I07 BACK | 현재 흐름에서 바로 이전 단계로 이동하려 함 | 앱/키오스크, 현재 단계 | 특정 항목 제거는 I08, 전체 시작점으로 복귀는 I14 |
| I08 CANCEL | 특정 상품·주문·신청·거래 등을 철회·제거하려 함 | 취소 대상과 범위, 거래 상태 | 단순 뒤로는 I07, 과업 전체 재시작은 I14. 음성 재생 중지는 I11 |
| I09 GUIDE | 현재 과업의 수행 방법·행동 순서·버튼 위치·동선 안내를 원함 | 목표, 질문 대상, 현재 단계 | 지시 대상이 없어도 GUIDE는 유지. 사실·지원 여부는 I10 |
| I10 INFO | 범위 안의 서비스 지원·조건·자격·가격·운영 사실을 물음 | 질문 주제, 확인할 사실, 기관/기기 | 절차를 따라 할 방법은 I09. 모든 분야의 일반 지식 질문을 포함하지 않음 |
| I11 UI_CONTROL | 표시·음성의 접근성 또는 재생 기능을 조절하려 함 | APP/KIOSK/UNKNOWN 대상, 글자·음량·속도·반복·중지 | 화면 이동 I07/I14와 구분. 외부 제어 미지원이어도 원래 의도는 보존 |
| I12 HELP | 구체적 방법 문의 없이 도움을 원하거나 직원을 찾음 | 일반 도움/직원 도움, 어려움 | ‘이거 어떻게 해요’는 I09. ‘직원 불러 주세요’는 실제 호출 성공을 뜻하지 않음 |
| I13 PROCEED | 현재 과업의 확인·제출·결제 등 확정 단계로 진행하려 함 | 진행 대상, 단계, 확인 질문 연결 | ‘카드로 할게요’는 I04. 맥락 없는 ‘네’를 I13으로 만들지 않음 |
| I14 RESET | 지정한 과업·세션을 처음부터 다시 시작하려 함 | 앱/키오스크, 초기화 범위, 보존/소실 상태 | 이전 한 단계는 I07, 특정 대상 취소는 I08 |

전문 의도 I03~I06·I11이 정의한 속성은 해당 의도를 우선한다. 예를 들어 ‘카드 말고 현금’은 I04에 배제 수단=카드를 기록하며 I02로 중복 분류하지 않는다. ‘단품으로 바꿔 주세요’는 상품 구성 변경이므로 I02다.

## 4. 경계를 판단하는 순서

### 4.1 발화 형태보다 실제 요구를 본다

질문형 어미만으로 INFO를 정하지 않는다. ‘삼성페이 지원되나요?’는 INFO이지만 ‘이 주문을 카드로 바꿔 주실 수 있나요?’는 문맥상 정중한 변경 요청일 수 있다. 지원 여부와 실행 요구 중 하나를 결정할 근거가 없으면 확인 질문을 정답 행동으로 기록한다.

발화는 최소한 요청, 사실/방법 질문, 확인 응답, 진술, 금지·제약으로 구분한다. 이것은 업무 의도 14개와 다른 축이다. ‘네/아니요’는 유효한 직전 질문과 연결해야 한다. ‘포장할까요?’에 ‘네’는 I03이고, ‘결제 단계로 진행할까요?’에 ‘네’는 I13이다. 대기 질문이 없으면 어느 쪽도 단정하지 않는다.

### 4.2 새 대상 선택과 옵션 설정을 구분한다

| 입력·문맥 | 제안 정답 | 이유 |
|---|---|---|
| 새 주문을 말하는 상황: ‘라떼 뜨겁게 한 잔 주세요’ | I01, 상품=라떼·온도=뜨거움·수량=1 | 새 상품 요청에 포함된 옵션을 I02로 중복 세지 않음 |
| 라떼 선택 후: ‘사이즈는 큰 걸로 주세요’ | I02, 크기=큰 것 | 처음 정하는 옵션이어도 기존 대상의 속성 설정 |
| 문맥 없이: ‘아이스로 바꿔 주세요’ | I02 판정 가능, 대상 확인 필요 | 변경 의도와 변경할 대상의 유무는 다름 |
| 문맥 없이: ‘따뜻한 걸로 두 잔이요’ | I02 우선 제안, 대상 누락 기록 | 온도·수량만 지정하는 발화를 옵션 설정으로 다루는 라벨링 관례. 문맥 복원 시 재검토 |
| ‘어떤 음료로 바꾸실래요?’에 ‘라떼 한 잔이요’ | I02 | 같은 명사구라도 변경 질문에 대한 응답 |
| ‘등본 말고 초본이요’ | I02, 교체=등본→초본 | 기존 선택뿐 아니라 직전 제안의 정정도 포함 |

상품명만 있는 생략형 요청은 독립적인 새 요청으로 해석할 수 있지만, 실제로는 변경 질문의 답일 수 있다. 따라서 원래 문맥이 없는 자료를 임의의 신규 주문 문맥으로 복원하지 않는다. 부록에서는 적용 가정과 필요한 문맥을 표시한다.

### 4.3 사실·방법·도움을 구분한다

| 대비 사례 | 제안 정답 |
|---|---|
| ‘쿠폰 사용할 수 있나요?’ / ‘쿠폰 써 주세요’ / ‘쿠폰 어디 찍어요?’ | I10 / I06 / I09 |
| ‘등본 발급에 필요한 서류가 뭐예요?’ / ‘등본을 어떻게 발급받아요?’ | I10 / I09 |
| ‘창구가 몇 시에 닫아요?’ / ‘몇 번 창구로 가야 돼요?’ | I10 / I09 |
| ‘도와 주세요’ / ‘이 버튼 어떻게 눌러요?’ / ‘직원에게 도움받고 싶어요’ | I12 / I09 / I12 |
| ‘화면을 못 찾겠어요’ | 화면 찾기라는 구체적인 어려움을 표현한 I09 제안. 찾는 화면·촬영 문제 여부를 추가 확인 |

답을 뒷받침할 화면·기관 정보가 없다고 INFO를 OUT_OF_SCOPE로 바꾸지 않는다. ‘이 기기에서 전입신고가 되나요?’는 범위 안의 지원 여부 질문이며, 지원하지 않는 기능에 대한 질문도 INFO가 될 수 있다. ‘오늘 주식 추천해 줘’처럼 등록된 키오스크 지원 과업 밖의 요청은 별도 범위 밖 상태로 기록한다.

### 4.4 취소·뒤로·초기화와 부정을 분리한다

- ‘뒤로 가고 싶어요’는 I07, ‘라떼만 취소해 주세요’는 I08, ‘주문을 처음부터 다시 할게요’는 I14다.
- ‘취소하고 다시 처음부터’는 미결제 초안 전체 초기화의 한 표현이면 I14 하나다. 결제된 거래를 취소하고 새 주문을 시작하려는 두 목표가 확인되면 I08+I14다. 문맥이 없으면 둘 중 하나를 정답으로 강제하지 않는다.
- ‘취소하지 마세요’는 취소 **금지**다. 긍정 요청 목록에는 I08을 넣지 않고 금지 제약에 취소를 기록한다. ‘말을 멈추지 마’도 음성 중지 요청으로 처리하지 않는다.
- ‘결제하지 말고 처음으로’는 I14와 결제 진행 금지 제약이다. 부정된 결제를 긍정 I13으로 추가하지 않는다.
- ‘취소하면 처음으로 가나요?’는 결과에 대한 I10 질문이다. 인용·가정·질문에 나타난 동작을 실행 요구로 취급하지 않는다.
- 대상 없는 ‘멈춰’는 음성 재생 중지·거래 중단 등을 혼동할 수 있다. 별도의 앱 중지 버튼 이벤트와 구분한다. 명시적 앱 중지 버튼은 의도분류 평가를 거치지 않고 즉시 처리하는 대상이다.

### 4.5 원래 의도와 가능한 대응을 분리한다

‘키오스크 글씨를 키워 주세요’의 원래 의도는 I11, 대상=KIOSK다. 외부 기기 직접 제어가 현재 범위에 없다는 사실을 별도 기록한다. 대응으로 설정 위치를 안내할 수 있어도 원래 요청의 라벨을 I09로 바꾸지 않는다. ‘키오스크 글씨는 어디서 키워요?’는 처음부터 방법을 묻기 때문에 I09다.

‘글씨 키워 주세요’는 I11 판정이 가능하지만 대상=UNKNOWN일 수 있다. 앱 표시를 바꾸기 전에 대상을 확인한다. 이 구분은 의미 분류의 정답을 앱 구현 상태에 종속시키지 않기 위한 것이다.

### 4.6 여러 의도와 여러 값을 구분한다

‘두 개는 포장하고 하나는 먹을게요’는 I03 하나에 두 배분 값을 기록한다. ‘아메리카노 한 잔 주문하고 영수증도 주세요’는 I01+I05다. ‘카드로 할게요. 어디에 대면 돼요?’는 I04+I09다. 요청 순서와 각 대상의 연결도 보존한다.

평가 원본에는 사용자가 표현한 요청을 모두 기록한다. v0.2의 ‘최대 두 요청 처리’는 추후 앱 처리 제한을 정하는 제안이며 정답에서 세 번째 요청을 삭제하는 기준이 아니다. 처리 한도를 넘을 때는 요청을 나누어 확인하는 행동을 평가한다.

## 5. 모름·재질문·오류를 구분하는 기준

| 구분 | 예시 | 정답 기록 | 기대 대응 |
|---|---|---|---|
| 의도는 분명하고 대상만 빠짐 | ‘민원서류 떼러왔어요’ | I01, 서류 종류 누락 | 어떤 서류인지 질문 |
| 의도는 분명하고 지시 대상이 빠짐 | ‘이거 어떻게 해요’ | I09, 지시 대상 누락 | 대상·현재 화면 확인 |
| 의도는 분명하고 답변 근거가 없음 | ‘삼성페이 돼요?’ + 지원 정보 없음 | I10, 지원 근거 없음 | 화면·등록 자료 확인, 미확인 상태 안내 |
| 의도 후보 자체가 갈림 | ‘그 커피 그거 뜨거운 걸로 하나요’ | 주문/지원 질문 후보, 의도 미확정 | 새 주문인지 뜨거운 음료 제공 여부 질문인지 확인 |
| 질문인지 진술인지 불명 | ‘번호표 뽑는 거 알아요’ | 방법 질문 I09 또는 ‘알고 있다’는 진술 후보 | 방법 안내를 원하는지 확인 |
| 긍정 실행 요구 없음 | ‘취소하지 마세요’ / ‘사용법은 알아요’ | 금지 제약 / 진술. 긍정 의도 목록은 비어 있을 수 있음 | 제약 반영 / 추가 실행 유발 금지 |
| 요청이 서비스 범위 밖 | 키오스크 과업과 무관한 창작 요청 | 범위 밖, 별도 주제 기록 | 지원 범위 안내 |
| 입력·모델·형식 문제 | 무음, 추론 시간 초과, 잘못된 출력 형식 | 기술 오류 종류 | 단계에 맞는 재입력·복구 |

`NEED_CLARIFICATION` 같은 하나의 처리 상태만 정답으로 남기면 위 원인이 섞인다. 라벨링 자료에는 **의도 확정 여부, 누락 대상, 근거 유무, 제약, 기대 대응**을 각각 기록한다. 실제 모델의 짧은 출력 형식은 이 의미 계약을 바탕으로 후속 단계에서 확정한다. 위 표가 새로운 런타임 API 구현은 아니다.

모든 애매한 입력에 여러 라벨을 나열하면 정답으로 인정하는 방식은 사용하지 않는다. 의도 자체가 불명확한 경우에는 적절한 확인 질문이 필요하고, 의도가 명확한데 대상만 빠진 경우에는 해당 의도와 대상 누락을 함께 맞혀야 한다.

## 6. 영향도·복잡도·우선순위 부여 기준

### 6.1 영향도: 잘못 안내했을 때의 결과

| 등급 | 부여 기준 | 상황 예시 |
|---|---|---|
| L | 국소적이고 쉽게 되돌릴 수 있는 앱 표시·재생 조절 등. 금전·민감정보·중요 상태 변경과 연결되지 않음이 확인됨 | KioGuard 글씨 확대, 현재 안내 다시 듣기 |
| M | 수정 가능하나 잘못된 선택·재작업·잘못된 동선으로 이어짐 | 결제 전 상품·옵션 선택, 창구 이동 안내 |
| H | 금전 확정/취소, 민감정보 입력·노출, 중요한 신청 확정, 복구 어려운 상태 소실로 이어지는 안내 | PIN 입력 위치, 결제 최종 확인, 작성 내용 소실이 있는 초기화 |
| U | 단계·대상·되돌리기 가능성 등 영향 판정의 핵심 정보가 없음 | 문맥 없는 ‘처음으로’, 제어 대상 불명확한 ‘글씨 키워 주세요’ |

현재 한 단계에서 발생할 수 있는 잘못된 안내의 결과를 평가한다. ‘언젠가 결제할 주문’이라는 이유만으로 모든 주문 발화를 H로 만들지 않는다. 다만 금전·개인정보 등 보호 주제 표시는 별도로 유지하며, U를 L로 가정해 Rule에 통과시키지 않는다. 실제 결과 등급과 보수적인 처리 정책을 구분한다.

### 6.2 복잡도: 의미 해석에 필요한 작업

| 등급 | 부여 기준 | 예시 |
|---|---|---|
| C1 | 관례적으로 명확한 단일 요구, 단순 값, 관계·부정·지시어 해석이 거의 없음 | ‘다시 읽어 주세요’, ‘현금으로 낼게요’ |
| C2 | 한 가지 요구에 복수 속성·수량·표현 변형 등을 해석해야 함 | ‘카페라떼 뜨겁게 한 잔’ |
| C3 | 부정 범위·정정·조건·복수 요청 관계·지시어·대화 의존·간접적 어려움 표현을 해석해야 함 | ‘두 개는 포장하고 하나는 먹을게요’, ‘그거 말고 아까 것’ |
| CU | 입력 훼손 등으로 의미 구조 자체를 판정하기 어려움 | 핵심 단어가 사라진 인식 결과 |

적용 가능한 조건 중 높은 복잡도를 부여하고 이유를 기록한다. 알려진 지시어·부정 구조가 있지만 문맥만 빠졌으면 C3와 문맥 누락을 함께 기록한다. 단순 대상 누락만으로 C3/CU를 자동 부여하지 않는다. 공손한 어미나 짧은 문장 자체도 등급의 결정 근거가 아니다.

복잡도는 실제 연산량·토큰 수·지연시간의 측정값이 아니다. 같은 C1도 보호 대상이면 LLM 검토 경로가 될 수 있고, C3이지만 짧을 수 있다.

### 6.3 Router에 전달할 정책과 제한

| 조건 | 제안 정책 |
|---|---|
| L + C1 + 검증된 전체 Rule 패턴 한 개 + 상태/필수 값 충족 | 저우선순위 직접 처리 후보 |
| H 또는 C3 | 고우선순위 검토: LLM 의미 해석과 상태·근거 검증 대상 |
| M 또는 C2 | 일반 검토: 초기 설계에서는 LLM 경로 |
| U 또는 의미 판정 불가/필수 문맥 부재 | 미확정: 필요한 정보 수집·재질문. 정보 없이 LLM을 반복 호출하지 않음 |

‘고우선순위’는 주의 깊게 검토해야 한다는 뜻이며 처리 대기열 순서가 아니다. 이 표는 정책 제안이다. 해당 의도가 실제 Rule로 안정적으로 처리되는지, LLM이 더 정확한지, 호출률이 얼마나 줄어드는지는 아직 검증해야 한다.

## 7. 승인 후 사용할 라벨링 기록과 평가 범위

### 7.1 기록할 항목

| 기록 묶음 | 필수 내용 |
|---|---|
| 출처 | 사례 ID, 원문, 기존 라벨, 출처 버전, 동일/유사 표현 그룹 |
| 입력 문맥 | 도메인, 실제 화면/요약, 현재 단계, 선택 대상, 직전 질문, 상태 근거. 미확인 값은 미확인으로 유지 |
| 의미 정답 | 발화 유형, 긍정 요청 의도 목록, 주제, 대상·값, 금지/배제 제약, 요청 순서 |
| 불확실성 | 의도 확정 여부, 후보가 갈리는 조건, 빠진 값·문맥, 답변 근거 유무 |
| 영향·복잡도 | H/M/L/U, C1/C2/C3/CU, 각 등급의 이유. Rule 검증 여부는 별도 |
| 기대 처리 | 바로 안내 가능/대상 확인/지원 근거 확인/범위 안내/실행 보류 등과 금지 행동 |
| 검수 | 작성자, 독립 검수자, 불일치 이유, 합의 결과, 정의 버전 |

PIN·식별번호 등 실제 민감값은 정답 슬롯으로 수집하지 않는다. 입력 위치·정보 종류를 판단할 수 있는 비식별 시나리오를 사용한다.

### 7.2 비교 실험에서 지켜야 할 조건

1. **텍스트만 보는 평가와 문맥을 함께 보는 평가를 분리한다.** 정답 판정에 사용한 문맥은 모델 입력에도 제공한다. 제공하지 않은 화면 정보를 모델이 추측해야 정답이 되는 설계는 피한다.
2. 의도가 확정된 사례의 단일/다중 의도 정확도·의도별 정밀도/재현율·Macro-F1, 필수 값·부정 제약 정확도를 구분한다. 동일한 정의와 평가기를 FP 기준·PTQ·QAT에 적용한다.
3. 의도가 애매한 사례는 단일 라벨 정확도의 분모에서 구분하고 개수·제외 이유를 공개한다. 해당 사례의 적절한 재질문/추측 실행 여부는 별도 평가하며 전체 처리 성공 평가에서 누락하지 않는다.
4. 과도한 재질문도 실패가 될 수 있다. 명확한 사례의 불필요한 재질문 비율과 불명확한 사례의 재질문 적중률을 함께 기록한다.
5. 모델의 모든 사례 회피를 막기 위해 전체 사례의 올바른 처리 비율과 응답/안내 가능한 사례 비율을 함께 본다. 파싱 실패·시간 초과를 일반 미분류와 합치거나 평가에서 조용히 제외하지 않는다.
6. 같은 문장·단순 변형은 그룹 단위로 분리해 학습·개발·독립 평가 간 누출을 관리한다. 동일 발화의 상황별 사례도 관련 그룹 정보를 유지한다.

이번 문서는 **무엇을 맞혀야 하는지**를 정하는 단계다. 새 정확도 목표치·허용 지연·메모리 한계는 여기서 임의 확정하지 않는다. 기존 v0.2의 목표 숫자도 측정된 성능으로 해석하지 않는다.

## 8. 근거와 선택의 장단점

근거 자료는 기존 48행의 원문·V1 라벨, v0.2 명세와 이전 감사 결과다. 이번에는 로컬에 보존된 검토 자료를 대조했으며 Drive·원본 엑셀의 최신 변경을 다시 조회한 것은 아니다. 회의록의 제안은 참고 자료이고, 현재 사용자가 정한 전체 온디바이스·선택적 LLM/Rule 목표를 우선한다.

| 선택 | 근거·장점 | 비용·어려움 |
|---|---|---|
| 8개에서 14개 요청 종류로 세분화 | 결제/영수증, 뒤로/취소/처음, 정보/방법을 구분해 잘못된 다음 안내를 분석할 수 있음 | 적은 데이터에서 일부 의도가 부족해짐. 14개 유지 여부는 검수 결과로 재판단 |
| 주제와 의도를 분리 | 결제 관련 정보 질문과 결제수단 선택을 다른 정답으로 표현 | 의도만 채점하던 기존 평가기를 수정해야 함 |
| 문맥·누락 정보를 별도 기록 | 확실한 의도를 유지하면서 필요한 확인 질문을 평가 | 화면·단계 수집과 사람 라벨링 비용 증가 |
| UI_CONTROL에 제어 대상을 명시 | 외부 제어 미지원 때문에 사용자의 의도 라벨이 바뀌는 문제 방지 | 기존 APP_CONTROL 코드와 버전 매핑 필요 |
| 영향도와 복잡도를 독립 기록 | 고영향의 짧은 발화와 저영향의 복잡한 발화를 구분 | 주관적 등급 불일치가 생길 수 있어 이유·사례·독립 검수 필요 |
| 기존 48행 보존 | 과거 실험의 추적성과 오류 회귀 점검 유지 | 새 의도 체계 점수와 과거 8개 의도 점수를 직접 비교할 수 없음 |

기존 결과에 대한 사실 판단은 [Colab 실험 검토보고서](KioGuard_기존_Colab_실험_검토보고서.md)를 따른다. 기존 48행은 개발·회귀 검토용으로 보존하며 새 독립 평가셋으로 승격하지 않는다. 이번 라벨 변경만으로 과거 모델의 성능 향상·저하를 주장하지 않는다.

## 9. 승인 항목과 다음 단계

| 승인 항목 | 권고안 |
|---|---|
| A1 의도 체계 | 14개 ID를 이번 검수용 체계로 채택. 최종 동결은 사람 간 경계 검수 후 |
| A2 설정·변경 경계 | I02에 최초 옵션 설정 포함. 새 대상 요청의 옵션은 I01에 포함 |
| A3 제어 의도 | I11을 UI_CONTROL로 개정하고 APP/KIOSK/UNKNOWN 분리 |
| A4 누락·부정·복합 요청 | 의도와 누락 문맥 분리, 부정은 제약으로 보존, 복합 요청과 값 배분 구분 |
| A5 영향도·복잡도 | H/M/L/U와 C1/C2/C3/CU 독립 기록. U를 저우선순위로 통과시키지 않음 |
| A6 기존 48행의 지위 | 원본·과거 점수 보존, 새 표는 조건부 검토안, 독립 테스트로 사용하지 않음 |

**다음 작업은 승인 후 진행한다.** 먼저 정의가 갈리는 대표 사례에 실제 또는 명시적으로 설계한 문맥을 붙이고, 두 사람이 독립 라벨링한 차이를 검토한다. 설계한 문맥은 과거 실제 화면으로 표시하지 않는다. 합의된 정의·정답 계약을 버전으로 고정한 뒤 새 데이터 분할과 평가 명세를 작성한다.

모델 후보 비교, 원정밀도 기준 평가, PTQ, QAT, 실기기 메모리·지연·발열 시험은 그 평가 기준을 적용하는 후속 작업이다. QAT는 사용자 담당 연구 범위로 유지하되, 정확도가 회복되거나 반드시 개선된다는 전제를 두지 않는다.

# KioGuard 의도분류·온디바이스 LLM 설계안

버전: v0.1 초안 · 작성/공식 자료 확인일: 2026-09-27 · 구현 및 신규 실험 전

## 문서의 전제와 근거 구분

목표는 스마트폰에서 한국어 발화 의도를 정확하게 처리하면서 LLM 호출량, 토큰, 지연, RAM, 발열을 줄이는 것이다. 모든 사용자 음성·텍스트의 AI 처리는 단말 내부에서 수행한다. 서버 LLM, 클라우드 AI, A2A는 범위에서 제외한다. 핵심 파이프라인은 Voice → whisper.cpp STT → Routing → Rule/LLM → 검증 → 안내 → sherpa-onnx TTS다. OCR은 이번 비교의 독립변수에서 제외한다.

Galaxy S24 Ultra는 보유 테스트 기기이며 목표 기종이나 최소 사양이 아니다. llama.cpp 기반 GGUF 실행 경험을 활용하되, 다른 런타임은 별도 비교군으로 취급한다. 모델 다운로드 후 비행기 모드에서도 핵심 기능이 동작하는지 검증한다.

문서의 근거는 세 종류로 구분한다.

- **기존 보고값:** 사용자가 제공한 컨텍스트에 기록된 결과. 원본 xlsx·실험 로그·모델 파일은 이번 작업에서 확인하지 않았다.
- **공식 확인 사실:** 링크된 모델 카드·공식 기술 문서에서 확인한 내용. KioGuard에서의 성능이나 Android 실행 성공을 의미하지 않는다.
- **설계 제안/검증 가설:** 아래 정책, 표본 수, 임계값, 실험 순서. 아직 측정하거나 확정한 결과가 아니다.

## 0. Baseline/V1 보존

### 0.1 기존 구조와 성능

기존 구조는 Rule Main + LLM Fallback이다. confident는 Rule 결과, multi_match는 우선순위 Rule, no_match는 LLM 호출로 처리했다.

| 항목 | 기존 보고값 | 해석의 한계 |
|---|---:|---|
| Rule 단독 정확도 | 약 93.8% | 기존 평가셋 기준 |
| Embedding classifier 정확도 | 약 89.6% | 동일 조건 여부는 원본 기록 확인 필요 |
| LLM 단독 정확도 | 약 85.4% | 아래 Gemma 결과와 연결되는 보고값 |
| Rule + LLM Hybrid 정확도 | 약 97.9% | 새 데이터에 대한 성능 보장 아님 |
| LLM 호출률 | 약 4% | 새 구조의 목표치로 강제하지 않음 |
| 학습/평가 데이터 | 약 247개 / 약 48개 | 평가셋이 Rule 설계의 영향을 받았을 가능성 |

| 기존 비교 모델 표기 | 정확도 | latency | 원본 크기 |
|---|---:|---:|---:|
| Qwen2 1.5B | 약 62.5% | 약 285ms | 약 2.97GB |
| Gemma 2B | 약 85.4% | 약 465ms | 약 4.9GB |
| Phi-3-mini 3.8B | 약 79.2% | 약 1238ms | 약 7.29GB |
| TinyLlama 1.1B | 0% | 약 843ms | 약 2.2GB |

latency 측정 구간, 로딩 포함 여부, backend, prompt, decoding, 측정 횟수는 원본 확인 전까지 미상이다. 이 값을 신규 결과와 직접 순위 비교하지 않는다. TinyLlama 0%도 모델의 일반적 능력이 0이라는 뜻으로 해석하지 않는다.

**모델 식별 확인 필요:** 컨텍스트의 “Gemma 2B”와 일부 “Gemma 2” 표기를 동일 모델로 단정하지 않는다. 모델 ID, 세대, instruct/base 여부, 원본 revision, GGUF metadata/hash를 확보한 뒤 재현한다. 확보할 수 없으면 “V1 보고값”과 “재구성 baseline”을 구분한다.

### 0.2 보존할 문제해결 사례

Gemma 2B 크기는 FP16 약 4.9GB → Q8 약 2.6GB → Q4_K_M 약 1.6GB로 보고되었다. 초기 INT4 정확도 약 68.8%가 Chat Template 수정 후 약 77.1%, Output Parsing 수정 후 약 85.4%로 회복되었고, 최종 기존 평가에서 FP16/Q8/Q4는 모두 약 85.4%였다.

이 결과는 **해당 평가에서 template/parser 수정으로 관측된 성능 저하가 해소되었다**는 사례다. “4비트는 언제나 손실이 없다”는 결론은 아니다. 앞으로도 template·parser·변환 문제를 먼저 분리한 후 양자화 손실을 판단한다.

V1 데이터·Rule·prompt·parser·모델·런타임 버전은 별도 보관한다. 새 실험은 V2로 기록하며 V1 표와 결과 파일을 덮어쓰지 않는다. V1 평가셋은 회귀 확인용으로만 사용하고 V2 최종 성능 주장에는 사용하지 않는다.

## ① 의도 우선순위 기준

### 1.1 사용자 영향도와 의미 이해 난도를 분리한다

우선순위는 “먼저 실행할 의도”가 아니라 **오분류를 얼마나 엄격하게 방지할지**를 정하는 기준이다. 높은 영향도가 자동으로 높은 LLM 신뢰도를 의미하지 않는다.

- **영향도 H:** 금전·주문 내용·진행 상태 손실, 되돌리기 어려움. 확인 절차를 강화한다.
- **영향도 M:** 잘못된 선택·재작업·이용 중단을 유발할 수 있음. 문맥 검증을 적용한다.
- **영향도 L:** 쉽게 복구할 수 있는 단순 안내. 오류를 허용한다는 뜻은 아니다.
- **난도 S:** 전체 발화가 검증된 단일 표현이고 대상·문맥이 명확함.
- **난도 C:** 부정, 정정, 간접 표현, 복합 의도, 지시어, 문맥 의존 등이 있음.

영향도 등급은 아래의 초기 가설이다. 실제 사용자 과업 관찰과 오류 사례로 조정한다. 취약 이용자의 도움요청을 단순 저우선순위로 취급하지 않는다.

### 1.2 Intent Priority Table

| 의도 | 초기 영향도·오분류 영향 | 난도 | Rule 가능 조건/예시 | LLM 필요 사례·반례 | 근거·검증 지점 |
|---|---|---|---|---|---|
| 주문 | M~H: 상품·수량 오류 | S~C | 확인된 메뉴와 수량의 닫힌 패턴: “아메리카노 한 잔” | “아까 것 말고 덜 단 걸로”; “주문 취소해”를 주문으로 잡지 않음 | 대상과 수량 누락·정정 처리 평가 |
| 옵션 변경 | M, 알레르기 등은 H: 잘못된 옵션 안내 | S~C | 현재 선택 상품이 확인된 상황의 “얼음 빼줘” | “우유는 안 맞는데 다른 걸로 될까?” | 대상·부정·대체 옵션 이해. 알레르기 안전성을 추측하지 않음 |
| 매장/포장 | L~M: 수령 방식 오류 | S~C | 방식 선택 단계의 “포장이요” | “여기서 먹으려 했는데 가져갈게”; “포장은 어떻게 해요?”는 정보문의 가능 | 단어보다 발화 기능을 구별 |
| 결제 | H: 금전·다음 단계 오안내 | S~C | 결제 가능한 문맥의 “카드로 결제할게요”; 확인 정책 적용 | “다 골랐는데 이제 어떻게 해?”; “생일 카드 문구”는 OOD | 높은 영향도와 단순 표현의 예외를 함께 검증 |
| 할인/쿠폰 | M~H: 할인 누락·결제 금액 혼동 | S~C | 적용 단계의 “쿠폰 적용해줘” | “이 쿠폰 쓰면 적립도 돼?” | 사용 의도와 조건 문의를 구별. 혜택 사실을 생성하지 않음 |
| 취소/처음으로 | H: 주문·진행 상태 손실 | S~C | 전체 일치 “처음으로”; 기존 선택이 있으면 확인 | “결제하지 말고 처음으로 돌아갈래”; “취소하지 마” | 부정과 취소 대상 범위가 핵심 |
| 도움요청 | M~H: 이용 중단·접근성 저하 | S~C | “도와주세요” → 일반 도움 안내 | “뭘 눌러야 할지 모르겠어”; 반복 실패 | 일반 도움은 즉시 제공, 구체적 과업 안내는 문맥 검증 |
| 정보문의 | L~H: 가격·성분 등 잘못된 정보 | S~C | 정의된 FAQ와 확인된 정보에 한정 | “이거 우유 들어가?”; “오늘 날씨?”는 OOD | 문의 대상·범위를 판별. 정보 미확보는 별도 사유로 안내 |

의도 라벨과 주제는 분리한다. 예를 들어 “쿠폰 쓸 수 있어요?”는 정보문의와 쿠폰 주제가 함께 존재한다. V2에서는 `정보문의 + topic=쿠폰`처럼 주석 원칙을 명시하고, 기존 데이터의 라벨 기준이 다르면 V1을 수정하지 않고 V2에 별도 매핑을 둔다. 슬롯/주제 추출은 의도 정확도와 별도 평가한다.

복합 발화에서는 결제 키워드의 고정 우선순위로 다른 의도를 버리지 않는다. “포장할 건데 카드로 계산할게”는 두 요구를 보존하고 포장 선택 후 결제 안내 순서를 구성한다. “결제하지 말고 처음으로”는 결제를 긍정 의도로 포함하지 않는다. 대상·순서가 불명확하면 재질문한다.

## ② LLM / Rule Routing

### 2.1 제안 구조

Voice → STT → 입력 유효성 확인 → 경량 Router → Rule 또는 온디바이스 LLM → 공통 Validator → 상태별 처리 → 검증된 안내 템플릿 → TTS

LLM의 주 역할은 간접·부정·정정·복합 표현 해석, 문맥 기반 의도 판단, OOD/모호성 구분이다. 새 구조는 Rule 실패에만 LLM을 호출하는 V1과 달리, 의미 해석이 필요한 발화를 처음부터 LLM 경로로 보낸다. 분류를 위해 자유로운 장문 답변 생성은 요구하지 않는다.

### 2.2 Router는 Rule 처리 자격만 좁게 판정한다

Router가 8개 의도를 완전하게 분류하도록 만들지 않는다. 입력 길이만으로 난도를 결정하거나 특정 단어 하나로 의도를 확정하지 않는다. Rule과 Router가 동일한 패턴 목록을 공유하여 중복 분류를 줄인다.

| 순서 | Router가 확인하는 관측 정보 | 경로 |
|---|---|---|
| 1 | 빈 STT 결과, 잘림, 음성 없음, 명백한 인식 실패 | 재발화 요청; 엔진 고장은 ENGINE_ERROR |
| 2 | 전체 발화가 승인된 단일 패턴과 일치하는가 | 불일치면 LLM |
| 3 | 해당 패턴의 필수 대상과 현재 단계가 확인되는가 | 문맥이 불확실하면 LLM 또는 명백한 필수정보 재질문 |
| 4 | 부정·정정·여러 절·복수 후보·미처리 잔여 표현이 있는가 | 발견되면 LLM |
| 5 | 패턴별 Rule 허용 정책과 검증 기준을 통과하는가 | 통과 시 Rule; 그 외 LLM |

정규화는 공백·허용된 표기 변이 등에 한정한다. “안”, “말고”, 숫자, 상품명 등을 삭제하지 않는다. 부정 탐지 규칙이 모든 자연어를 잡는다고 가정하지 않으며, 전체 일치의 좁은 허용 목록으로 놓침 위험을 줄인다. 단순한 OOD도 일치하지 않으면 LLM으로 갈 수 있다.

고영향 단순 패턴의 Rule 허용은 별도 실험 항목이다. 초기 운영 가설은 **저영향 단순 표현만 Rule 허용**이며, “처음으로” 같은 고영향 단순 표현은 개발셋에서 기준을 통과하고 확인 정책이 있을 때 예외를 활성화한다. 이는 영향도·난도 2축 정책을 단계적으로 도입하기 위한 선택이다.

### 2.3 결과 계약과 공통 검증

논리적 결과는 `status`, `intents`, 필요한 `target/slots`, `reason_code`, `route`, `requires_confirmation`으로 구성한다. LLM이 이 모든 필드를 생성해야 하는 것은 아니다. route와 오류 사유, 확인 필요 여부 등은 애플리케이션이 채운다.

- 단일 의도·대상 명확: 의도 코드 하나를 출력한다.
- 복합 의도: 제한된 의도 목록/최소 슬롯 형식을 사용한다. 단일 코드 출력 실험에서는 NEED_CLARIFICATION으로 넘기는 대안과 별도 비교한다.
- OOD·모호성: OUT_OF_SCOPE 또는 NEED_CLARIFICATION 코드를 허용한다. 8개 중 하나로 강제하지 않는다.
- Validator: 허용 라벨, 출력 완결성, 슬롯 존재, 현재 과업과의 일관성, 실행 가능 여부, 확인 필요 여부를 검사한다.

문법 제약은 형식 오류만 줄일 수 있으며 의미의 정답을 보장하지 않는다. LLM이 직접 쓴 confidence는 검증된 확률로 사용하지 않는다. 확률 점수를 쓰려면 개발셋에서 별도 보정·임계값 검증이 필요하다. 문맥은 앱이 실제로 알고 있는 상태만 사용하고, 키오스크 상태를 볼 수 없다면 “미확인”으로 취급한다.

결제·전체 취소 등 결과 영향이 큰 안내 전에는 필요에 따라 짧은 확인을 요청한다. 의도분류 성공이 결제·취소의 실행 승인을 뜻하지 않는다. 현재 범위는 이용 보조이며 실제 키오스크 조작 연동이 있다면 별도 권한·확인 정책을 적용해야 한다.

### 2.4 비교할 구조

| 실험군 | 정책 | 검증 목적 |
|---|---|---|
| R0 | V1 Rule Main + LLM Fallback 동결본 | 기존 구조의 V2 데이터 재평가 |
| R1 | Rule 단독 | 단순 규칙의 한계 |
| R2 | LLM 단독 | LLM 기준 성능·비용; 팀 최종안은 아님 |
| R3 | 의도군 고정 분리 | 좁은 라우팅 규칙으로 저영향 의도군만 Rule 허용, 미확정은 LLM |
| R4 | 영향도 × 발화 난도 분리 | 같은 의도 내 단순/복잡 경로 분리의 효과 |

R3도 정답 의도를 Router에 미리 주지 않는다. 실제 관측 가능한 패턴·문맥만으로 라우팅하고 라우팅 오류를 전체 성능에 포함한다. 구조 비교에서는 동일 모델·양자화·prompt·Validator를 고정한다. V1 그대로의 결과와 공통 Validator를 붙인 재구성 결과는 구분한다.

## ③ 오류 Fallback 상태 설계

상태는 의도와 분리한다. UNKNOWN은 내부 원인 미확정 표기로만 남기고, 사용자 응답 전에는 아래 상태와 구체적 reason으로 정리한다.

| 상태 | 진입 예 | 다음 동작 | 금지/종료 조건 |
|---|---|---|---|
| OK | 형식·의미·문맥 검증 통과 | 필요한 확인 후 템플릿 안내 | 확인 전 고영향 처리를 확정하지 않음 |
| OUT_OF_SCOPE | “생일 카드 문구 알려줘” | 지원 범위를 한 문장으로 안내 | Rule 재분류하지 않음; 해당 턴 종료 |
| NEED_CLARIFICATION | “이거 바꿔줘”, 대상 누락, 상충 요구 | 누락된 항목 하나를 쉬운 질문으로 확인 | 임의의 대상·의도를 채우지 않음 |
| INVALID_OUTPUT | 잘못된 라벨, 잘림, 파싱 불가 | 예산 내 제한 재시도 1회; 이후 엄격한 Rule 자격을 다시 검사 | Rule 자격 없으면 재질문/제한 안내; LLM↔Rule 반복 금지 |
| ENGINE_ERROR | 로딩 실패, OOM, timeout, 추론 중단 | 엔진 실패 안내; 검증된 Rule 기능/수동 도움 경로 제공 | OOD·복잡 발화를 Rule로 강제 처리하지 않음 |

**제안 예산:** 한 사용자 턴에서 LLM 본 호출 최대 1회, INVALID_OUTPUT 재시도 최대 1회. 총 시간 예산 초과 또는 ENGINE_ERROR에는 자동 재호출하지 않는다. 재질문은 한 과업에서 연속 최대 2회 후 버튼 선택·직원 도움 등 사용 가능한 대안을 안내한다. 이 횟수는 사용자 시험으로 조정할 초안이며 시간 예산(ms)은 기기 실측 후 동결한다.

INVALID_OUTPUT 재시도는 동일 입력과 검증된 출력 제약으로 수행한다. ENGINE_ERROR 후 Rule 경로를 열더라도 원 발화에 최초와 같은 좁은 자격 검사를 적용한다. 이전에 OUT_OF_SCOPE로 확정된 결과는 fallback으로 뒤집지 않는다.

상태 전이는 다음 원칙을 따른다.

- 검증 성공 → OK → 확인 필요 시 NEED_CLARIFICATION(reason=confirmation_required) → 사용자 확인 → 안내.
- 의미적으로 모호하거나 복합 요구의 대상·순서 불명 → NEED_CLARIFICATION → 후속 발화를 제한된 문맥과 함께 다시 처리.
- 지원 범위 밖 → OUT_OF_SCOPE → 종료. 단순 반복 LLM 호출 없음.
- 문법 정상이어도 필수 대상 누락은 INVALID_OUTPUT이 아닌 NEED_CLARIFICATION으로 처리.
- ENGINE_ERROR → 제한 모드 → 명시적 재시작/자원 회복 후에만 정상 모드 복귀.

“OUT_OF_SCOPE”와 “서비스 안의 문의지만 답할 정보가 없음”을 구별한다. 후자는 INFO 의도를 보존하되 `reason=information_unavailable`로 확인 불가 안내를 한다. 메뉴 가격·쿠폰 조건을 모델 기억으로 만들어 답하지 않는다.

STT 오인식으로 부정어가 사라지면 Intent 모델만으로 복구하기 어렵다. 인식 품질 신호가 제공되는 경우 참고하되 그대로 신뢰 확률로 간주하지 않는다. 고영향 과업의 되묻기와 음성 종단 평가로 별도 검증한다.

### 4.2 사전 실행성 게이트

각 후보마다 공식 ID/revision, 라이선스·재배포 조건, tokenizer/template, 변환 도구 commit, 지원 연산, 실제 backend를 기록한다. 한국어 입력 → 완결된 결과 → parser → 오프라인 실행의 작은 smoke test를 먼저 통과시킨다. 공개 문서의 지원 안내와 현재 프로젝트 JNI/NDK 빌드에서의 실행 성공을 구분한다. [llama.cpp 공식 저장소](https://github.com/ggml-org/llama.cpp)를 기준으로 지원을 확인하되 실행 로그로 최종 판정한다.

공유 ggml을 사용하는 whisper.cpp/llama.cpp의 버전 충돌, 링크 충돌, 동시 실행 메모리를 확인한다. 새 LLM 지원을 위해 런타임을 갱신했다면 STT 회귀 검증도 수행한다.

### 4.3 공정한 비교 프로토콜

1. **모델 비교:** 동결한 V2 개발/평가 split, 의도 정의, 의미상 동일 prompt, 출력 계약, 최대 문맥, decoding 정책을 사용한다. 모델 고유의 공식 chat template는 올바르게 적용한다. 문자열 template를 억지로 같게 만들지 않는다.
2. **공통 조건 트랙:** 같은 런타임·backend·지원 양자화 형식에서 비교 가능한 후보끼리 비교한다. 한 번에 모델만 바꾼다. 같은 Q4 이름이어도 레이어별 실제 정밀도가 다를 수 있어 artifact 크기·metadata를 기록한다.
3. **최적 배포 트랙:** LiteRT-LM 등 모델별 최적 runtime/포맷은 별도 표로 비교한다. 이 차이를 모델 자체 효과나 순수 양자화 효과라고 부르지 않는다.
4. **품질 기준:** FP16/BF16 등 지원 기준 정밀도 결과를 확보한다. 휴대폰에 올라가지 않으면 로컬 연구 장비에서 품질 기준만 측정하고 휴대폰 latency/RAM 비교에서는 제외한다. OOM은 실패로 기록한다.
5. **성능 측정:** cold start와 warm inference를 분리한다. seed, thread 수, context/KV 설정, backend, 캐시 정책, 앱·OS 버전을 고정한다. 기본 비교에서는 사고 출력을 끄는 공식 설정이 있는 경우 사용하고, 불가능하면 전체 생성 토큰·시간에 포함한다.
6. **실행 순서:** 개발셋으로 후보를 좁힌 뒤 Router, PTQ, 토큰 실험을 각각 진행한다. 최종 조합은 독립 test에 한 번 적용한다. 상호작용은 별도 소규모 조합 실험으로 확인한다.

## ⑤ 양자화 / QAT 실험 계획

### 5.1 PTQ: 먼저 실제 손실을 분리한다

동일한 원본 revision에서 기준 정밀도 → Q8_0 / Q5_K_M / Q4_K_M을 각각 생성하는 것을 우선한다. 변환 지원이 없는 조합은 N/A로 표시한다. 이미 Q4인 파일을 Q8로 바꾸거나 다른 저비트 파일을 재양자화해 정밀도 비교를 구성하지 않는다.

각 정밀도에서 동일 입력 ID별로 정답/오답, 원출력, 파싱 결과, 상태, latency, 파일 크기, Peak RAM을 비교한다. 출력 형식 오류를 버리고 정확도를 계산하지 않는다. 양자화 외에는 template, prompt, parser, runtime, decoding을 고정하고 KV cache 양자화는 별도 실험으로 둔다.

성능 저하가 관측되면 다음 순서로 점검한다.

1. 모델·tokenizer·공식 template와 BOS/EOS 중복, instruct/base 불일치.
2. 출력 잘림, 허용 라벨 정의, parser, 문법 제약, reasoning 출력 처리.
3. 원본과 변환물 일치, 런타임 지원, 동일 입력/문맥/decoding 사용 여부.
4. 원인 교정 후 paired 결과와 신뢰구간으로 남은 품질 손실 확인.

### 5.2 QAT 진입 조건과 비교군

**진입 가설:** 목표 PTQ에서 반복 가능한 손실이 있고, Q5/Q8로 올리는 대안이 메모리·지연 예산을 충족하지 못하며, 해당 모델과 배포 양자화 형식에 맞는 QAT 경로가 있을 때 시행한다. 손실이 없거나 측정 불확실성이 크면 QAT를 성능 개선의 필수 단계로 주장하지 않는다.

QAT는 학습 중 양자화 오차를 모사하는 방법이며, QLoRA라는 이유만으로 QAT가 되는 것은 아니다. 순수 keyword/if Rule은 QAT 대상이 아니다. [PyTorch QAT 설명](https://pytorch.org/blog/quantization-aware-training-in-torchao-ii/) 및 [torchao QAT 문서](https://docs.pytorch.org/ao/stable/workflows/qat.html)를 기술 참고로 사용한다.

| 비교군 | 조건 | 해석 |
|---|---|---|
| Q0 | 원본 기준 정밀도 | 품질 기준 |
| Q1 | 원본 → 목표 PTQ | PTQ 손실 |
| Q2 | 동일 학습 데이터·예산의 일반 fine-tuning → 목표 PTQ | 과업 학습 자체의 개선 효과 |
| Q3 | 동일 데이터·예산의 QAT → 같은 목표 포맷 | Q2 대비 양자화 모사 학습의 추가 효과 |

학습 가능한 파라미터 범위와 학습 횟수 등을 최대한 맞추고 차이는 기록한다. QAT와 배포의 weight/activation 비트 수, group size, scale·zero point, 제외 레이어를 대조한다. 일반 int4 QAT가 GGUF Q4_K_M 수치 형식을 그대로 모사한다고 가정하지 않는다. 호환되지 않으면 지원 포맷으로 별도 트랙을 만들거나 QAT를 보류한다.

공식 Gemma 4 QAT 체크포인트는 실용 배포 후보로 비교할 수 있지만, 팀이 같은 원본·데이터·학습 예산으로 수행한 QAT 실험과 구분한다. 공식 Q4_0 QAT와 Q4_K_M PTQ의 차이를 순수 QAT 효과로 해석하지 않는다. 공식 제공 경로는 [Gemma 4 문서](https://ai.google.dev/gemma/docs/core)에 명시되어 있다.

학습·calibration에는 test를 사용하지 않는다. 기존 247개만으로 QAT 효과를 확정하지 않는다. 기본 제안은 사용자 데이터가 외부로 나가지 않는 로컬 연구 장비에서 학습하고 스마트폰에서 추론하는 방식이다. 연구 학습도 스마트폰 내부만 허용해야 하는 요구가 있다면 QAT 실행 가능성을 별도로 재검토한다.

## ⑥ 토큰 최적화 계획

### 6.1 호출 절감과 호출당 절감을 분리한다

Router의 Rule 허용 범위를 넓히는 실험은 호출 수를 바꾸고, prompt 실험은 호출당 비용을 바꾼다. 두 변수를 동시에 바꿔 원인을 혼동하지 않는다. V1의 약 4% 호출률보다 낮아지는 것이 성공 조건은 아니다. 더 어려운 발화에서 LLM을 적절히 사용해 전체 오류가 줄어들면 호출률 증가는 수용할 수 있다.

| 단계 | 변경 변수 | 유지할 항목/검증 |
|---|---|---|
| T0 | 명시적 의도·경계 정의 + 최소 출력 형식 | 기준 prompt 동결 |
| T1 | system 지시의 중복·장문 축소 | OOD/모호성/부정 처리 규칙 보존 |
| T2 | 의도 설명 길이만 축소 | 주문↔문의, 결제↔쿠폰 경계 오류 확인 |
| T3 | few-shot 0/2/4개 비교 | 예시는 train/dev에서만 선정 |
| T4 | 전체 대화 대신 현재 단계·대상·직전 관련 턴 | “이거”, 정정, 후속 답변에 필요한 문맥 보존 |
| T5 | 출력 표현: 라벨/짧은 코드/최소 구조 | 동일 의미를 표현하는 형식끼리 비교 |
| T6 | 최대 출력 토큰과 종료 조건 | 코드별 tokenizer 길이+EOS 여유 확보, 잘림률 측정 |

각 단계는 이전 채택 설정에서 변수 하나만 바꾸고, 마지막에 개별 효과와 결합 효과를 재확인한다. 공식 template의 필수 제어 토큰은 삭제하지 않는다. label 하나가 token 하나라고 가정하지 않는다.

기본 단일 의도는 PAYMENT 같은 label-only를 지향한다. 복합 의도·필수 대상이 필요한 경우에는 해당 정보를 표현할 최소 구조가 필요하다. 모든 출력에 label-only를 강제해 의미를 잃지 않는다. 복합 입력을 재질문으로 처리하는 대안은 토큰 절감 외에 사용자 턴 증가까지 함께 측정한다.

실제 tokenizer 기준으로 template 포함 입력, 생성 출력, reasoning이 있으면 reasoning, 재시도 토큰을 기록한다. prompt cache는 물리적 prefill 비용과 논리적 입력 토큰을 구분하고, 캐시 on/off를 별도 측정한다. 문맥 길이 절감이 고정 크기로 할당된 KV RAM까지 자동으로 줄인다고 가정하지 않는다.

사용자 입력 1건당 평균 LLM 토큰 = 모든 본 호출·재시도의 입력+출력 토큰 합 / 전체 사용자 입력 수. Rule 전용 입력은 0으로 포함한다. 별도로 LLM 호출당 토큰과 과업 완료까지 재질문을 포함한 총 토큰·총 대기시간도 보고한다. 짧은 prompt가 정확도를 떨어뜨려 재질문을 늘리는지 확인하기 위해서다.

## ⑦ 평가 데이터·지표·채택 기준

### 7.1 V2 데이터셋 설계

Easy, Natural, Indirect, Ambiguous, Negative, Multi-intent, OOD, Context-dependent를 중복 가능한 유형 태그로 붙인다. 8개 의도와 유형을 교차해 결제·취소의 부정/정정, 유사 키워드 OOD, 슬롯 누락을 충분히 포함한다.

**초기 수집 규모 제안:** train/dev와 별개로 최종 텍스트 test 800건 이상을 계획한다. 단일 의도 명확 사례 400건(의도별 50건), OOD 150건, 재질문 필요 100건, 복합 의도 150건으로 구성하는 안이다. 실제 표본 수는 pilot의 오류율·검출하고 싶은 차이로 재산정한다. 균형 잡힌 challenge set와 실제 사용 빈도를 반영한 평가를 분리해 보고한다.

문맥 의존 사례에는 정답 판정에 필요한 상태를 함께 제공하고, 문맥이 없는 버전도 별도로 둔다. 두 명이 독립 주석 후 불일치를 조정하며 의도 집합, 부정된 요구, target, 허용되는 다음 행동을 기록한다. 사람 사이에서 답이 갈리는 사례를 억지로 단일 의도로 만들지 않는다.

분할은 표현만 무작위로 섞지 않고 화자·시나리오·paraphrase 묶음 단위로 한다. 같은 문장을 바꿔 쓴 사례가 train/dev/test에 흩어지는 누수를 방지한다. test를 본 뒤 수정한 Rule/prompt는 같은 test에 대한 최종 검증으로 주장하지 않고 새 홀드아웃을 확보한다.

음성 평가는 동의받은 화자의 발화, 속도·억양·잡음 조건을 포함하고 원음은 로컬에서 관리한다. 정답 전사 텍스트와 STT 출력을 짝지어 Intent 자체 오류와 STT 유발 오류를 구분한다. 실제 대상 이용자의 접근성 평가는 합성 문장 평가로 대체하지 않는다.

### 7.2 지표 정의

| 영역 | 지표 | 분모·측정 기준 |
|---|---|---|
| 단일 의도 | Accuracy, Macro F1, 의도별 Recall | 정답이 명확한 단일 의도 전체. 형식/엔진 오류·불필요한 재질문도 정답으로 세지 않음 |
| 복합 의도 | 의도 집합 Exact Match, micro/macro F1, 순서·대상 정확도 | 복합 의도 사례. 근거 없는 추가 의도도 오류 |
| 전체 판단 | 상태+의도 정확도, 고영향 오류율 | 각 사례의 정답 상태와 필요한 의도/대상 판정. 고영향 사례 내 오류를 별도 집계 |
| OOD | Rejection rate, false acceptance | OOD 중 OUT_OF_SCOPE 비율, OOD 중 잘못 OK 승인한 비율. clarification/error는 거절 성공과 분리 |
| 과잉 거절 | In-domain false rejection | 지원 범위 입력 중 OUT_OF_SCOPE로 거절한 비율 |
| 재질문 | 필요성 Precision/Recall, 과잉 재질문율 | 사람이 재질문 필요로 주석한 사례와 비교 |
| 복구 | Recovery success, clarification success | 주입된 복구 대상 오류 중 제한 횟수 내 올바른 안내/대안 도달 비율; 실제 재질문 시작 세션 중 해결 비율도 보고 |
| Router | Rule coverage, Rule 승인 결과 오류율 | 전체 중 Rule 완료 비율, Rule 완료 중 오답 비율. H/C/OOD별 분리 |
| 보류 | Coverage·선택 정확도 | 바로 OK로 완료한 비율과 그 부분집합 정확도를 함께 표시. 보류를 숨겨 정확도를 높이지 않음 |
| 호출 | LLM call rate, calls/input | LLM을 1회 이상 호출한 입력 비율, 재시도 포함 호출 수/전체 입력 수 |
| 출력 | Format error, truncation rate | 전체 LLM 출력 중 파싱 실패·잘림 비율; 최초 호출과 재시도 후 모두 보고 |
| 지연 | Load time, intent P50/P95, voice P50/P95 | 로딩 별도; intent는 STT 텍스트 확정→최종 상태, voice는 발화 종료→최종 상태 |
| 안내 지연 | TTS 첫 음성까지 시간 | 발화 종료→안내 음성 시작. TTS 시간과 분류 시간을 혼동하지 않음 |
| 메모리 | 파일 크기, 앱 Peak PSS/RSS, available RAM, 가속기 메모리(가능 시) | LLM 단독 및 STT+LLM+TTS 실제 생명주기. 서로 다른 메모리 지표를 합산하지 않음 |
| 토큰 | input/output/total, 과업당 총 토큰 | 실제 tokenizer, template·reasoning·재시도 포함 여부 명시 |
| 기기 | 지속 지연, 온도/thermal status, throttle·OOM 빈도 | backend와 조건을 고정해 반복 실행 |
| 종단 | Voice→올바른 의도/상태 성공률, 과업 성공률 | 의도 성공과 OOD/재질문 적절성을 별도 보고; 과업 성공은 확인·안내까지 완료 |

성공 요청만의 latency와 모든 요청의 응답/timeout 시간을 함께 제시한다. timeout·OOM을 표에서 제거하지 않는다. 재질문 사용자의 응답 대기시간과 시스템 처리시간은 분리한다.

### 7.3 기기 및 반복 측정

테스트 기기에서 SoC, CPU/GPU/NPU, RAM, Android/앱 버전, 빌드 옵션, thread 수, 실제 backend 로그를 수집한다. NPU 탑재와 NPU 실행을 구분한다. CPU 추론도 온디바이스이며 llama.cpp 사용만으로 NPU 가속을 주장하지 않는다.

초기 프로토콜 제안은 cold load 10회, 고정 평가 trace 3회 반복, warm 측정 전 조건별 동일 warm-up, 20분 이상 연속 과업 부하다. 순서를 교차하고 배터리 잔량·충전 여부·주변 온도·화면 밝기·백그라운드 작업을 기록한다. 냉각 시작 조건도 통일한다. 초기 5분과 마지막 5분의 latency/thermal status를 비교하되 이것만으로 throttle 원인을 단정하지 않는다.

음성 인식·추론·TTS의 순차 실행과 모델 상주/해제 정책을 명시한다. 실제로 동시 실행되는 구간과 단순 동시 상주를 구별해 Peak RAM을 측정한다. 최소 한 종류 이상의 중간/낮은 RAM 기기에서 후속 검증하고, 그 전에는 일반 스마트폰 전체에 대한 성능 보장을 하지 않는다.

### 7.4 통계와 채택 규칙

동일 사례별 paired 비교를 사용하고 화자/시나리오 묶음을 고려한 bootstrap 신뢰구간을 제시한다. 희귀한 고영향 오류는 발생 건수와 분모, 신뢰구간을 함께 보고한다. 관측 오류 0건은 실제 오류율 0%의 증명이 아니다. 작은 차이는 표본 부족으로 결론 유보할 수 있다.

개발셋 pilot 후 최종 test를 열기 전에 다음 값을 동결한다: 허용 정확도/F1 감소폭, 고영향 오류 상한, OOD false acceptance 상한, P95 지연, Peak RAM 여유, 반복 부하 기준. 이 초안에서는 근거 없는 고정 목표치를 달성 기준으로 선언하지 않는다.

채택 순서는 (1) 고영향·OOD·전체 품질 기준 충족, (2) 목표 기기군의 실행 안정성·자원 예산 충족, (3) 충족 후보 사이에서 지연·RAM·토큰의 Pareto 비교다. LLM 호출률이나 모델 파일 크기 하나만으로 최종 모델을 고르지 않는다.

## 실행 순서와 최종 산출물

1. V1 artifact와 보고값 보존, 정확한 모델 ID 및 측정 조건 복원.
2. 의도/상태 주석 가이드와 V2 데이터 분할 확정.
3. 최신 후보의 Android 오프라인 실행성 및 template/parser 검증.
4. 모델 비교와 R0~R4 라우팅 비교. 고영향 Rule 예외의 허용 여부 결정.
5. 동일 원본 PTQ 비교와 오류 원인 분리. 손실·호환성이 확인될 때만 QAT.
6. T0~T6 토큰 실험 및 최종 조합의 상호작용 확인.
7. 독립 test, 음성 종단, 반복 부하, 다른 기기 검증 후 설계 v1.0 결정.

필수 산출물은 V1 재현 기록, Intent Priority Table, Router 허용 패턴/반례 목록, 상태 전이표, 데이터 카드, 모델·런타임 manifest, 사례별 예측 로그, 정밀도·토큰별 결과표, 기기 측정표다. 원발화·음성 로그는 로컬에서 접근과 보관을 제한하고, 공유 보고서에는 비식별 예시와 집계치를 사용한다.

**현재 결론은 설계 가설이다.** R4가 R0보다 우수한지, 최신 후보가 기존 Gemma보다 나은지, QAT가 손실을 회복하는지, 토큰 축소가 지연을 줄이는지는 이 문서의 실험으로 확인할 사항이다. 구현 코드는 작성하지 않았고 신규 성능 측정도 수행하지 않았다.

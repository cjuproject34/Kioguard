# KioGuard 평가 데이터·FP16 모델 비교 계획 v1.0

상태: **평가 데이터 초안·자동 검증 준비 완료 / 사람 검수·모델 7종 정식 실행 전**

## 1. 이번 결정

Qwen3.5-2B와 Gemma 4 E2B만 비교하지 않는다. 기존 Gemma 2 2B와 과거 Colab에서 실행한 Qwen2 1.5B, Phi-3-mini 3.8B, TinyLlama 1.1B, 최근 smoke를 실행한 Qwen3.5-0.8B까지 같은 새 평가 계약으로 다시 비교한다.

과거 8개 라벨 점수와 새 14개 의도 점수는 직접 합치지 않는다. 과거 결과는 실험 이력과 하한·기준 정보로 보존한다. 새 후보 선정에는 새 데이터의 재실행 결과만 사용한다.

## 2. 평가 데이터

| 구분 | 건수 | 역할 | 독립 test 여부 |
|---|---:|---|---|
| 핵심 의도 dev | 84 | 14개 의도별 6건, 음식점·관공서·공통 문맥 | 아니요 |
| 안전 challenge dev | 34 | 재질문 8, 부정·경계 8, 복합·조건 10, 문맥 대조 8 | 아니요 |
| 기존 48 회귀 | 48 | 과거 발화의 경계 변화와 사용자 지정 해석 확인 | 아니요 |

핵심 dev와 challenge 118건이 모델 선별의 주 데이터다. 기존 48은 회귀로 별도 보고한다. 새 데이터는 모델 선택과 프롬프트 조정에 쓰이므로 최종 성능을 주장하는 자료가 아니다.

## 3. 출력 계약 v3

이전 smoke의 v2.1 계약은 `needs_clarification`과 `clarification_type`의 조합이 불일치하는 문제가 있었다. v3은 최상위를 `requests`와 `fallback` 두 개로 줄인다.

- 각 요청은 ID, 의도, 대상, 슬롯, 조건, 선행 요청을 가진다.
- 조건은 앱 상태 key·연산자·값으로 기록한다.
- 재질문·입력 복구·범위 밖·실행하지 않음은 `fallback`으로 표현한다.
- code fence 제거는 별도 transport 정규화 지표로 허용한다.
- 누락된 괄호, 필드, 의도 라벨을 사후 추측해 채우지 않는다.

계약 변경은 과거 smoke 결과를 지우지 않는다. v2.1 smoke와 v3 정식 비교는 서로 다른 run으로 기록한다.

## 5. 동일 조건

- 같은 118건과 같은 순서
- 같은 prompt v3의 의미 내용
- 모델별 native chat template
- user role 하나에 동일 지시·문맥·발화를 넣어 system role 지원 차이를 줄임
- greedy decoding, 동일 최대 출력 토큰
- 모델별 FP16 원본
- raw 생성문, 입력·출력 토큰, 생성 시간, GPU peak, 로드 시간 저장
- strict JSON과 code-fence 정규화 결과를 분리
- 모델·tokenizer resolved revision, Transformers commit, PyTorch/CUDA/GPU를 run manifest에 저장

Gemma 4와 Qwen3.5에서 reference PyTorch fallback 커널을 사용한 기존 smoke 시간은 정식 Android 지연이 아니다. 이번 FP16 Colab 시간도 후보 선별용 개발 환경 참고값으로만 쓴다.

## 6. 판정 순서

### 6.1 안전 gate

요청하지 않은 `CANCEL`, `COMMIT_REQUEST`, `RESET`은 위험한 추가 행동으로 센다. 한 건이라도 발생하면 모델 출력을 그대로 앱 동작에 연결하는 후보에서 제외한다. 모델 자체를 폐기한다는 뜻은 아니며, 문법 제약·미세조정·공통 상태 검증을 적용한 뒤 다시 평가할 수 있다.

`must_not_intents`는 사례별 금지 동작을 추가로 검사한다. 예를 들어 ‘처음으로 돌아가 주세요’에서 `CANCEL`·`RESET`, ‘카드로 결제할게요’의 수단 선택 문맥에서 `COMMIT_REQUEST`를 금지한다.

### 6.2 계약과 의미

1. strict JSON 성공률
2. code fence만 제거한 JSON 성공률
3. v3 계약 유효율
4. 전체 의미 exact match
5. 14개 의도 macro-F1와 의도별 recall
6. fallback exact
7. 고영향 사례 exact
8. 위험한 추가 행동·사례별 금지 의도 건수

정답 의도만 맞고 대상·수량·부정·조건·순서를 틀리면 전체 의미는 실패다. 형식 실패를 평가 분모에서 제외하지 않는다.

### 6.3 자원

Colab에서 로드 시간, 생성 시간, token 수, process RSS, GPU allocated/reserved/peak를 기록한다. 후보 1~2개를 고른 뒤 GGUF 변환·PTQ와 S24 Ultra 실측을 진행한다. Colab FP16 시간을 모바일 허용 지연시간으로 사용하지 않는다.

## 7. 후보 결정

주 후보는 안전 gate를 통과한 모델 중 의미 품질이 가장 높은 모델이다. 경량 후보는 안전 gate를 통과하고 주 후보와 품질 차이가 작은 모델 중 메모리·파일·단말 지연이 작은 모델로 정한다. 현재는 결과가 없어 모델명을 확정하지 않는다.

모든 모델이 안전 gate를 실패하면 ‘선정 실패’가 올바른 결론이다. 그 경우 상위 모델 1~2개에 JSON grammar 또는 constrained decoding과 소규모 지도 미세조정을 적용하고 다시 비교한다. 이 재평가에서 사용한 118건은 계속 dev이며 새 독립 test가 필요하다.

## 8. PTQ·QAT 연결

118건 FP16 비교와 초기 Android 로딩 확인 후 후보를 1~2개로 줄인다. 그 다음 동일한 원본 revision에서 FP16 GGUF, Q8_0, Q4_K_M을 각각 만들고 Gemma 4에는 공식 QAT와 맞춘 Q4_0 비교를 추가한다.

직접 QAT는 모델 후보와 목표 배포 양자화 규격을 정한 뒤 수행한다. 7개 모델 모두를 PTQ·QAT하지 않는다. 먼저 공정한 FP16 비교로 후보를 줄여 무료 Colab 자원을 보호한다.

## 9. 완료 조건

- 166행 사람 검수와 수정 이력 기록
- 7개 모델의 gate 결과
- 기술 실패가 없는 후보의 118건 결과와 raw 출력
- 모델별 안전·계약·의미·자원 비교표
- 주 후보 1개와 경량/대안 후보 1개, 또는 선정 실패 판정
- 기존 48회귀의 별도 결과
- 다음 PTQ 대상과 양자화 형식 결정

현재 완료된 것은 데이터·계약·모델 행렬·검증기·채점기 초안이다. 7개 모델의 새 비교 결과와 최종 후보는 아직 없다.

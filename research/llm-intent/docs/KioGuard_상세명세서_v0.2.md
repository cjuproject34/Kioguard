# KioGuard 온디바이스 앱 상세 명세서

버전: v0.2 검토안

이 문서는 구현 전에 검토할 기능·데이터·실험 명세다. 앱 구현, 모델 다운로드, 신규 추론, 양자화, 학습, 실기기 시험은 이번 작성 작업에서 수행하지 않았다. 원본 자료와 이전 결과는 보존했다.

문서 상태 표기:

- **설계 결정:** 이번 명세에서 사용할 구체적인 설계안. 구현 착수 전에 사용자가 검토한다.
- **검증 목표:** 팀의 초기 수용 기준으로 제안하는 값. 측정값이나 외부 표준의 의무값이 아니다.
- **공식 확인:** 공급자의 문서에서 확인한 사실. KioGuard의 성능을 보증하지 않는다.
- **실측 후 확정:** 모델 승자, 최종 양자화, 최종 실행 backend 등 비교 시험이 필요한 항목.

관련 문서: [작성 근거와 결정 기준](KioGuard_작성근거와_결정기준_v0.2.md), [기존 48발화 검토표](KioGuard_기존48발화_의도검토_v0.2.md), [기존 Colab 실험 검토보고서](KioGuard_기존_Colab_실험_검토보고서.md).

## 1. 목표와 적용 범위

### 1.1 제품 목표

사용자가 자신의 스마트폰으로 카페·관공서 키오스크 화면을 비추고 원하는 일을 말하면, 앱이 발화와 화면을 해석해 다음에 살펴보거나 눌러야 할 항목을 화면과 음성으로 안내한다. STT·OCR·LLM·TTS의 서비스 중 추론은 전부 단말 안에서 수행한다. 설치 시 모델을 내려받는 과정은 사용 중 추론과 구분한다.

의미 해석이 어렵거나 오분류 영향이 큰 발화는 온디바이스 LLM을 사용한다. 영향이 낮고 검증된 고정 표현은 Rule로 처리한다. 입력이나 화면 정보가 부족하면 필요한 정보를 다시 묻는다. 모델이 답을 냈다는 이유만으로 안내를 승인하지 않는다.

### 1.2 첫 검증 범위

| 항목 | 설계 결정 | 근거·한계 |
|---|---|---|
| 실증 도메인 | 카페 주문·관공서 서류 발급 안내 | 개발보고서 2~3쪽의 범위. 실제 화면·과업을 등록한 시나리오부터 검증 |
| 단말 | 보유 Galaxy S24 Ultra 1대에서 첫 검증 | 보유 시험 기기이며 최소 지원 사양이나 전체 Android 대표 기기가 아님 |
| 앱 | Android, Kotlin UI와 로컬 추론 모듈 연결 | iOS 성능은 이번 결과로 주장하지 않음 |
| 조작 범위 | 사용자가 직접 키오스크를 조작하도록 안내. 앱 자체 확대·재생·중지는 앱에서 실행 | 외부 키오스크 자동 클릭, 결제, 신청 제출 API 연동은 포함하지 않음 |
| 화면 안내 | 확인된 글자 영역을 강조하고 위치를 설명 | OCR 글자 박스를 실제 버튼 테두리라고 부르지 않음. 버튼 영역 검출은 별도 검증 항목 |
| 답변 | 검증된 안내 템플릿 + 현재 화면의 확인된 항목 | 모델 지식으로 가격·할인·발급 가능 여부를 추측하지 않음 |
| 실행 조건 | 필수 자원 설치 후 네트워크 차단 상태에서 핵심 기능 실행 | 자원 미설치 상태와 설치 완료 후 오프라인 상태를 구분 |
| 개발 환경 | Colab에서 데이터·모델 실험, Android에서 배포 성능 시험 | 개발용 학습·변환까지 휴대폰에서 수행할 필요는 없음 |

등록하지 않은 키오스크에서도 모두 동작한다는 보장은 하지 않는다. 화면 정보가 불충분하면 일반 안내 또는 직원에게 도움을 요청하는 방법을 제공한다. 고령 사용자 대상 사용성 검증은 팀 내부 테스트와 별도로 수행한다.

| 항목 | 현재 확인 상태 | V2 처리 |

이전 v0.1 문서는 감사 전 보고값을 포함한다. 기존 실험에 대한 해석은 감사보고서와 본 표를 우선한다. 회의록의 서버/A2A 제안, QAT 수행 완료 서술, CPU 10코어·가용 RAM 7GB 추정은 현재 합의나 측정 사실로 채택하지 않는다.

## 2. 의도 정의 V2

### 2.1 의도와 주제를 분리한다

V1의 8개 라벨에는 사용자의 요청 종류와 대화 주제가 섞여 있다. V2는 `의도 + 주제 + 대상/값 + 발화의 긍정·부정 + 처리 상태`로 표현한다. 원본 라벨은 유지하고 새 라벨을 별도 열에 기록한다.

| ID | V2 의도 | 포함 기준 | 제외·경계 사례 |
|---|---|---|---|
| I01 | 선택·신청 요청 SELECT | 품목 또는 서류를 새로 선택·요청 | 기존 선택의 수정은 I02. 지원 여부 질문은 I10 |
| I02 | 선택 내용 변경 MODIFY | 현재 선택된 대상의 종류·수량·온도·구성을 수정 | 현재 대상이 없으면 I01 후보 또는 재질문. 서류 종류 교체는 subtype=대상변경 |
| I03 | 이용 방식 선택 FULFILLMENT | 매장 이용·포장·수령 방식 선택 | “포장 되나요?”는 I10, topic=이용방식 |
| I04 | 결제수단 선택 PAYMENT_METHOD | 카드·현금 등 사용할 결제수단 표현 | “삼성페이 돼요?”는 I10. 결제 완료를 뜻하지 않음 |
| I05 | 영수증 요청 RECEIPT | 영수증 발급·출력 요청 | 실제 결제 완료 상태 확인. 현금영수증 개인정보 입력 안내는 I09와 구분 |
| I06 | 혜택 적용 BENEFIT_APPLY | 쿠폰·할인·적립의 적용 의사 | 적용 가능 여부는 I10, 사용 위치·방법은 I09 |
| I07 | 이전 단계 이동 BACK | 현재 단계에서 직전 화면으로 이동하려는 의사 | 항목 취소 I08, 전체 초기화 I14와 구분 |
| I08 | 특정 대상 취소 CANCEL | 선택·주문·신청 등 특정 대상을 취소하려는 의사 | 대상 없는 “취소”는 확인. “취소하지 마”는 취소 승인 금지 |
| I09 | 과업 안내 GUIDE | 현재 과업의 버튼 위치·사용 방법·다음 단계 문의 | 서비스 가능 여부·수수료 등 사실 질문은 I10 |
| I10 | 정보 조회 INFO | 가능 여부·조건·가격·절차·운영 정보 질문 | 사실은 화면 또는 등록된 로컬 안내 자료에서 확인해야 함 |
| I11 | 앱 접근성·재생 제어 APP_CONTROL | KioGuard의 글씨·속도·음량·다시 듣기·재생 중지 | 외부 키오스크의 설정을 바꿀 수 있다고 안내하지 않음 |
| I12 | 일반 도움·직원 도움 HELP | 구체적 과업 없이 도움 요청, 반복 실패 후 도움 요청 | 직원 호출 시스템을 실제로 실행했다고 표현하지 않음 |
| I13 | 확정·진행 요청 PROCEED | 선택·결제·신청의 확정 단계로 진행하려는 의사 | “네”는 대기 중인 확인 질문과 연결될 때만 확인 응답으로 처리 |
| I14 | 전체 초기화 RESET | 과업 전체를 처음부터 다시 시작하려는 의사 | BACK과 구분. 앱 세션 초기화와 키오스크 초기화도 구분 |

주제 값: 상품, 서류, 옵션, 이용방식, 결제, 영수증, 혜택, 화면조작, 접근성, 기관정보 등. 의도가 INFO여도 topic=결제이면 결제 관련 상황 검증을 적용한다. 14개 라벨은 기존 경계를 분리하기 위한 설계안이며, G0 라벨링 검토에서 병합·수정할 수 있다. 기존 48개에는 I13 등 일부 신규 의도의 충분한 사례가 없으므로 새 데이터를 수집한다.

### 2.2 경계 판정 규칙

1. 질문과 실행 의사를 구분한다. “삼성페이 돼요?”는 INFO, “삼성페이로 할게요”는 PAYMENT_METHOD다.
2. 새 요청과 변경은 현재 선택 상태를 근거로 구분한다. “따뜻한 걸로 두 잔이요”만으로 변경이라고 확정하지 않는다.
3. 방법·위치 질문은 GUIDE로 분류하고 결제·쿠폰 같은 주제를 함께 기록한다.
4. BACK, CANCEL, RESET을 구분한다. 상태 손실이 있는지 확인한다.
5. 부정된 의도를 실행 대상으로 만들지 않는다. “결제하지 말고 처음으로”는 RESET 요청과 결제 부정 정보를 보존한다.
6. 여러 요청이 있으면 `intents[]`에 보존하고 수행 순서를 검증한다. 같은 의미의 “취소하고 처음부터”가 RESET 하나인지, 결제 취소 후 재시작인지 상황을 확인한다.
7. 서술과 질문이 구분되지 않으면 강제 라벨을 붙이지 않는다. GV-09 “번호표 뽑는 거 알아요”는 억양·문맥 없이는 서술일 수 있다.
8. 개인정보 실제 값은 intent/slot으로 저장하지 않는다. PIN 입력 위치를 안내할 수 있어도 PIN을 말해 달라고 요청하지 않는다.

### 2.3 처리 상태

`OK`, `NEED_CLARIFICATION`, `OUT_OF_SCOPE`는 의미 판단 결과다. `INPUT_ERROR`, `ENGINE_ERROR`, `TIMEOUT`, `CANCELLED`는 앱 실행 결과다. 미분류, 출력 파싱 실패, 엔진 실패를 한 라벨로 합치지 않는다. 확인 응답 YES/NO는 유효한 대기 질문 ID에 결합하며 일반 요청을 덮어쓰지 않는다.

## 3. 영향도·복잡도·우선순위

### 3.1 영향도

| 등급 | 조건 | 처리 원칙 |
|---|---|---|
| H 높음 | 금전 확정, 개인정보 입력·노출, 중요한 신청 결과, 복구 어려운 초기화·취소로 잘못 안내할 가능성 | 의미 해석 + 상태·근거 검증. 결정적인 다음 단계 안내 전 필요한 확인 |
| M 중간 | 수정 가능한 주문·서류·옵션·단계 변경, 잘못 안내하면 재작업 발생 | 상황과 대상 확인. 초기 Rule 직접 처리 대상에 포함하지 않음 |
| L 낮음 | KioGuard 내부의 되돌릴 수 있는 재생·표시 조절, 영향이 제한된 일반 도움 | 엄격한 고정 패턴과 상태 조건을 충족할 때 Rule 허용 |
| U 미확정 | 영향 판단에 필요한 단계·대상·기존 선택 상태가 없음 | L로 간주하지 않음. 상황 수집 또는 재질문 |

높음 우선 적용: 어느 한 조건이 H이면 낮은 복잡도로 상쇄하지 않는다. 입력에 민감정보가 있다는 사실과 안내 결과의 영향은 별도로 기록한다. 같은 문장도 결제 전후·수정 가능 여부에 따라 등급이 달라질 수 있다.

### 3.2 해석 복잡도

| 등급 | 조건 | 예시 |
|---|---|---|
| C1 낮음 | 검증된 단일 전체 패턴, 대상·값 명확, 필요한 상태가 존재 | 앱 안내 재생 중 “다시 읽어줘” |
| C2 중간 | 단일 요구이지만 수량·속성·표현 변형을 해석해야 함 | “카페라떼 뜨겁게 한 잔” |
| C3 높음 | 부정·정정·복합 요청·간접 표현·지시어·이전 문맥 의존 | “아까 것 말고 덜 단 걸로” |
| CU 판단 불가 | 입력 훼손 또는 필수 문맥 누락으로 의미 판정 불가능 | 대상 없이 “이걸로” |

C3이면서 대상 부족이면 `C3 + missing_context`로 기록할 수 있다. 복잡도는 의미 특성이고 처리 상태는 현재 해결 가능 여부다. 짧은 문장, 한 개 키워드 일치, 모델의 자기 확신도를 C1의 근거로 사용하지 않는다.

### 3.3 경로 정책

| 정책 ID | 조건 | 경로·후속 동작 |
|---|---|---|
| R00 | 사용자의 명시적인 앱 중지 버튼, 유효한 취소 이벤트 | 즉시 로컬 제어. 오래 걸리는 의미분석 대기열을 거치지 않음 |
| R01 | 무음·빈 텍스트·지원하지 않는 입력 | INPUT_ERROR 안내. LLM 호출 없음 |
| R02 | 필수 대상·화면이 명백히 없음 | CLARIFY 또는 화면 재촬영. 단순히 문장이 낯설다는 이유로 적용하지 않음 |
| R03 | L이고 C1이며, 전체 허용 패턴 1개·현재 앱 상태·필수 슬롯·부정 부재가 모두 충족 | RULE. 공통 Validator 적용 |
| R04 | R03에 해당하지 않고 해석 가능한 입력 | LLM. H/M/C2/C3/U를 포함하되 필요한 문맥이 부족하면 결과를 재질문으로 전환 |
| R05 | LLM/Rule 결과가 형식·상태·화면 근거 검증에 실패 | 안내 보류. 재질문·재촬영·복구 경로 |

우선순위 표시는 `LOW_DIRECT`(R03), `HIGH_REVIEW`(영향 H 또는 C3), `REVIEW`(그 밖의 해석 대상), `UNDETERMINED`(미확정)로 둔다. 이는 처리 순서를 정하는 CPU 스케줄 우선순위가 아니다. 사용자에게는 내부 코드 대신 “확인 중”, “다시 말씀해 주세요” 등 필요한 상태만 표시한다.

Router는 완전한 의도분류기가 아니라 Rule 직접 처리 자격을 확인하는 좁은 모듈로 시작한다. 오프라인 라벨링에서 영향도·복잡도를 상세 기록하되, 실행 중에도 모든 등급을 먼저 완벽히 예측해야 한다는 전제를 두지 않는다. 단어 기반 위험 신호는 보수적으로 경로를 올리는 데만 사용하고 위험이 없다는 증거로 쓰지 않는다.

장점은 중요한 오류의 구분과 호출 비용의 분석이 가능하다는 것이다. 비용은 문맥 관리·라벨링 작업과 초기 높은 호출률이다. 낮은 호출률을 강제하지 않고 잘못된 Rule 통과를 먼저 줄인다.

## 4. 공통 입출력 계약

구현 언어와 무관한 논리 명세이며 실제 클래스나 API 코드는 아니다.

| 객체 | 필수 정보 | 제약 |
|---|---|---|
| Request | session_id, request_id, 입력 종류, text 또는 audio_ref, 시작 시각, domain | 한 세션에서 의미분석 요청은 한 번에 1개. 새 요청 시 이전 결과 식별·폐기 |
| ScreenContext | frame_id, capture_time, orientation, view_transform, blocks[{id,text,box}], 상태 출처, 상태 확실성 | OCR 추정은 확정된 키오스크 내부 상태와 구분. 민감값 제거 |
| SessionState | stage, selected_item, pending_question_id, last_guidance_id, context_version | 모르는 값은 UNKNOWN. LLM 추정을 확정 상태로 자동 저장하지 않음 |
| RouteDecision | route, matched_rule_id, reason_codes, context_version | 경로 선택 이유 기록. 모델 자기 확신도에 의존하지 않음 |
| NLUResult | status, intents[{type,topic,slots,polarity}], missing_fields, evidence_block_ids | 허용 enum·키·길이만 승인. 복합 요청 최대 2개로 시작하며 초과는 나누어 질문 |
| GuidancePlan | template_id, 확인된 대상 ID, frame_id, 강조 영역, requires_confirmation, question_id | 좌표는 OCR/추적 결과에서 계산. LLM이 생성한 좌표·가격·개인정보 값 사용 금지 |
| ErrorResult | error_code, failed_stage, retryable, request_id, 사용자 안내 ID | 시간 초과·추론 실패·파싱 실패를 구분 |
| RunRecord | 버전·장치·경로·시간·토큰·오류·검증 결과 | 운영 기본 기록에는 원음·원본 프레임·전체 발화를 저장하지 않음 |

NLU 출력은 짧은 구조화 결과를 기본으로 한다. 허용되지 않은 라벨, 여러 라벨을 설명문에서 부분 문자열로 찾는 방식, prompt echo를 정답으로 승인하는 방식은 사용하지 않는다. 제약 생성은 형식을 돕는 수단이며 의미 정확성을 증명하지 않는다. OUT_OF_SCOPE와 NEED_CLARIFICATION도 출력 형식에서 허용한다.

### 5.1 모델 생명주기

F01에서 미리 로딩하고 준비 상태를 표시한다. 메모리 예산을 충족하는 경우 활성 세션 동안 LLM을 유지한다. 세션 종료·메모리 압박·백그라운드 전환 때 취소 후 해제한다. 전경 복귀 시 모델 상태와 화면 문맥을 다시 확인한다. 음성 입력마다 CLI 프로세스로 모델을 새로 로딩하는 구조를 최종 앱 기준으로 사용하지 않는다.

whisper.cpp와 llama.cpp는 각각의 버전·native library 충돌을 검증한다. 개발보고서의 공유 ggml 구성을 필수 조건으로 삼지 않는다. 호환 확인 없이 서로 다른 버전의 ggml을 억지로 합치지 않는다.

### 5.2 화면 근거의 유효성

강조 대상은 최신 안정 프레임에서 재확인한다. 초기 신선도 기준은 안내 승인 시점 기준 1초 이내이며 **검증 목표**다. 긴 추론 뒤에는 최신 OCR과 대상이 같은지 다시 확인한다. 카메라 이동·회전·화면 전환 시 기존 강조를 즉시 제거하고 새 좌표계를 적용한다. 시간 기준만 충족했다고 같은 화면이라고 가정하지 않는다.

앱 중지·음성 재생 중지는 항상 접근 가능하게 둔다. 최소 터치 영역 48dp는 Android 공식 접근성 권고를 따른다. 본문 20sp, 주요 조작 56dp를 초기 UI 값으로 제안하고 큰 시스템 글꼴·TalkBack·확대 상태에서 잘림과 순서를 검증한다. [Android 접근성 안내](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views)

| INVALID_OUTPUT | enum·JSON·길이·복수 출력 계약 위반 | 같은 잔여 시간 안에서 형식 재시도 최대 1회, 이후 복구 | 설명문 부분 문자열로 라벨 추출 금지 |
| CONTRADICTION | 부정·현재 상태·근거와 결과 충돌 | 확인 또는 안내 중지 | “LLM이므로 맞다”는 승인 근거 금지 |
| TIMEOUT | 단계 또는 전체 deadline 초과 | “시간이 오래 걸려요”, 재입력·도움 선택지 | 늦게 도착한 결과 폐기. 재시도로 deadline 초기화 금지 |
| OOM/THERMAL | 할당 실패·OS 열 상태 악화 | 작업 중지·빈도 축소·가능 기능 안내 | 고영향 발화를 임의 Rule로 내려서 계속 처리 금지 |
| TTS_FAILED | 합성·재생 실패 | 동일 안내의 텍스트 표시 | 클라우드 TTS 자동 전환 금지 |
| USER_CANCELLED | 중지·새 요청·세션 종료 | 즉시 UI 반응, 작업 취소·임시 자료 정리 | 취소된 안내를 뒤늦게 재생 금지 |

고정 문구로 안전하게 제공할 수 있는 일반 도움과, 구체적인 다음 버튼을 안내하는 행위를 구분한다. 엔진 장애 시 일반 도움을 제공할 수 있지만 의미가 불확실한 거래·신청 안내를 확정하지 않는다.

## 8. 모델·엔진·양자화 선정

### 8.1 비교 후보를 구체적으로 지정한다

기존 Gemma 2는 baseline이며 신규 앱의 최종 모델로 고정하지 않는다. 최신 공급자 문서를 확인한 소형 후보를 포함한다. 후보 공개 사실과 한국어 KioGuard 성능은 별개다.

| 실험 ID | 모델 ID | 역할·선정 근거 | 주의점·첫 확인 |
|---|---|---|---|
| M0 | `google/gemma-2-2b-it` | 과거 실험과 연결되는 재구성 기준 | 과거 revision 미확인. 새 다운로드 revision으로 재구성하면 V1 원실험과 구분 |
| M1 | `google/gemma-4-E2B-it` | **신규 주 비교 후보**. 공식 모바일 대상이며 최신 Gemma 소형 계열 검토를 충족 | E2B는 단순 총 2B가 아님. 모델 카드의 embedding 포함 5.1B 표기를 반영해 실제 파일·RAM 측정 |
| M2 | `Qwen/Qwen3.5-2B` | 다른 계열의 소형 instruction 모델 비교 | text-only·non-thinking 경로와 변환 지원 확인 |
| M3 | `Qwen/Qwen3.5-0.8B` | 작은 모델로 자원 절감 가능성 검증 | 중요 의도 품질·출력 반복 검증. 작다는 이유로 채택하지 않음 |
| M4 | `kakaocorp/kanana-2-1.3b-instruct` | 한국어 및 온디바이스 목적의 추가 후보 | custom hybrid attention. Colab 지원을 Android GGUF 지원으로 간주하지 않음. 변환·커널 미지원이면 조사 결과로 기록하고 주 실험에서 제외 |

공식 근거: [Gemma 4 모델 카드](https://huggingface.co/google/gemma-4-E2B-it), [Qwen 2B](https://huggingface.co/Qwen/Qwen3.5-2B), [Qwen 0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B), [Kanana 1.3B](https://huggingface.co/kakaocorp/kanana-2-1.3b-instruct). 이번 문서의 신규 주 후보 지정은 비교 순서 결정이며 최종 성능 순위가 아니다.

### 8.2 단계별 기준 조합

| 단계 | 모델·엔진·정밀도 기준 | 확정 의미 |
|---|---|---|
| G0 방법 검증 | M0 + llama.cpp + 고정밀 GGUF/Q8_0/Q4_K_M | 기존 측정 오류를 분리하기 위한 기준 조합 |
| G1 최신 후보 시험 | **M1 + llama.cpp + text-only 고정밀/Q8_0/Q4_K_M**부터 호환성 검사. M2·M3도 같은 순서 | 초기 비교 계획으로 지정. M1 실행 성공·속도 미확인 |
| G2 앱 통합 기준 | G1 통과 후보 중 중요 오류·정확도 기준 충족 모델을 고르고 RAM·P95로 선별 | 통합 시작 전 실측으로 한 모델·한 정밀도 선택 |
| G3 대안 엔진 | 최상위 후보의 LiteRT-LM 지원 artifact·backend 확인 후 동일 단말 비교 | llama.cpp로 목표 미달이거나 이득 검증 필요 시 진행. 서로 다른 포맷의 양자화 차이도 기록 |
| G4 최종 채택 | 독립 평가·통합 장시간 시험을 모두 통과한 단일 조합 | model revision, artifact hash, runtime commit, backend·threads까지 고정 |

llama.cpp는 기존 경험과 Android 실행 경로를 활용하는 기준 엔진이다. LiteRT-LM은 Android용 대안 후보다. NPU·GPU는 해당 모델·연산자·단말 드라이버의 지원과 실제 실행 backend를 확인해야 하며, 기기에 가속기가 있다는 이유로 사용됐다고 기록하지 않는다. [llama.cpp Android](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md), [LiteRT-LM](https://developers.google.com/edge/litert-lm)

G1에서 모델 구조·변환이 지원되지 않으면 임의로 비슷한 architecture 이름을 지정하지 않는다. G2에서 아무 후보도 기준을 통과하지 못하면 “최종 모델 미선정”으로 기록하고 데이터·분류·자원 병목을 개선한다. 기준을 결과에 맞춰 조용히 낮추지 않는다.

### 8.3 다른 AI 축의 초기 선택

| 축 | 초기 구성·후보 | 근거와 확정 조건 |
|---|---|---|
| STT | 기존 `ggml-small-ko-q5_0.bin`은 출처 확인 대상으로 보존. 재현 가능한 비교 후보는 `openai/whisper-small` + whisper.cpp | 통합 노트북 셀 14~16에서 기존 파일명 확인. 파일명만으로 한국어 미세조정 출처를 단정하지 않음. checkpoint/hash·정규화·변환 이력 확보 후 기존 모델 재사용 여부 결정 |
| OCR | ML Kit Text Recognition v2 한국어 **bundled** 방식 | 초기 자원 미다운로드 실패를 줄이는 설계. `com.google.mlkit:text-recognition-korean:16.0.1`은 확인 시점 공식 예시 버전이며 착수 시 의존성 고정·호환 검증 |
| TTS | G1 최소 앱은 설치된 Android 한국어 offline Voice를 조건부 사용. G2는 기존 sherpa-onnx 자산과 비교 | offline Voice 이름·엔진 버전·설치 여부를 장치 manifest에 기록. 네트워크 필요 Voice는 제외. 사용 가능 Voice가 없으면 자원 준비 또는 텍스트 대체 |
| TTS 기존 기록 | 통합 Colab 셀 18은 `facebook/mms-tts-kor` + Transformers/uroman | 보고서의 sherpa-onnx 설명과 구분. 실제 Android TTS checkpoint는 이번 자료만으로 미확정. MMS 라이선스 표기와 배포 조건을 출시 전에 검토 |

관련 공식 문서: [whisper.cpp](https://github.com/ggml-org/whisper.cpp), [ML Kit 한국어 OCR](https://developers.google.com/ml-kit/vision/text-recognition/v2/android), [Android Voice의 네트워크 요구 여부](https://developer.android.com/reference/android/speech/tts/Voice#isNetworkConnectionRequired()), [MMS Korean 모델 카드](https://huggingface.co/facebook/mms-tts-kor). TTS의 명칭·버전이 확인되지 않은 상태에서 “sherpa 한국어 모델 확정”이라고 기재하지 않는다.

### 8.4 PTQ 실험

1. 고정된 원본 checkpoint와 tokenizer로 고정밀 출력을 먼저 검증한다.
2. 고정밀 GGUF로 변환하고 원본 실행과 템플릿·특수 토큰·출력 영역을 대조한다. 이 차이는 양자화 손실과 별도 기록한다.
3. 동일 고정밀 GGUF에서 Q8_0과 Q4_K_M을 각각 생성한다. Q8에서 Q4로 재양자화하지 않는다.
4. 공통 프롬프트·파서·데이터·실행 backend·문맥·생성 설정에서 고정밀/Q8/Q4를 비교한다. 모델별 native template는 사용하되 의미 지시는 동일하게 둔다.
5. 기본 비교가 끝난 후 Q5_K_M 또는 중요도 행렬 보정을 조건부 실험한다. 보정 자료는 train/calibration에서만 사용한다.
6. 최종 배포 파일의 tensor type 분포·실제 크기·hash를 저장한다. Q4_K_M을 모든 가중치가 정확히 4비트인 모델로 표현하지 않는다.

GGUF 변환과 양자화는 별도 단계이며, 공식 quantize 도구는 고정밀 원본에서의 변환과 재양자화 주의사항을 안내한다. [llama.cpp quantize 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md)

우선은 LLM 가중치 양자화만 바꾼다. KV 캐시·활성값·STT 양자화까지 동시에 바꾸지 않는다. 모바일에서 고정밀 실행이 불가능하면 N/A로 기록하고 같은 모바일 엔진에서 실행 가능한 후보끼리 자원을 비교한다.

### 8.5 QAT 실험 진입·종료 조건

진입 조건은 (a) 입력·파서·변환 오류를 분리했고, (b) 필요한 저정밀 모델에서 개발셋 품질 손실이 반복 확인되며, (c) 해당 저정밀의 자원 이득이 필요하고, (d) 학습·변환·배포 양자화 형식이 호환되는 것이다. 평균 정확도 손실 1%p 초과 또는 새 고영향 오류는 분석 시작 조건으로 제안하며, 48건에서 한두 건 차이만으로 QAT 필요를 확정하지 않는다.

QAT는 일반 INT4라는 이름만 맞추지 않고 group/block 크기, scale, 대상 layer, 예외 tensor, 활성값 설정까지 배포 방식과 맞춘다. 일반 TorchAO INT4 QAT를 Q4_K_M과 동일하다고 가정하지 않는다. 지원 조합이 없으면 해당 QAT 실험은 보류하고 지원 엔진의 별도 연구 트랙으로 남긴다. [PyTorch QAT 문서](https://pytorch.org/blog/quantization-aware-training-in-torchao-ii/)

비교군은 원본→PTQ, 동일 데이터의 일반 미세조정→PTQ, 동일 예산의 QAT→배포 양자화다. 추가 학습 효과와 QAT 효과를 분리한다. 학습에는 train만 사용하고 dev에서 epoch·설정을 선택한 뒤 동결한다. 공개 QAT 모델을 사용했다면 “공개 QAT artifact 평가”로 기록하고 팀이 QAT를 수행했다고 쓰지 않는다. 원 성능 회복·모바일 목표 충족 여부로 종료하며 개선이 없으면 그 결과도 보존한다.

## 9. 프롬프트·문맥·토큰 계획

| 항목 | 초기 검증 설정 | 비교 계획·제약 |
|---|---|---|
| 입력 문맥 | 초기 input budget 768 tokens, runtime context 2048 tokens | 모델별 실제 토큰 수 기록. 512/768/1024 입력 예산을 dev에서 비교 |
| 출력 | 구조화 결과 최대 96 tokens | 64/96/128 비교. 복합 결과가 잘리면 오류로 집계. 8 tokens를 모든 모델에 강제하지 않음 |
| 예시 | 0-shot 기준, 필요 시 train에서 고른 4-shot | 기존 test 문장·정답을 예시에 넣지 않음 |
| 화면 정보 | 현재 과업의 후보 글자 영역 최대 8개, 이전 확인된 상태·질문만 포함 | 너무 많으면 사용자에게 화면을 좁혀 달라고 요청. 정답 후보가 사라지는 절단 평가 |
| 대화 | 최근 필요한 요청·재질문 응답과 확인된 상태 | 전체 대화 무제한 첨부 금지. 모델 생성 추론 과정은 저장·재전달하지 않음 |
| 생성 설정 | non-thinking 및 greedy를 첫 재현 기준으로 사용 | 모델별 권장 sampling과 다를 수 있어 dev에서 별도 비교 후 고정. Qwen의 /nothink 문자열을 공식 hard switch 대신 사용하지 않음 |
| 로딩·캐시 | 세션 중 상주 우선, prefix cache는 지원·정확성 확인 후 추가 | 템플릿 변경·모델 변경·세션 종료 시 캐시 무효화 |

예산 초과 시 과거 대화·비관련 OCR부터 제거한다. 현재 발화의 부정·대상·수량과 필수 화면 근거는 보존한다. 그래도 초과하면 임의 절단 대신 재질문한다. 처음 입력부터 안내 완료까지의 모든 LLM 호출·재시도 토큰을 합산한다. KV 캐시도 prompt 압축과 별개의 자원 항목으로 기록한다.

Qwen 3.5 공식 카드에는 non-thinking 지원과 thinking 반복 가능성이 안내돼 있다. 이 기능을 사용하더라도 KioGuard에서는 실제 생성 로그로 모드가 적용됐는지 확인한다. [Qwen 3.5 2B](https://huggingface.co/Qwen/Qwen3.5-2B)

## 10. 데이터·평가 설계

### 10.1 데이터 구성과 검수

다음 수량은 준비할 **초기 계획량**이며 이미 존재하는 데이터가 아니다.

| 세트 | 초기 계획 | 용도 |
|---|---:|---|
| V1 회귀 | 기존 48행 + 원래 라벨 | 과거 동작·오류 추적. 새 정확도 주장에 미포함 |
| V2 개발 | 새 사례 400건 | 의도 경계, Rule, prompt, threshold 조정 |
| V2 최종 평가 | 720건 | 단일 해결 가능 420건(14의도×30), 복합 60, 필수 문맥 부족 60, OOD 120, 입력 훼손·무음 등 60 |
| Rule 자격 시험 | 별도 200건 | 허용 표현·반례·부정·상태 변경. 정상 100/반례 100을 초기 구성으로 제안 |
| 실제 음성 평가 | 최소 20명×12발화=240건 제안 | 화자 분리, 실제 대상 사용자와 주변 소음 포함. 수집·보관 동의 별도 |
| 화면 평가 | 미사용 화면/배치 100장 이상 제안 | 글자 검출과 의미 대상 선택·좌표 변환을 분리 평가 |
| QAT train | 필요 시 별도 수집, 초기 1,200 검수쌍에서 학습 곡선 확인 제안 | 충분성을 보장하는 숫자가 아님. 기존 126행만으로 일반화 주장 금지 |

각 최종 평가 사례는 카페/관공서, 영향도, 복잡도, 화면 상태, 발화 출처, 유사표현 그룹을 가진다. 고영향·중요 오류 시나리오는 720건 중 최소 200건을 확보하도록 층화한다. 그룹 단위로 분리해 같은 원문·패러프레이즈·화자·대화·화면 배치가 train/dev/test로 누출되지 않게 한다. 기존 공개 개발 발화의 단순 변형은 최종 평가에서 제외한다.

단일 의도 420건의 14개 라벨에는 INFO·GUIDE 등 경계 사례를 균형 있게 넣는다. 복합 60건은 별도 집계하며 단일 라벨 Macro F1에 섞지 않는다. 인위적 균형 데이터의 호출률을 실제 사용률로 주장하지 않는다. 별도 사용성 세션에서 현실적 분포를 기록한다.

두 검수자가 의도·영향도·복잡도를 독립 부여한다. 불일치와 판단 근거를 기록하고 R1/R2가 조정한다. 화면이 없어서 정답을 확정할 수 없는 사례는 조건부 라벨로 보존하거나 실제 문맥을 보완하며 추측으로 강제 단일화하지 않는다. 최종 test를 보고 수정한 경우 그 test는 다음 버전부터 회귀셋으로 전환한다.

### 10.2 구조 비교

1. V1 8라벨의 Rule/LLM/Hybrid는 V1 정의로 재검증한다.
2. V2에서는 같은 14라벨 계약의 Rule-only, LLM-only, 기존 방식(no-match 시 LLM), 새 Router를 비교한다. 여기서 기존 방식은 정책 재구성이며 과거 8라벨 코드와 동일한 실험이라고 쓰지 않는다.
3. 같은 모델·prompt·parser·문맥·출력 예산을 사용해 구조 효과를 분리한다. Rule-only가 처리하지 못한 입력도 분모에서 제거하지 않는다.
4. 구조를 고정한 뒤 모델, PTQ, 토큰 설정을 순차 변경한다. 대안 엔진 비교는 엔진·artifact 차이를 포함한 배포 조합 비교로 별도 표기한다.
5. 개발셋에서 후보를 좁힌 후 최종 조합과 사전 등록한 비교 기준만 독립 test에 적용한다. test 결과로 다시 최적화하면 새 test가 필요하다.

### 10.4 지연 목표와 측정 경계

| 구간 | 시작 → 끝 | 초기 목표·상한 |
|---|---|---|
| 사용자 조작 피드백 | 탭 이벤트 → 화면 상태 변경 | P95 ≤100ms |
| 모델 cold load | 로컬 파일 로딩 시작 → 추론 준비 | P95 ≤10초 목표, 20초에서 복구 안내. OS 캐시 상태 별도 기록 |
| Rule 경로 | 최종 텍스트 수신 → 검증된 결과 | P95 ≤50ms |
| STT | 녹음 종료 확정 → 최종 텍스트 | P95 ≤2초, 길이 ≤10초 발화 기준. 10~15초는 별도 층 |
| LLM 의도 경로 | prompt 구성 시작 → 파싱·검증 완료 | P50 ≤1초, P95 ≤2초 목표. 모델 상주, 입력 ≤768·출력 ≤96 tokens 기준 |
| OCR 준비 | 분석 프레임 수신 → 글자 후보·좌표 | P95 ≤500ms 목표, 조명·해상도 고정 |

전체 5초는 STT 약 2초, 의도 처리 약 2초, TTS 시작 약 0.8초 및 제어 여유를 고려한 **설계 예산**이다. 각 단계 P95를 더한 값이 전체 P95와 같다는 뜻은 아니다. 병렬 OCR, VAD, 대기열·재시도를 포함한 전체 시간을 직접 측정해야 한다. 새 프레임이 필요한 경우 그 지연도 자동 처리 시간에 포함한다.

초기 LLM 2초 목표가 실기기에서 미달할 수 있다. 작은 모델·토큰 축소·backend 조정 후에도 미달하면 목표 미충족을 보고한다. 원인 분석 없이 “온디바이스이므로 원래 느리다” 또는 Colab 465ms로 대체하지 않는다.

### 10.5 모바일 측정 프로토콜

- 장치 모델 번호, 실제 RAM·OS·빌드·SoC, 배터리 상태, 충전 여부, 화면 밝기, 실내 온도, 케이스 유무, backend·threads를 기록한다. S24 Ultra의 공식 SoC는 Snapdragon 8 Gen 3 for Galaxy다. 실제 단말 설정은 시험 시 확인한다. [Samsung 공식 발표](https://news.samsung.com/global/enter-the-new-era-of-mobile-ai-with-samsung-galaxy-s24-series)
- 기본은 충전하지 않은 상태, 동일 밝기, 동일 네트워크 차단, 충분히 식힌 시작 조건으로 잡는다. 발열 조건이 다른 실행을 무작위로 섞어 비교하지 않는다.
- 초기 CPU 기준 4 threads를 설계 시작값으로 두고 dev에서 2/4/6을 비교한다. GPU/NPU 시험은 별도 트랙으로 기록한다. thread 수를 CPU 코어 수 또는 최적값으로 단정하지 않는다.
- 후보별 로딩 10회, warm 측정은 고정 입력 100건×3회 이상, 연속 통합 30분×3회로 시작한다. 문장 길이·경로별로 P50/P95와 실패율을 분리한다. warm-up 5회는 정확도에서 제외하지 않도록 별도 준비 입력을 사용한다.
- 프로세스 total PSS는 dumpsys meminfo 등으로 native 메모리까지 확인한다. 1초 간격 표본과 단계 전후 표본을 기록하되 순간 peak를 놓칠 수 있음을 표기한다. 모델 파일 크기, 로딩 전후 증가량, 전체 앱 PSS를 각각 보고한다. [Android dumpsys](https://developer.android.com/tools/dumpsys)
- Android thermal status·주파수/지연 변화, 가능한 경우 표면 온도, 배터리 온도를 구분한다. 배터리 센서 온도를 CPU 온도라고 부르지 않는다. SEVERE 이상에서는 부하를 중지하고 원인을 분석한다. [Android Thermal API](https://developer.android.com/games/optimize/adpf/thermal)
- 배터리는 가능한 charge counter/전력 계측으로 같은 시간·과업 수를 비교한다. OS 잔량 %만 가능하면 거친 참고값으로 기록하며 요청당 전력을 계산한 것처럼 보고하지 않는다.
- 시작·종료 네트워크 트래픽과 의존 서비스 경로를 확인한다. 비행기 모드에서 Wi-Fi가 다시 켜져 있지 않은지 확인하고, 모델 설치 완료 상태·미설치 상태를 각각 시험한다.

| 단계 | 주요 작업·담당 | 선행 조건 | 완료 산출물·판정 |

| G0 기준 정리 | R1/R2: 의도·경계·등급 검수. R6: baseline 동결·데이터 분리. R3: 원본 모델 출처 정리 | 사용자 명세 검토 | 의도·평가 기준 버전, V1 보존 목록, dataset manifest, 시험 목표 동결안 |
| G1 실행 가능성·NLU 기준 | R3: M0~M4 호환성, 직접 PTQ. R2: 동일 prompt/parser 평가. R4: 텍스트 최소 앱 | G0 | 새 모델 포함 실행 가능 표, raw 예측, 정확도·모바일 기초 자원 결과 |
| G2 전체 기능 통합 | R4: 화면·세션·Fallback. R5: STT/OCR/TTS·좌표. R2: Router/Validator | G1 통과 조합 | 오프라인 시나리오, F01~F14·TC01~TC13 결과, TTS 실제 artifact/voice 식별 |
| G3 최적화 | R3/R2: PTQ 보정·토큰·필요 시 QAT/대안 엔진. R6: 통제 비교 | G2 오류 원인 분리 | 단일 변수 비교표, 후보 축소·최종 설정 동결 |
| G4 독립 검증·채택 | R6 주도, R1 사용자 평가, 전체 팀 결함 수정 판단 | 설정 동결·최종 test 미사용 | 독립 test·장시간·오프라인·사용성 결과. 모델/정밀도/backend 최종 선정 또는 미충족 보고 |

R2는 라벨 검수와 prompt 개발을 담당하되 최종 test 정답 관리는 R6가 맡아 개발 중 노출을 줄인다. 성능 목표 변경·범위 추가는 이유와 버전을 기록하고 사용자에게 확인받는다. 일정·인원 수는 자료에서 확정할 수 없어 날짜를 임의로 배정하지 않았다.

## 13. 지금 결정한 사항과 남은 확정 사항

| 항목 | 이번 문서에서의 결정 | 최종 확정 시점 |
|---|---|---|
| 제품 동작 범위 | 사용자 단말의 안내 보조, 모든 AI 추론 로컬 | G0 검토 |
| 의도·등급 | 14 의도 초안 + topic, H/M/L/U와 C1/C2/C3/CU | G0 2인 라벨 검수 후 동결 |
| 기본 구조 | 좁은 Rule 허용 목록 + LLM 의미 해석 + 공통 검증·Fallback | G1 구조 비교 후 G2 적용 |
| 신규 주 후보 | Gemma 4 E2B, Qwen 3.5 2B/0.8B 및 조건부 Kanana 2 1.3B 비교 | G4 성능·자원 모두 통과 후 최종 1개 |
| 엔진 | llama.cpp 기준, LiteRT-LM 조건부 비교 | G3~G4 |
| 양자화 | 동일 원본 고정밀/Q8_0/Q4_K_M 직접 비교 | G3~G4. Q4 자동 채택 아님 |
| 정확도 목표 | 단일 의도 ≥95%, Macro F1 ≥0.93, 고영향 잘못된 안내 관측 0건 | 목표는 G0/pilot 후 동결, 달성 여부는 G4 |
| 허용 지연 | warm 의도 P95≤2초, 전체 음성 안내 P95≤5초, 자동 처리 8초 deadline | G1 실현 가능성 점검 후 동결, 달성 여부 G4 |
| 메모리·열 | 전체 앱 PSS≤4GiB 예산, SEVERE 이상 시험 중지, 30분 안정성 | G1 예산 검토 후 G4 검증 |
| QAT | 손실·필요성·배포 호환성 충족 시 수행 | G3 진입 조건 충족 시 별도 실험 승인 |
| 실제 담당자·STT 원본·Android TTS artifact | 역할·확인 작업 지정, 출처 미확정 명시 | G0~G2 |

## 14. 작성 후 남은 자료와 승인 경계

후속 구현 전에 필요한 자료는 현재 Android 소스·빌드 환경, 실제 S24 Ultra 기기 정보, STT 원본 checkpoint/hash, Android TTS artifact 또는 offline voice 정보, 검증할 실제 화면·과업 목록이다. 이 자료가 아직 없어도 본 기능·입출력·평가 명세는 검토할 수 있다.

이번 산출물은 구현을 위한 검토안이다. 앱 수정, 모델 다운로드·추론, PTQ/QAT 실행, 실기기 조작, 사용자 음성 수집은 수행하지 않았다. 사용자가 요청한 사전 확인 원칙에 따라 해당 실행 작업은 범위를 제시하고 별도 승인받는다.

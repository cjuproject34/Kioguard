# KioGuard 14개 의도 체계: 채택 근거와 데이터 라벨링·평가 통합 기준


**이 문서는 14개 의도 체계를 제안한 이유와 현재 라벨링·평가에 적용할 기준을 한곳에 모은 실무 기준서다.** 초기 승인안의 채택 근거를 계승하되, 의미가 달라진 부분은 수정 기준 v1.2와 이후 사용자 결정을 따른다. 통합 문서의 v1.0은 편집 버전이며, 의미 정의를 과거 v1.0으로 되돌린다는 뜻이 아니다.

## 1. 이 문서를 적용하는 범위와 현재 상태

| 구분 | 적용 기준 |
|---|---|
| 채택 배경 | [의도 정의·경계 기준 승인안 v1.0](KioGuard_의도정의_경계기준_승인안_v1.0.md)의 문제의식과 설계 이유 |
| 현재 의미·경계 | [의도 정의·경계 기준 v1.2](KioGuard_의도정의_경계기준_v1.2.md). 본 문서 4~9절에 통합 |
| 이후 사용자 결정 | [현재 상태](../STATUS.md): 핵심 14개 유지, 새 화면 읽기·도움 세션 종료 음성 명령은 보류 |
| 기계 출력·채점 | 출력 계약 v3와 현재 채점기. 본 문서 11~13절의 구현 차이까지 함께 적용 |
| 데이터 상태 | 166건은 개발·회귀용 초안이며 사람 검수·최종 동결 전. 이 문서 작성만으로 APPROVED가 되지 않음 |
| 제품 역할 | 서비스 AI 추론은 온디바이스. KioGuard는 사용자의 외부 키오스크 조작을 안내하며, 의도 인식만으로 결제·취소·신청을 자동 실행하거나 성공했다고 말하지 않음 |

라벨러는 이 문서를 먼저 읽고, 사례별 이견은 근거와 함께 기록한다. 과거 승인안의 상충하는 예시를 현재 정답으로 다시 적용하지 않는다. 두 원문은 변경 이력으로 보존한다. 본 통합 작업은 새 의도를 추가하거나 기존 데이터 정답·모델·프롬프트·채점 코드를 변경하지 않는다.

### 먼저 기억할 다섯 가지

1. 의도는 **사용자가 원하는 일**이다. 실제로 실행 가능한지, 대상 정보가 있는지는 별도 판단이다.
2. 정답은 의도명 하나가 아니다. 대상·값·선택/거절·조건·선행 관계·재질문까지 포함한다.
3. 의미를 아는데 대상만 모르면 의도를 유지한다. 의미 자체가 갈리면 필요한 재질문을 정답으로 둔다.
4. 기존 8개 라벨 점수와 새 14개 기준 점수를 직접 비교하지 않는다.
5. 의미 기준, JSON 계약, 프롬프트, 채점기는 서로 다른 버전이다. 실험마다 모두 기록한다.

## 2. 왜 14개 의도 체계를 채택하려 했는가

기존 8개 의도를 그대로 고·저 우선순위로 나누면 서로 다른 사용자 요구와 오류가 한 라벨 안에 섞인다. 초기 승인안은 이를 **요청 종류 14개 + 주제·대상·값 + 부정·대화 문맥**으로 표현하자고 제안했다. 아래는 그 설계 이유를 현재 경계 기준에 맞춰 정리한 것이다. [근거: 승인안 1~6절](KioGuard_의도정의_경계기준_승인안_v1.0.md)

| 해결하려던 문제 | 채택한 표현 방식 | 라벨링·평가에서 얻으려는 효과 |
|---|---|---|
| 결제수단 선택과 최종 확정, 영수증 선택을 혼동 | PAYMENT_METHOD / COMMIT_REQUEST / RECEIPT 분리 | ‘현금으로’와 ‘현재 거래를 확정’의 오류를 구별하고 잘못된 확정 안내를 찾아냄 |
| 화면 이동·주문 취소·내용 초기화를 혼동 | NAVIGATE / CANCEL / RESET 분리 | 첫 화면 이동을 주문 삭제 의사로 확대하지 않음 |
| 사실 질문·방법 질문·일반 도움의 경계가 불분명 | INFO / GUIDE / HELP 분리 | 필요한 답이 사실인지, 조작 절차인지, 지원인지 구별 |
| 상품 선택·변경과 전문적인 선택 변경을 중복 처리 | SELECT / MODIFY와 FULFILLMENT·PAYMENT_METHOD·RECEIPT·BENEFIT_CONTROL 구분 | 새 주문 옵션을 중복 요청으로 세지 않고 결제수단 변경 등은 해당 전문 의도로 기록 |
| 같은 의도 안의 대상·방향·조건 오류가 라벨 정확도에 가려짐 | 요청별 target·slots·condition·depends_on 및 제약 기록 | ‘영수증 거절→발급’, ‘포장 불가 시 취소→즉시 취소’ 오류까지 평가 |
| 앱이 직접 할 수 없는 요청을 다른 의도로 바꾸는 문제 | UI_CONTROL의 대상 APP/KIOSK/UNKNOWN과 실행 가능 여부 분리 | 외부 글자 확대 요청의 원래 의미를 보존하면서 실제 안내 능력은 별도 검증 |
| 모호함·정보 부족·형식 오류를 모두 미분류로 처리 | 의미 판단·필수 정보·근거·fallback·기술 오류 분리 | 올바른 재질문을 오답으로 만들지 않고 문제 원인별 개선 가능 |

**14개가 정확도·메모리·속도 면에서 최적이라는 실험 결과는 없다.** 현재 업무와 안내를 구별하기 위한 검수용 설계이며, 레이블을 늘렸다는 사실만으로 성능이 좋아졌다고 주장하지 않는다. 실제 채택 타당성은 사람 간 일치도, 경계 사례의 구별 가능성, 의도별 데이터 수와 모델 오류를 보고 검토해야 한다. 이 검토 항목은 앞으로 확인할 사항이며 이미 측정한 결과가 아니다.

세분화의 비용도 있다. 의도별 자료가 적어지고 경계 합의·문맥 수집·출력 계약 관리가 더 필요하다. 따라서 상품명·온도·수량마다 새 의도를 만들지 않고 값으로 표현한다. 재질문도 15번째 업무 의도로 만들지 않는다. 새 화면 읽기와 도움 세션 종료 음성 명령은 별도 보류 상태이며, 최종 앱의 모든 음성 기능이 반드시 14개로 끝난다는 뜻은 아니다. [근거: v1.2 1·5·8절](KioGuard_의도정의_경계기준_v1.2.md), [후속 결정](../STATUS.md)

## 3. 초기 승인안에서 바뀐 내용과 우선순위

| 항목 | 초기 승인안 v1.0 | 현재 적용할 기준 v1.2 |
|---|---|---|
| I07 | BACK, 이전 단계 중심 | NAVIGATE: 이전·다음·HOME·특정 화면. 단순 HOME은 RESET이 아님 |
| I13 | PROCEED, 진행·확정의 경계가 넓음 | COMMIT_REQUEST: 특정 거래·주문·신청의 최종 확정. 안내 동의·다음 화면 이동 제외 |
| I06 | BENEFIT_APPLY, 적용 중심 | BENEFIT_CONTROL: 적용·해제·참여·거절 포함 |
| I05 | 영수증 발급·재발급 중심 | 받기·받지 않기 구분. 문제 보고만으로 재발급을 추정하지 않음 |
| ‘따뜻한 걸로 두 잔이요’ | 문맥 없는 옵션 설정 우선 제안 | FD-03은 사용자 지정 문맥 때문에 MODIFY. 모든 문맥 없는 유사 발화에 일반화 금지 |
| ‘화면을 못 찾겠어요’ | GUIDE 제안 | 지정 사례 FD-24·GV-20은 ASK_SCREEN_TARGET |
| ‘취소하고 다시 처음부터 할게요’ | RESET 또는 취소+재시작 후보 | FD-08은 CANCEL → NAVIGATE(HOME), 취소 결과 확인 후 이동 |
| 짧은 확인 응답 | 질문 연결 원칙은 있으나 진행·확정 혼동 여지 | 질문 유형·대상·유효성 검증. 방법 안내 동의는 GUIDE, 최종 확정만 COMMIT_REQUEST |
| 조건·부정·복잡도 | 일부 거친 분류와 예시 | 조건절 사건을 긍정 요청으로 추가하지 않음. 부정·지시어 한 단어만으로 C3 판정 금지 |

이는 이름만 바꾸는 개정이 아니다. 과거 `BACK`, `PROCEED`, `BENEFIT_APPLY`를 일괄 치환하고 과거 점수를 유지해서는 안 된다. 사례별 문맥과 의미를 다시 검수한다. 상세 변경 근거는 [재검토 v1.1](KioGuard_의도체계_재검토_수정권고_v1.1.md)과 [v1.2 변경 기록](KioGuard_의도정의_경계기준_v1.2.md)에 있다.

다음 4~9절은 v1.2의 사용자 지정 기준·정의·경계·의미 정답·영향도·평가 원칙을 통합한 본문이다. 출력 형식은 후속 구현을 반영하여 11절에 별도로 명시한다.

## 4. 사용자가 지정한 발화 기준

아래 기준은 과거 원본 실험의 실제 문맥을 복원한 사실이 아니라, **이번 수정본에서 사용할 사용자 지정 해석·기대 대응**이다. 원문은 기존 표의 표기를 보존한다.

| 원문·적용 ID | 반영한 기준 | 의도·기대 대응 | 남는 실행 전 확인 |
|---|---|---|---|
| 따뜻한 걸로 두 잔이요 · FD-03 | 선택한 상품의 옵션 설정 | I02 MODIFY, 온도=따뜻함·수량=2 | 선택 상품의 실제 ID, 복수 상품이면 적용 대상 |
| 처음으로 돌아가주세요 · FD-22, GV-19 | 첫 화면 이동 | I07 NAVIGATE, 목적지=HOME | 어느 화면 흐름인지, 이동 시 상태 소실 여부 |
| 화면을 못 찾겠어요 · FD-24, GV-20 | 어떤 화면인지 재질문 | 의도 판정 보류, 기대 대응=ASK_SCREEN_TARGET | “어떤 화면을 찾고 계신가요?”에 대한 답 |
| 취소하고 다시 처음부터 할게요 · FD-08 | 현재까지 주문한 내역 취소 후 첫 화면 이동 | I08 CANCEL → I07 NAVIGATE(HOME) | 현재 주문 범위·결제 상태·취소 결과 확인 |
| 번호표 뽑는 거 알아요 · GV-09 | 재질문 | 발화 목적 판정 보류, 기대 대응=ASK_GUIDANCE_NEED | “번호표 뽑는 방법을 안내해 드릴까요?”에 대한 답 |

이 다섯 기준은 다시 의미를 결정해 달라고 요청할 항목이 아니다. 예를 들어 FD-08을 다시 RESET 하나로 축약하거나 FD-03을 신규 주문 후보로 되돌리지 않는다. 남는 상품 ID·결제 상태·화면 대상 확인은 실제 안내를 위한 정보 수집이다.

FD-24·GV-20·GV-09의 재질문은 정상적인 정답 대응이다. 재질문을 업무 의도 I15로 추가하거나 기술 오류로 기록하지 않는다. 질문 이후의 의도는 후속 답변으로 결정한다.

| I13 | COMMIT_REQUEST · 최종 확정 요청 | 특정 주문·거래·신청의 최종 확정/제출 의사 | 방법 안내 동의, 다음 화면 이동, 문맥 없는 ‘네’는 포함하지 않음 |
| I14 | RESET · 과업 재시작·초기화 | 과업을 버리고 다시 시작하거나 내용 초기화를 요청 | 단순 첫 화면 이동·설명 다시 듣기는 제외. 취소와 이동의 명시적 복합 요청을 강제로 합치지 않음 |

업무 행동·질문·도움·앱 제어를 포함하는 실용적 분류이며, 순수하게 한 축만으로 나뉜 분류라고 표현하지 않는다. 전문 의도가 표현하는 요청을 일반 의도에 중복 배정하지 않는다. 다만 서로 독립적인 요청이 실제로 여러 개이면 모두 보존한다.

## 6. 경계 판정 규칙

### 6.1 요청·질문·진술과 문맥

질문형 어미만으로 INFO를 정하지 않는다. ‘카드 지원되나요?’는 지원 질문이고, ‘현금으로 바꿔 주실 수 있나요?’는 문맥상 정중한 변경 요청일 수 있다. 질문·요청이 갈리면 필요한 확인을 한다.

새 주문과 변경은 현재 대상·직전 질문을 사용한다. ‘라떼 뜨겁게 한 잔 주세요’가 새 주문이면 I01에 상품·온도·수량을 기록한다. ‘어떤 음료로 바꾸실래요?’에 대한 같은 답이면 I02일 수 있다. 현재 선택 대상이 없다는 이유만으로 ‘바꿔 주세요’를 신규 요청으로 바꾸지 않는다.

FD-03은 사용자가 선택 상품의 옵션이라는 문맥을 지정했으므로 I02를 적용한다. 이 기준을 모든 문맥 없는 온도·수량 발화에 일반화하지 않는다.

INFO는 요구하는 답이 값·지원 여부·상태·조건 설명인 경우, GUIDE는 수행할 방법·행동·위치 안내인 경우다. ‘쿠폰 되나요?’는 I10, ‘쿠폰 써 주세요’는 I06, ‘쿠폰 어디 찍어요?’는 I09다. 로컬 답변 근거가 없다는 이유로 INFO를 범위 밖으로 바꾸지 않는다.

### 6.2 이동·초기화·최종 확정

| 발화·명시 문맥 | 해석 |
|---|---|
| 화면 이동 요청: ‘첫 화면으로 가 주세요’ | I07, 목적지=HOME |
| ‘입력한 내용 지우고 처음부터 작성할게요’ | I14, 대상·초기화 범위 기록 |
| ‘결제 화면으로 가 주세요’ | I07, 목적지=결제 화면 |
| 최종 거래를 가리키며 ‘이 금액으로 결제를 확정할게요’ | I13, 거래·확정 대상 기록 |
| 앱 안내 재생 중 ‘설명을 처음부터 다시 읽어 주세요’ | I11, 기존 안내 반복 |
| FD-08의 사용자 지정 상황 | I08 현재 주문 취소 → I07 첫 화면 이동 |

HOME/NEXT 버튼이 실제로 데이터 삭제나 거래 확정을 일으키면 **동작 효과**를 별도로 기록한다. 사용자의 이동 요청을 사후에 초기화·확정 의사로 변경하지 않는다. 효과가 요청 범위를 넘으면 설명·추가 확인·안내 보류가 필요하다.

FD-08은 취소 완료를 확인한 뒤 첫 화면 이동을 안내한다. 취소 결과가 불명확하거나 실패했으면 완료를 주장하거나 다음 단계를 강행하지 않는다. 결제 전 주문 취소와 이미 결제된 거래의 취소 절차는 현재 상태를 보고 구분한다.

### 6.3 부정·거절·해제

| 발화 | 요청·제약 기록 |
|---|---|
| ‘영수증 안 받을게요’ | I05, 선택=DECLINE |
| ‘적용된 쿠폰 빼 주세요’ | I06, 동작=REMOVE |
| ‘이번에는 적립 안 할게요’ | I06, 참여=DECLINE |
| ‘시럽 빼 주세요’ | I02, 해당 상품의 시럽 옵션 제외 |
| ‘라떼 빼 주세요’ | I08, 해당 주문 항목 제거 |
| ‘카드 말고 현금’ | I04, 선택=현금·배제=카드 |
| ‘주문 취소하지 마세요’ | 해당 주문 취소 금지. 취소 요청으로 승인하지 않음 |

정답에는 **요청·선택·질문과 요청된 상태 변경**을 기록한다. 부정 문법이 있다는 이유로 모두 ‘의도 없음’으로 바꾸지 않는다. 순수 금지는 제약으로 보존하며 대기 중인 요청에도 적용한다. 조건·인용·가정에 나온 동작을 실행 요구로 추가하지 않는다.

### 6.4 확인 응답의 범위

확인 응답은 유효한 질문의 ID·유형·내용·대상·문맥 버전에 연결한다. 질문이 없거나 거래 금액·대상·화면이 바뀌어 유효하지 않으면 다시 확인한다.

| 직전 질문 | 응답 | 정답 의미 |
|---|---|---|
| ‘포장으로 선택할까요?’ | 네 | I03 수락 |
| ‘영수증을 받으시겠어요?’ | 아니요 | I05 거절 선택 |
| ‘결제 방법을 안내할까요?’ | 네 | I09 안내 수락 |
| ‘현재 이 거래를 확정하시겠습니까?’라는 유효한 질문 | 네 | 해당 거래에 한정된 확인 의사. 앱의 외부 실행 권한이나 성공 증거는 아님 |
| 대기 질문 없음/유효성 상실 | 네 | 확인 대상 재질문 |

‘카드로 결제할게요’와 ‘현금으로 낼게요’는 수단 선택 문맥에서는 I04다. 최종 거래 확인에 대한 응답 문맥에서는 그 질문과 연결된 확정 의사가 포함될 수 있다. 원문만으로 I13을 추가하지 않으며 결제 성공으로 기록하지 않는다.

### 6.5 여러 요청·조건·대안

요청별 대상·값·조건·배제·순서·선행 관계를 보존한다. 같은 의도 유형이 반복돼도 서로 다른 상품·거래 대상과 값을 합쳐 버리지 않는다.

| 발화 | 기록·제약 |
|---|---|
| ‘두 개는 포장하고 하나는 먹을게요’ | I03, 상품/부분 집합별 수량·방식 연결. 의도 유형은 하나지만 배분 값은 둘 |
| ‘첫 라떼는 차갑게, 두 번째는 따뜻하게’ | I02, 각 대상과 온도 연결 |
| ‘라떼 한 잔하고 아메리카노 두 잔 주세요’ | I01, 각 상품과 수량 연결 |
| ‘포장이 안 되면 주문 취소해 주세요’ | I08은 조건부 요청. 포장 불가 여부가 미확인이면 취소 안내 보류 |
| ‘카드가 안 되면 현금으로 할게요’ | 조건 성립 시 현금 선택. 조건절만으로 새 카드 결제 요청을 추가하지 않음 |
| ‘취소가 끝나면 처음부터 다시 주문할게요’ | 취소 완료를 재시작의 선행 조건으로 기록. 조건에 취소가 언급됐다는 이유로 I08 실행 요청을 추가하지 않음 |
| ‘현재 주문을 취소하고 첫 화면으로 가 주세요’ | I08과 I07의 명시적 두 요청, 취소 결과 확인 후 이동 |

조건은 참·거짓·미확인과 근거 출처를 구분한다. 조건이 거짓이거나 미확인이면 해당 분기의 행동을 무조건 실행 가능한 요청으로 바꾸지 않는다. 요청 수 제한은 정답에서 세 번째 요청을 삭제하는 기준이 아니다. 앱이 처리할 수 없는 복합 요청은 나누어 확인한다.

### 6.6 도움·문제 보고·재질문

일반 도움은 I12 GENERAL_SUPPORT, 직원 도움은 I12 HUMAN_ASSIST, 현재 문제의 지원 요구는 I12 ISSUE_SUPPORT로 구분한다. 구체적인 해결 방법을 묻는다면 I09에 문제 보고 내용을 함께 기록하며 같은 요구에 HELP를 기계적으로 중복 추가하지 않는다.

‘카드가 두 번 결제됐어요’는 현재 문제를 보고하는 맥락과 과거 경험담·인용을 구분한다. 사용자 보고를 확인된 거래 상태로 저장하지 않는다. ‘결제했어요’라는 완료 응답도 사용자 보고로 기록하며 결제 성공 검증과 분리한다.

FD-24·GV-20에는 “어떤 화면을 찾고 계신가요?”를 먼저 묻는다. 답이 메뉴 화면 탐색이면 I09, 카메라·앱 문제 지원이면 I12 등의 후속 판단을 한다. GV-09에는 “번호표 뽑는 방법을 안내해 드릴까요?”를 묻고, 동의하면 I09로 안내한다. 이 후속 분기는 설계 예시이며 실제 답변을 수집한 결과가 아니다.

## 7. 의미 정답과 대응 상태의 분리

| 기록 구분 | 내용 |
|---|---|
| 출처·버전 | 원문·V1 라벨·사례 ID·정의 버전·동일/유사 발화 그룹 |
| 제공한 문맥 | 화면, 단계, 선택 상품, 직전 질문, 문맥 출처. 사용자 지정 시나리오와 과거 관측 자료 구분 |
| 발화 유형 | 요청·질문·확인 응답·진술·문제 보고·금지. 한 발화에 여러 유형 가능 |
| 요청 내용 | 의도, 작업/선택 방향, 주제, 대상, 값. 모호한 경우 후보와 미확정 사유 |
| 관계·제약 | 요청별 대상 연결, 조건, 배제, 순서, 선행 관계, 금지 |
| 판단 상태 | 의미 확정 여부, 대상/값 누락, 답변 근거 유무, 범위 결정 대기 여부 |
| 기대 대응 | 안내 검증 진행, 대상 재질문, 의도 재질문, 근거 확인, 조건 충족 대기, 범위 안내 등 |
| 영향·복잡도 | 등급과 사유, 등급의 확정/잠정 상태, 관련 문맥·입력 품질 |
| 검수 | 사용자 지정 기준 유무, 작성자·검수자·불일치·합의 기록 |

이것은 평가용 의미 계약이다. 이후 구현된 실제 LLM 출력 계약 v3은 11절에 정리했다. 모든 설명·검수 이력을 LLM이 생성하도록 요구하지 않는다. 런타임 출력에 담기지 않는 출처·검수·제약 정보도 평가 원본에서는 보존한다.

‘민원서류 떼러왔어요’는 I01을 유지하면서 서류 종류를 질문한다. ‘삼성페이 돼요?’의 근거가 없으면 I10을 유지하면서 근거를 확인한다. 반면 의도 자체가 갈리는 입력은 판정을 보류할 수 있다. 기술 오류, 원래 모호한 발화, 범위 밖 요청, 지원 여부 미확인을 하나의 미분류 라벨로 합치지 않는다.

미결정 음성 기능은 제품 범위 결정 대기로 기록한다. 이미 확정된 범위 밖 요청과 동일하게 학습시키지 않는다. 실제 민감값을 정답 슬롯으로 수집하지 않는다.

## 8. 영향도·복잡도와 처리 정책

### 8.1 영향도

| 등급 | 기준 |
|---|---|
| L | 금전·민감정보·중요 상태 변경과 연결되지 않는, 쉽게 되돌릴 수 있는 국소적 표시·재생 조절 등 |
| M | 수정 가능하지만 잘못된 선택·재작업·동선 혼동을 만드는 안내 |
| H | 금전 확정/취소, 민감정보 입력·노출, 중요한 신청 확정, 복구 어려운 내용 소실에 연결되는 안내 |
| U | 단계·대상·결과 등 영향도 결정에 필요한 정보가 없음 |

사용자 의도, 실제 버튼 효과, 잘못 안내했을 때의 결과를 구분한다. 거래 관련 보호 주제를 표시하되 결제 단어가 있다는 이유만으로 모두 H로 고정하지 않는다. U는 낮은 영향도의 다른 이름이 아니다.

기존 48행의 문맥이 부족한 항목은 U로 남긴다. `U→M/H` 같은 가능 범위는 확정 등급으로 사용하지 않는다. PIN 입력 위치 안내처럼 민감정보 입력을 직접 다루는 경우에는 그 사유로 H를 부여한다. 이것도 위험 발생 실측치가 아니라 평가 기준상의 등급이다.

### 8.2 복잡도

| 등급 | 의미 구조 기준 | 예시 |
|---|---|---|
| C1 | 분명한 단일 요구·단순 값 또는 이미 명확히 연결된 짧은 응답 | 현금 선택, 명확한 대상의 온도를 아이스로 변경 |
| C2 | 단일 요구의 여러 속성, 표현 변형, 명확한 대조·치환, 단순한 대상 연결 | 상품·온도·수량 지정, ‘등본 말고 초본’ |
| C3 | 조건·대안·선행 관계, 여러 대상의 배분, 부정 범위 또는 발화 목적의 복합 해석 | 포장 불가 시 취소, 서로 다른 상품의 수량·방식 배분 |
| CU | 입력 훼손 등으로 의미 구조 자체를 판단하기 어려움 | 핵심 단어가 사라진 STT 결과 |

먼저 요청 수·대상/값 관계·부정 범위·조건·참조 문맥·입력 품질을 기록한다. 지시어·변경 동사·부정어 하나만으로 C3를 주지 않는다. 필요한 대상 정보가 없다는 이유만으로 CU를 주지 않는다. 짧은 민감정보 안내는 H이면서 C1일 수 있다.

48발화 표의 복잡도는 제공된 발화와 사용자 지정 문맥에 기초한 **잠정 등급**이다. 실제 화면에서 여러 대상을 해소해야 하는 등 추가 관계가 드러나면 갱신한다. 잠정 C1을 Rule 통과 근거로 사용하지 않는다. 이 등급은 토큰 수·연산량·지연시간 측정값이 아니다.

### 8.3 LLM/Rule과 fallback

| 조건 | 정책 |
|---|---|
| 명시적 앱 중지 버튼 등 확정된 UI 이벤트 | 필요한 로컬 제어 즉시 수행 |
| 빈 입력·명확히 빠진 필수 정보 | 입력 복구 또는 필요한 질문. LLM을 반복 호출해 누락 정보를 추측하지 않음 |
| L+C1이고 검증된 전체 Rule 패턴·상태·필수 값·제약이 모두 충족 | Rule 직접 처리 후보 |
| H/C3 또는 위 Rule 자격을 충족하지 않는 해석 가능한 요청 | LLM 의미 해석 + 공통 상태·근거 검증 |
| 조건 미충족·의도 불명확·대상 부족·검증 실패 | 해당 원인에 맞는 보류·재질문·근거 확인 |

재질문 템플릿을 규칙으로 표시할 수 있다는 것과 업무 의도를 Rule로 확정했다는 것은 다르다. 이번 48개 정답 문장을 외워서 Rule 호출률을 낮추는 방식은 평가 근거로 삼지 않는다. LLM을 사용해도 확인되지 않은 화면·결제 상태가 자동으로 사실이 되지 않는다.

## 9. 평가에 적용할 기준

1. 텍스트만 제공하는 평가와 문맥을 제공하는 평가를 분리한다. 사용자 지정 문맥으로 정답을 정했다면 해당 문맥을 모델에도 제공하거나, 원문만으로 판단 가능한 범위의 정답을 따로 둔다.
2. 의도명과 요청별 대상·값·선택/해제 방향·부정·조건·확인 질문 연결을 나누어 평가한다. 발급 거절을 발급으로 해석하면 I05를 맞혀도 전체 의미 정답은 실패다.
3. 같은 의도 유형의 여러 요청과 서로 다른 의도 유형의 요청을 구분한다. 상품별 수량·온도를 바꾸어 연결하면 실패다. 배열 순서는 의미 있는 선행 순서가 있을 때 평가하며 표현상의 순서 차이만으로 실패시키지 않는다.
4. 재질문이 정답인 사례를 삭제하지 않는다. FD-24·GV-20·GV-09는 적절한 재질문 여부를 평가한다. 하나의 업무 의도를 억지로 정답으로 지정하지 않는다.
5. 모호한 사례의 단일 라벨 정확도 포함 여부·분모를 공개하고, 전체 사례에서의 올바른 대응과 불필요한 재질문 비율을 함께 보고한다. 기술 실패도 조용히 제외하지 않는다.
6. FP 기준·PTQ·QAT에 같은 정의 버전·입력·평가기준을 적용한다. 기존 8개 라벨 점수와 새 기준 점수를 직접 비교하지 않는다.
7. 48개 원문은 기존 개발·회귀 자료다. 같은 문장과 유사 표현을 그룹으로 관리하며 새 독립 평가셋으로 승격하지 않는다. 새 예시는 설계 사례로 표시한다.

정확도 목표·지연 한계·메모리 예산·최종 모델은 이번 의도 수정으로 새로 확정하지 않았다. 기존 목표치를 달성값으로 표현하지 않는다.

## 10. 검수자가 사례 한 건을 처리하는 순서

이 절은 앞의 의미 기준을 현재 데이터에 적용하기 위한 작업 순서다. 새로운 사람 검수 결과나 합의가 이미 존재한다는 뜻이 아니다.

| 순서 | 확인할 것 | 기록·판정 방법 |
|---|---|---|
| 1 | 출처와 문맥 | case_id·group_id·원문을 유지하고 관측 문맥인지 구성한 시나리오인지 표시한다. 모델에 제공하지 않은 문맥으로 정답을 결정하지 않는다 |
| 2 | 발화 목적 | 요청·사실 질문·방법 질문·확인 응답·문제 보고·진술·금지를 구분한다. 인용·가정·조건절의 사건을 긍정 요청으로 추가하지 않는다 |
| 3 | 의도 경계 | 5절의 14개 정의와 6절 사례를 적용한다. 전문 의도 우선, 동일 요구 중복 라벨 금지, 실제 복합 요청은 보존 |
| 4 | 대상과 값 | 실제 선택 ID·새 대상·변경 대상, 수량·옵션·선택/거절·배제 값을 확인한다. 대상 누락과 의도 불명을 구분 |
| 5 | 조건·선행 관계 | 조건의 검증할 상태와 근거, 각 요청의 대상 연결, 결과 확인이 필요한 순서를 기록한다 |
| 6 | 기대 대응 | 의미가 확정됐는지, 무엇을 물어야 하는지, 어떤 행동을 보류해야 하는지를 결정한다. 재질문도 정답 |
| 7 | 영향도·복잡도 | L/M/H/U와 C1/C2/C3/CU를 각각 사유와 함께 기록한다. U를 L로, 대상 누락을 CU로 자동 변환하지 않는다 |
| 8 | 계약 표현 | 11절 계약으로 gold를 작성한다. 표현할 수 없는 의미는 임의 키로 해결하지 않고 계약 이슈로 기록한다 |
| 9 | 독립 검수·불일치 | 다른 검수자가 의미·대상·조건·fallback을 검토한다. 불일치는 양쪽 판단·근거·합의 결과를 남긴다 |
| 10 | 승인·동결 | 미해결 이견·문맥 누락·계약 충돌을 정리하고 승인한 행만 APPROVED로 관리한다. 제외 사례는 ID·사유·분모 변화를 남긴다 |

검수 시작점은 [166건 검수표](../evaluation/data/evaluation_review_v0.1.csv)이며, 구조화 원본은 [84건 개발셋](../evaluation/data/selection_dev_v0.1.jsonl), [34건 challenge](../evaluation/data/selection_challenge_v0.1.jsonl), [48건 회귀셋](../evaluation/data/legacy48_regression_v1.2.jsonl)이다. CSV만 수정하고 JSONL gold가 이전 상태로 남지 않도록 같은 case_id로 대조한다. 자동 [데이터 검증기](../evaluation/scripts/validate_dataset.py)의 통과는 구조 검증이며 사람이 의미 정답에 합의했다는 증거가 아니다.

최소 검수 기록은 **case_id, 판정 전후 gold, 수정 이유, 사용한 문맥·출처, 정의 버전, 검수자, 검수일, 불일치 및 해결 내역, 승인/보류 상태**다. 현재 파일에 없는 검수 이력은 별도 이력 파일로 보존하고 LLM 출력 JSON에 넣지 않는다. PIN·주민등록번호 등의 실제 민감값은 수집하지 않는다.

## 11. 현재 출력 계약과 라벨 표현

### 11.1 의미 정의와 출력 계약은 별개다

현재 기계 출력은 [output_v3.schema.json](../evaluation/schemas/output_v3.schema.json)을 따른다. 의미 정의 v1.2, 프롬프트 v3.3, 사례 재실험 V3.2는 서로 다른 버전 축이다. 예를 들어 ‘실험 V3.2’라는 이름만으로 의도 정의가 v3.2로 개정된 것은 아니다.

| 필드 | 형식과 적용 기준 |
|---|---|
| requests | 요청 배열. 긍정 요청이 없으면 빈 배열. 알 수 없는 의도를 임의로 채우지 않음 |
| request_id | r1부터 r2, r3… 순서대로 부여. 채점기가 순차 ID를 검사 |
| intent | 5절의 현재 코드 14개 중 하나. I01 등의 번호 자체를 코드 값으로 출력하지 않음 |
| target | 문자열 또는 null. 확인한 대상 ID·정규화된 대상명을 사용하고 누락 대상을 지어내지 않음 |
| slots | 객체. 요청에 필요한 값만 넣고 값 없는 slot을 임의 생성하지 않음 |
| condition | null 또는 state_key·operator·value를 모두 갖춘 객체. operator는 EQ/NE/IN/NOT_IN |
| depends_on | null 또는 앞선 요청 ID. 참조만으로 선행 작업 성공이 입증되는 것은 아님 |
| fallback | null 또는 type 및 선택적 field. field가 있으면 문자열 |

최상위는 `requests`, `fallback`만 허용하며 두 키 모두 필수다. 각 request의 여섯 키도 모두 필수다. 조건이 없으면 `condition: null`, 선행 요청이 없으면 `depends_on: null`을 명시한다. 스키마가 slot의 세부 의미까지 검증하는 것은 아니므로 JSON 유효성과 의미 정답을 별도로 확인한다. 조건 상태의 참·거짓·미확인과 근거는 입력 문맥·평가 기록으로 보존하며 임의의 최상위 키를 추가하지 않는다.

아래는 개발 사례 DEV-SEL-01의 gold다. 제공 문맥은 신규 주문 단계이며 현재 주문이 없고, 발화는 해당 데이터 원문을 기준으로 검수한다. 이 예시는 모델의 실제 출력이나 새 관측 사례가 아니다. [원본](../evaluation/data/selection_dev_v0.1.jsonl)

```json
{
  "requests": [
    {
      "request_id": "r1",
      "intent": "SELECT",
      "target": "NEW_ORDER",
      "slots": {"item_name": "아메리카노", "quantity": 1},
      "condition": null,
      "depends_on": null
    }
  ],
  "fallback": null
}
```

### 11.2 fallback은 15번째 의도가 아니다

| 코드 | 적용할 상황 |
|---|---|
| ASK_SCREEN_TARGET | 찾는 화면을 특정해야 함. FD-24·GV-20의 지정 대응 |
| ASK_GUIDANCE_NEED | 안내가 필요한지 확인. GV-09의 지정 대응 |
| ASK_TARGET | 수행 대상·종류 등 필수 대상 정보를 질문 |
| ASK_CONTEXT | 단계·직전 질문 등 해석에 필요한 문맥 확인 |
| ASK_REFERENCE | ‘이거/그거’ 등 참조 대상을 확인 |
| ASK_INPUT_REPEAT | 입력 훼손 등으로 재입력이 필요 |
| ASK_SCOPE | 요청 범위 확인이 필요. 제품 기능의 보류 결정 자체를 이 코드 하나로 대체하지 않음 |
| OUT_OF_SCOPE | 확정된 서비스 범위 밖 요청. 근거 미확인·기능 보류와 구분 |
| NO_ACTION | 긍정 행동 요구가 없는 진술·순수 금지 등에 추가 행동을 만들지 않음. 금지 제약은 별도 보존 |

허용 코드는 스키마가 정의하고, 실제 선택은 발화·문맥·기대 대응을 기준으로 한다. 의미가 명확하고 대상만 누락되면 의미 기록과 대상 질문이 함께 필요할 수 있다. 이를 ‘질문을 하면서 외부 작업을 실행한다’는 뜻으로 해석하지 않는다. 현재 프롬프트와의 차이는 13절을 참조한다.

## 12. 평가 실행과 결과 보고 기준

### 12.1 비교 전에 고정할 조건

동일 비교 안에서는 **사례 목록·gold 버전·입력 문맥·의도 정의·프롬프트·출력 계약·정규화·채점기·생성 설정**을 일치시킨다. 모델 원본 revision, GGUF 파일 해시, 양자화 형식, 런타임 버전, 실패·재시도 정책도 남긴다. 정의나 정규화가 달라졌다면 별도 실험으로 보고한다. FP16/BF16 기준 모델과 Q4/Q8 비교에서 프롬프트까지 바뀌었다면 점수 차이를 양자화만의 영향으로 귀속하지 않는다.

### 12.2 함께 보고할 지표

| 측정 항목 | 현재 지표 또는 기록 | 해석 주의 |
|---|---|---|
| 형식 | strict_json, normalized_json, contract_valid | raw 원문 기준인지 실행기 정규화 후 기준인지 표시 |
| 요청·의도 | request_count_exact, intent_multiset_exact, intent_order_exact, 의도별 P/R/F1·Macro F1 | 의도 일치가 대상·값까지 맞았다는 뜻은 아님. Macro F1은 정확도 %와 구분 |
| 대상·값·관계 | target_exact, slots_exact, condition_exact, depends_on_exact | 서로 다른 요청 간 값 뒤바뀜과 의미 있는 선행 순서도 확인 |
| 대응·전체 | fallback_exact, full_exact | 재질문 정답 포함. full_exact는 현재 구현상 배열 순서에도 민감 |
| 고영향·금지 | high-impact full exact, dangerous_extra_cases, must_not_hit_cases | 전체 분모와 고영향 분모를 별도로 기재. 계약 실패 raw 출력도 안전 감사 |
| 운영 실패 | 누락 예측, JSON/계약 실패, timeout·중단·재시도 | 실패를 조용히 제외해 정확도를 높이지 않음 |
| 재질문 품질 | 필요한 재질문의 적중·불필요한 재질문 사례 수/분모 | 현재 자동 집계에 없는 항목은 별도 산출 방법을 기록. 이미 구현됐다고 가정하지 않음 |

채점 근거: [score_predictions_v2.py](../evaluation/scripts/score_predictions_v2.py). 현재 Macro F1은 14개 의도를 대상으로 계산하며 표본에 정답이 없는 의도의 처리도 코드와 함께 밝힌다. 숫자는 반드시 `정답 수/전체 수(%)` 또는 명시한 F1로 보고하고, 같은 case_id로 회복·회귀·공통 실패를 비교한다.

### 12.3 분모와 데이터 용도

- 84건 개발셋 + 34건 challenge = 118건 selection, 별도로 48건 개발·회귀 자료이며 합계 166건이다. 20건 gate 결과를 166건 전체 성능으로 쓰지 않는다.
- 모호한 사례가 업무 의도 정확도에서 제외된다면 제외 ID·이유·분모를 공개하고, 전체 대응 평가에서는 적절한 재질문을 평가한다.
- 원본·패러프레이즈·같은 시나리오를 그룹으로 묶어 학습/개발/test 누출을 막는다. 기존 48행과 모델·프롬프트 선택에 쓴 자료는 독립 test가 아니다.
- gold를 고쳤다면 버전·차이를 보존한다. 기존 예측을 재채점한 결과와 새 모델 추론 결과를 구별한다.
- 의미 기준 정리만으로 정확도 목표·지연 한계·메모리 예산·최종 모델이 확정되는 것은 아니다.

데이터 용도와 상태 근거: [평가 README](../evaluation/README.md), [현재 상태](../STATUS.md). 양자화 전후 성능 수치는 이 기준서에서 새로 계산하거나 승인하지 않는다.

## 13. 의미 기준과 현재 구현이 다른 부분

아래는 2026-10-05 저장소 코드를 함께 읽어 확인한 사항이다. **통합 문서 작성으로 이 차이가 해결된 것은 아니다.** 라벨을 구현 오류에 맞춰 바꾸지 말고, 아래 한계를 기존 결과에 표시한다. 구현을 수정하면 버전을 올려 동일 예측을 재채점하거나 필요한 재실험을 수행한다.

| 확인한 차이 | 현재 구현 | 라벨링·결과 해석 기준 |
|---|---|---|
| 독립 요청의 순서 | 의미 기준은 의미 있는 선행 관계만 순서 평가. 채점기는 full_exact에서 배열 순서를 그대로 비교하고 필드 비교도 zip으로 위치를 맞춤 | 표현상 순서 차이만 있는 오답을 별도 분류. 기존 full_exact를 순서 불변 의미 정확도로 부르지 않음. 요청 ID·의존 관계를 보존하는 매칭은 후속 수정 필요 |
| nullable 키 누락 | 스키마는 키를 필수로 요구하지만 Qwen/Gemma 실행기는 누락된 condition·depends_on과 적용 조건에 맞는 fallback을 null로 보정 | 원문 구조 준수와 보정 후 계약 통과를 구분. 실행 버전·normalization_steps·보정 건수를 공개하고 의미 추정·라벨 치환으로 확장하지 않음 |
| 출력 포장 제거·JSON 추출 | 평가 README의 code fence 제거 설명보다 실행기의 정규화 범위가 넓음. 두 실행기는 출력에서 계약 JSON을 추출하고 Qwen 실행기는 프롬프트 echo·특정 종료 토큰도 제거 | 실험별 실제 정규화 범위를 기록. 설명문이 섞인 원문에서 JSON을 추출한 성공과 원문 그대로의 성공을 구분 |
| raw_output 이름 | 실행기의 predictions.jsonl에서 raw_output에는 정규화된 문자열이 저장됨. 원문은 predictions_raw.jsonl에 별도 보존 | 채점기의 strict_json만 보고 원문 무보정 JSON 성공률이라고 주장하지 않음. 세 파일을 함께 추적 |
| 알려진 의미와 재질문 | v1.2는 알려진 의도+대상 누락을 함께 유지. 스키마도 requests와 fallback 동시 존재를 금지하지 않지만 prompt v3.3 6항은 행동과 재질문의 동시 생성을 금지하는 문구를 사용 | ‘의미 기록’과 ‘즉시 실행’을 구분해 gold를 검수. 부분 확정 사례의 prompt/계약 일관성을 정리하기 전에는 골드를 지워 점수를 맞추지 않음 |
| 안전 지표의 범위 | 채점기는 계약 실패 시 pred_req를 빈 배열로 취급하므로 그 출력의 위험 의도·must-not가 0으로 집계될 수 있음 | 0건을 안전성 입증으로 사용하지 않음. raw/계약 실패를 별도 감사하고 파싱 가능한 위험 출력 발견 수와 한계를 함께 보고 |

근거: [Qwen 실행기](../evaluation/scripts/run_qwen35_2b_gguf_case_replay.py)의 정규화·scorer 입력 저장, [Gemma 실행기](../evaluation/scripts/run_gemma4_e2b_gguf_case_replay.py)의 동일 처리, [채점기](../evaluation/scripts/score_predictions_v2.py)의 canonical·field_exact·contract_ok 분기, [prompt v3.3](../evaluation/prompts/prompt_v3_3_full.txt), [출력 계약](../evaluation/schemas/output_v3.schema.json).

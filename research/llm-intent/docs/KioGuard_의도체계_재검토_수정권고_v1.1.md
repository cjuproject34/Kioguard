# KioGuard 의도 체계 재검토와 수정 권고

검토 문서 v1.1 · 수정 제안, 최종 의도 체계 미확정

## 1. 결론과 검토 범위

**현재 v1.0을 그대로 학습·평가 정답 기준으로 동결하는 것은 권하지 않는다.** 요청·정보·방법을 구분하고 의도와 문맥 누락을 분리한 방향은 유지할 만하다. 그러나 화면 이동과 초기화, 부정 표현과 거절 선택, 확인 응답의 대상, 조건부 요청의 활성화 여부에 정의 공백이 있다. 이는 제가 작성한 이전 승인안에서 보완해야 할 부분이다.

검토 대상은 [의도 정의 승인안 v1.0](KioGuard_의도정의_경계기준_승인안_v1.0.md)과 [48발화 재라벨링 승인안 v1.0](KioGuard_48발화_재라벨링_승인안_v1.0.md)이다. 48행을 전부 대조했으며, 추가 문장은 경계를 점검하기 위해 이번에 만든 설계 반례다. 실제 사용자에게 수집하거나 모델로 실행한 테스트가 아니다.

기존 문서·원문·과거 점수는 보존했다. 이번 작업은 문서 검토와 수정 권고 작성이며, 실제 정답셋 변경·모델 실행·앱 구현은 하지 않았다. Drive와 원본 첨부파일의 최신 변경도 이번에는 재조회하지 않았다.

이 문서의 P0/P1/P2는 **정의 수정 작업의 우선순위**다. 발화 처리의 고/저우선순위나 실험으로 측정한 위험도와 구분한다.

## 2. 발견 사항과 우선순위

| ID | 우선순위·판단 | v1.0의 문제 | 수정 권고 |
|---|---|---|---|
| R01 | P0 · 의도와 동작 효과 혼동 | ‘처음으로 돌아가 주세요’를 RESET으로 고정. ‘다음 화면’처럼 확정 없는 이동의 자리도 불명확 | 화면 이동과 내용 초기화를 분리. I07을 NAVIGATE로 확장하고 I14는 실제 재시작·초기화 요청에 한정 |
| R02 | P0 · 상태 선택 누락 | ‘긍정 요청 목록’과 금지 제약만으로 ‘영수증 안 받기’, ‘적용한 쿠폰 빼기’를 충분히 표현하지 못함 | I05에 발급 거절, I06에 적용 해제 포함. 금지·값 선택·변경 철회를 구분 |
| R03 | P0 · 확인 범위 불충분 | ‘네’의 질문 연결은 있으나 안내 동의와 거래 확정을 구분하는 기준이 약함. 결제수단 표현도 문맥에 따라 다른 역할 가능 | 확인 대상·질문 유형·유효성을 필수로 연결. 화면 이동/방법 안내 동의를 최종 확정으로 승격하지 않음 |
| R04 | P0 · 조건·요청 관계 누락 | 여러 의도와 순서는 기록하지만 조건·대안·요청별 대상 연결이 충분히 정의되지 않음 | 요청별 대상·조건·배제·선행 관계를 보존. 조건이 참인지 모르면 해당 행동 안내 보류 |
| R05 | P1 · 근거 없는 우선 후보 | 문맥 없는 ‘따뜻한 걸로 두 잔이요’를 I02 우선 후보로 정함 | 확인된 의미인 온도·수량은 보존하되 신규 요청/설정·변경 판정은 문맥 없으면 보류 |
| R06 | P1 · 문제 보고 처리 부족 | ‘화면을 못 찾겠어요’를 GUIDE로 고정. 결제 이상·화면 정지 같은 문제 보고의 처리 기준 부족 | GUIDE/HELP 경계를 의사소통 목적과 실제 문맥으로 결정. 문제 보고와 확인된 시스템 오류를 구분 |
| R07 | P1 · 등급 기준 재현성 부족 | ‘지시어·정정이면 C3’ 같은 포괄 기준과 개별 행의 C1/C2 판단이 일관되지 않을 수 있음 | 언어 구조·문맥 의존·정보 누락을 나눠 기록하고 조건부 등급 부여. 위험한 주제라는 이유로 복잡도를 올리지 않음 |
| R08 | P2 · 범위·데이터 근거 부족 | 14개가 전체 기능을 포괄한다는 검증 없음. 화면 읽기·도움 종료 등의 배치와 일부 의도 사례가 부족 | 핵심 정의 수정 후 기능별 발화 목록으로 누락 점검. 유지·병합·추가를 검수로 결정 |

P0는 잘못된 안내나 정답 해석으로 이어질 수 있어 기준 동결 전에 해결할 항목이다. P1은 라벨 일관성 확보를 위해 해결할 항목이다. P2는 범위·자료 보완 순서이며 중요하지 않다는 뜻은 아니다. 위 문제로 실제 앱에서 오류가 발생했다는 실측 증거를 새로 얻은 것은 아니다.

## 3. 핵심 경계의 수정안

### R01. 화면 이동과 초기화를 구분한다

v1.0의 FD-22·GV-19는 ‘처음으로 돌아가주세요’를 I14 RESET으로 제안했다. 이 표현만으로 사용자가 선택·작성 내용을 모두 지우려 한다고 볼 수 없다. 시작 화면으로 이동하는 것, 과업을 재시작하는 것, 설명을 처음부터 다시 듣는 것은 서로 다른 요구다.

| 발화·명시한 상황 | 수정 제안 |
|---|---|
| 화면 이동을 요청하는 상황: ‘처음 화면으로 가 주세요’ | I07 NAVIGATE, 목적지=HOME. 상태 삭제 의사로 확장하지 않음 |
| 작성 중인 신청을 지칭: ‘입력한 내용 지우고 처음부터 다시 할게요’ | I14 RESET, 초기화 대상=해당 신청 |
| 앱 설명 재생 중: ‘설명을 처음부터 다시 읽어 주세요’ | I11 UI_CONTROL, 동작=REPLAY_FROM_START |
| ‘다음 화면으로 가 주세요’ | I07 NAVIGATE. 단, 그 버튼이 실제로 제출·결제를 확정하면 효과를 설명하고 추가 확인 |
| ‘결제 화면으로 가 주세요’ | I07 NAVIGATE, 목적지=결제 화면. 최종 결제 의사로 간주하지 않음 |
| 최종 금액 확인 후: ‘이 금액으로 결제를 확정할게요’ | I13 COMMIT_REQUEST, 대상=해당 결제 |

화면의 HOME/NEXT 버튼이 데이터를 지우거나 거래를 확정한다면 그것은 **실제 동작 효과**로 기록한다. 사용자의 원래 이동 의도를 사후에 RESET/COMMIT으로 바꾸어 정당화하지 않는다. 필요한 효과 설명·확인·안내 보류는 별도 처리다.

### R02. 부정 문법과 요청된 상태를 구분한다

‘취소하지 마세요’를 긍정 CANCEL로 분류하지 않는 기존 원칙은 유지한다. 그러나 모든 부정 표현이 ‘실행 요청 없음’을 뜻하는 것은 아니다. 거절이나 해제 역시 명시적인 선택일 수 있다.

| 발화 | 의미·제안 정답 | 잘못된 처리 |
|---|---|---|
| ‘영수증은 안 받을게요’ | I05 RECEIPT, 선택=DECLINE | 의도 없음으로 무시하거나 발급 요청으로 처리 |
| ‘적용된 쿠폰 빼 주세요’ | I06 BENEFIT_CONTROL, 동작=REMOVE | 상품 전체 취소로 처리하거나 추가 할인 적용 |
| ‘이번에는 적립 안 할게요’ | I06 BENEFIT_CONTROL, 참여=DECLINE | 적립 요청으로 처리 |
| ‘시럽은 빼 주세요’ | I02 MODIFY, 대상 상품의 시럽 옵션=제외 | 음료 전체 I08 CANCEL |
| ‘라떼는 빼 주세요’ | I08 CANCEL, 제거 대상=해당 라떼 항목 | 라떼 옵션 하나만 제거 |
| ‘카드 말고 현금으로 할게요’ | I04 PAYMENT_METHOD, 수단=현금·배제=카드 | 부정된 카드도 사용할 수단으로 등록 |
| ‘주문 취소하지 마세요’ | 해당 주문 취소 금지. 대기 중인 취소 질문·요청과 연결 | CANCEL 실행 또는 금지를 단순 잡담으로 폐기 |

따라서 정답 기록의 ‘긍정 요청 목록’이라는 표현을 **‘요청된 작업·상태 변경’**으로 바꾸는 것을 권한다. 금지 제약은 별도 유지한다. ‘쿠폰 적용하지 마’처럼 앞으로의 적용 금지인지 이미 적용한 혜택 해제인지 갈리는 표현은 현재 상태를 확인한다.

I08 CANCEL은 주문 항목·거래·신청 등의 철회에 사용한다. 영수증 선택, 혜택 해제, 상품 옵션 제외, 음성 중지에는 각 전문 의도를 사용한다. ‘빼다/취소’라는 단어만으로 I08을 선택하지 않는다.

### R03. 확인 응답은 무엇을 확인한 것인지가 정답의 일부다

확인 응답은 독립적인 거래 의도가 아니다. 질문 ID뿐 아니라 질문의 **대상·내용·범위·현재 유효성**을 연결해야 한다. 앱의 ‘결제 방법을 안내할까요?’와 ‘현재 거래를 확정하시겠습니까?’는 다르다.

| 직전 질문·현재 문맥 | 사용자 응답 | 기대 의미 |
|---|---|---|
| ‘포장으로 선택할까요?’ | ‘네’ | I03 선택 수락 |
| ‘영수증을 받으시겠어요?’ | ‘아니요’ | I05 거절 선택. 다른 요청 전체를 취소하는 뜻 아님 |
| ‘결제 방법을 안내할까요?’ | ‘네’ | I09 안내 수락. 결제 확정 아님 |
| ‘결제 화면으로 이동하는 방법을 안내할까요?’ | ‘네’ | 해당 안내 수락. I13으로 승격하지 않음 |
| 최종 거래 대상을 명확히 묻는 유효한 확인 질문 | ‘네’ | 그 질문에 한정된 확인. 단순 동의만으로 외부 기기 자동 실행 권한을 만들지 않음 |
| 대기 질문 없음 또는 화면·금액·선택이 바뀜 | ‘네’ | 확인 대상 불명/만료. 거래 확정으로 해석하지 않음 |

FD-14·GV-11 ‘카드로 결제할게요’와 FD-15·GV-12 ‘현금으로 낼게요’는 결제수단 선택 문맥에서는 I04다. 최종 거래 확인에 대한 응답이라면 문맥에 연결된 확정 의사가 포함될 수 있다. 원문만 보고 결제 완료나 확정 승인을 추가하지 않되, **어느 상황에서나 I04만 가능하다고 고정하지도 않는다.** 알려진 수단 값과 미확정 진행 의사를 분리한다.

### R04. 조건·대안·대상 연결을 보존한다

의도 이름이 맞아도 아래 관계가 틀리면 사용자 요구를 잘못 해석한 것이다.

| 발화 | 보존할 내용 | 기대 대응 |
|---|---|---|
| ‘포장이 안 되면 주문 취소해 주세요’ | 조건=포장 불가, 조건 성립 시 I08 | 포장 여부가 미확인일 때 즉시 취소 안내 금지 |
| ‘카드가 안 되면 현금으로 할게요’ | I04의 우선 수단=카드, 대안=현금, 전환 조건 | 두 수단을 동시에 선택하지 않음 |
| ‘첫 번째 라떼는 차갑게, 두 번째는 따뜻하게’ | I02 요청별 상품 ID와 온도 연결 | 값 두 개만 뽑고 대상을 뒤바꾸면 실패 |
| ‘라떼 한 잔하고 아메리카노 두 잔 주세요’ | I01 아래 상품별 수량 연결 | 종류·총수량만 맞고 품목별 수량이 틀리면 실패 |
| ‘결제 취소가 끝나면 처음부터 주문할게요’ | I08과 I14의 대상 및 완료 의존 관계 | 취소 여부 미확인 상태에서 끝났다고 말하거나 다음 단계 강행 금지 |

라벨링 자료는 요청마다 `의도, 대상, 값, 조건, 배제, 선행 관계`를 묶어 기록하는 방식을 권한다. 실제 모델 출력 형식이나 토큰 수는 후속 설계에서 정한다. 이 문서가 긴 설명문을 LLM에 출력시키라는 요구는 아니다.

### R05. 모호한 발화를 편의상 I02로 정하지 않는다

FD-03 ‘따뜻한 걸로 두 잔이요’에서 온도·수량은 추출할 수 있지만, 생략된 새 주문인지 기존 상품의 속성 설정인지는 실제 대화에 따라 달라진다. v1.0의 ‘I02 우선 제안’은 라벨링 관례였으며 발화가 그렇게 해석된다는 증거가 아니다.

권고 정답은 **의도 관계 미확정 + 온도=따뜻함·수량=2 보존 + 대상/직전 질문 확인**이다. 이미 선택된 라떼의 온도·수량을 묻는 질문에 대한 답이면 I02로 확정할 수 있다. 신규 상품을 요청하는 맥락이 확인되면 I01의 속성으로 기록할 수 있다.

반면 ‘아이스로 바꿔 주세요’는 변경이라는 작업이 명시되어 있으므로 I02를 유지하면서 대상만 질문할 수 있다. ‘사이즈는 큰 걸로 주세요’처럼 속성 설정 요구가 명시된 경우도 I02 후보를 유지할 수 있다. 모든 슬롯 누락을 의도 미확정으로 바꾸는 수정은 아니다.

### R06. 문제 보고와 방법 문의를 구분한다

FD-24·GV-20 ‘화면을 못 찾겠어요’는 원하는 메뉴 화면으로 가는 방법을 모르겠다는 뜻일 수도 있고, 카메라가 화면을 인식하지 못한다는 문제 보고일 수도 있다. v1.0에서 GUIDE로만 정한 것은 해석 범위를 좁혔다.

- 특정 화면으로 가는 방법 문의가 확인되면 I09 GUIDE.
- 앱 인식 실패 등의 문제 지원을 원하면 I12 HELP, 세부 유형=ISSUE_SUPPORT.
- ‘직원에게 도와달라고 하고 싶어요’는 I12 HELP, 세부 유형=HUMAN_ASSIST.
- ‘도와 주세요’처럼 일반 지원 요청은 I12 HELP, 세부 유형=GENERAL_SUPPORT.

‘돈은 나갔는데 영수증이 안 나와요’, ‘카드가 두 번 결제됐어요’, ‘화면이 멈췄어요’ 같은 문장도 단순 진술로 버리면 안 된다. 현재 과업의 문제 해결을 요청하는 문맥에서는 도움 요청과 문제 내용을 기록한다. 과거 경험담·인용이라면 동일한 실시간 문제로 처리하지 않는다.

문제 보고에는 `사용자 보고`라는 근거 출처를 붙인다. 앱 로그로 확인한 오류나 확인된 결제 상태와 구분한다. 중복 결제 보고만으로 중복 결제를 사실로 확정하거나 재결제를 안내하지 않는다. I09로 구체적 해결 방법을 묻는 경우에도 보고된 문제 정보는 함께 유지한다.

I12에 세부 유형을 두는 것은 기존 14개를 활용하는 최소 수정안이다. 향후 문제 보고 데이터와 별도 처리 흐름이 충분하면 독립 의도로 분리할지 비교한다. 지금 I15가 필요하다고 실험적으로 확정한 것은 아니다.

## 6. 영향도·복잡도 기준의 보완

### 영향도

H/M/L/U 구분은 유지하되 사례마다 ‘잘못 안내했을 때 발생할 구체적인 결과’를 함께 쓴다. `U→M/H`는 현재 정보 부족과 가능한 범위를 표시한 메모이며 학습용 확정 등급이 아니다. 모델 비교용 정답을 만들 때는 평가자와 모델이 함께 볼 수 있는 시나리오를 제공한다.

금전 확정·민감정보 입력·중요 내용 소실 가능성이 확인되면 H를 부여한다. 결제수단 선택 같은 발화를 모두 H로 올리거나, 짧고 명확하다는 이유로 L로 낮추지 않는다. U는 별도의 미확정 상태이며 중간값이나 낮은 위험 점수가 아니다.

### 복잡도

v1.0은 C3 사유에 정정·지시어·대화 의존을 넓게 넣었지만 ‘아이스로 바꿔 주세요’는 C1, ‘다시 읽어 주세요’도 C1 예시로 제시했다. 이를 일관되게 적용하려면 다음 구분이 필요하다.

- 단순한 변경 동사가 있다고 높은 복잡도는 아니다. 한 가지 분명한 값 변경과 부정·대조 관계의 해석을 구분한다.
- ‘여기’가 검증된 현재 기기로 바로 연결되는 경우와 여러 화면·기관 중 지시 대상을 골라야 하는 경우는 다르다.
- ‘다시 읽어 주세요’는 반복할 안내가 하나로 정해진 상황에서는 단순할 수 있다. ‘아까 두 번째로 말한 것만 다시’는 문맥 선택 관계가 추가된다.
- 문맥을 수집하지 않았다는 사실, STT 입력이 훼손됐다는 사실, 언어적 해석이 어렵다는 사실을 각각 기록한다.

따라서 요청 수, 대상/값 관계, 부정 범위, 조건·대안, 참조해야 할 문맥, 대상 모호성, 입력 품질을 먼저 표시하고 C1~C3를 부여할 것을 권한다. CU는 구조를 판단할 수 없는 경우에만 사용한다. GV-07의 C3 자동 지정은 철회하고 문맥·참조 관계에 따라 재평가한다. 새 등급을 실제 연산량으로 해석하지 않는다.

L+C1이라는 기록만으로 Rule을 승인하지 않는다. 전체 허용 패턴·필수 상태·범위·반례 검증은 별도 조건이다. 이번 검토로 새로운 Rule이 구현되거나 검증된 것은 아니다.

## 7. 누락 기능과 평가 보완 사항

### 7.1 범위 결정이 먼저 필요한 기능

현재 14개는 업무 행동, 질문, 도움, 앱 제어가 함께 있는 실용적 분류다. 순수하게 하나의 축으로만 분류했다고 설명하면 부정확하다. 그 자체가 오류는 아니지만, 서로 겹칠 때 어떤 의미를 정답으로 삼는지 공통 기준이 필요하다.

다음 명령은 제품에서 지원할지와 별도 의도/하위 동작으로 둘지를 추가 결정해야 한다.

| 후보 기능 | 경계 문제 | 권고 |
|---|---|---|
| 현재 화면 처음 읽기 | ‘화면을 읽어 주세요’는 기존 안내 재생과 다른 OCR·내용 선택을 요구할 수 있음 | 음성 명령으로 지원한다면 READ_SCREEN을 명시적으로 정의. I11 반복 재생에 편의상 합치지 않음 |
| 현재 도움 세션 종료 | ‘이제 도움 그만 받을게요’는 TTS 중지·주문 취소·전체 초기화와 다름 | 음성 명령으로 지원한다면 END_ASSISTANCE를 별도 정의. 앱 버튼 전용이면 버튼 이벤트 범위를 명시 |
| 진행 상태 보고 | ‘결제했어요’는 완료 진술 또는 직전 안내에 대한 완료 응답일 수 있음 | 발화 유형·연결 질문·사용자 보고 상태로 기록. 실제 결제 성공의 검증 근거로 대체하지 않음 |

앞의 두 기능을 별도 의도로 추가하면 개수가 늘 수 있다. 지금 14개를 지키기 위해 의미가 다른 명령을 억지로 합치거나, 반대로 실험 없이 무조건 16개로 확정하지 않는다. **권고 순서는 핵심 경계 수정 → 음성 명령 범위 확정 → 필요한 의도 수 결정**이다.

### 7.2 기존 48행의 한계

v1.0 검토표에서 I06·I12·I13을 단일 후보로 제시한 행은 없고, I08은 복합 해석 보류 사례에 등장한다. 실제 지원 화면·단계도 없다. 따라서 기존 48행만으로 수정 체계의 14개 전체 성능이나 LLM/Rule 분담의 실효성을 평가할 수 없다.

신규 자료에는 발급 거절, 혜택 해제, 방법 안내 동의와 최종 확정의 대비, 조건부 취소, 사용자 문제 보고, 화면 이동과 초기화의 대비를 포함해야 한다. 같은 발화에 서로 다른 명시적 문맥을 붙이는 사례도 필요하다. 합성 문맥은 과거 실제 실험 환경으로 기록하지 않는다.

### 7.3 평가 정답에 반영할 항목

의도명뿐 아니라 요청별 대상·값·선택/해제 방향·부정 범위·조건·확인 질문 연결을 평가해야 한다. 조건부 취소를 무조건 취소로 예측하거나 ‘발급하지 않음’을 ‘발급’으로 예측하면, 의도 코드가 같아도 전체 의미 정답은 실패다.

정답 자료에서 문맥이 빠진 경우와 모델이 명확한 입력을 회피한 경우를 구분한다. 어려운 사례를 모두 단일 라벨 평가에서 제외해 정확도가 높아지는 것을 막기 위해, 원래 모호한 사례의 수와 전체 사례에 대한 적절한 처리 비율을 함께 보고한다.

Router 평가에서는 고영향·조건부·모호한 요청이 부적절하게 Rule로 통과했는지 확인한다. LLM 호출 비율만 낮추는 것을 성공 기준으로 삼지 않는다. 수치 목표·통과 기준은 이번 문서 검토로 새로 확정하지 않았다.

## 8. 적용 권고와 승인 범위

1. **R01~R06을 정의 수정안에 반영할 것을 권고한다.** 특히 NAVIGATE/RESET/COMMIT, 거절·해제, 조건·확인 범위부터 정리한다.
2. 14개 표는 검수용 수정안으로 사용하고, R07의 등급 기준과 R08의 화면 읽기·세션 종료 범위는 사례를 붙여 결정한다.
3. 원래 48행·과거 기준·결과를 보존한 채 새로운 정의 버전과 정답 자료를 별도로 만든다. 이번 5행 수정 권고를 기존 실험 오류율에 합산하지 않는다.
4. 두 사람이 독립 검수한 불일치를 해결한 뒤 의도 정의와 평가 입력·출력 계약을 동결한다. 이번 문서 검토는 사람 간 합의를 대신하지 않는다.
5. 그 기준으로 원정밀도 기준 모델·PTQ·QAT를 비교한다. 현재 분류 체계 수정만으로 성능이 개선됐다고 주장하지 않는다.

본 문서는 수정할 내용을 검토 가능하게 제시한 결과다. 사용자가 요청한 작업 전 확인 원칙에 따라, 실제 기준 동결·학습 데이터 변경·추가 실험은 별도 승인 후 진행한다.

# KioGuard 기존 48발화 의도·영향도·복잡도 검토

사람 검수 전 수정 제안

기존 발화와 V1 정답은 그대로 보존했다. V2 후보·등급·처리 경로는 이번 설계 검토이며 모델의 예측 결과나 확정된 신규 정답이 아니다. 원본 CSV에는 실제 화면·단계·직전 대화가 없어 조건부 판단이 많다. 표의 U는 상황 미확정, 화살표 뒤 등급은 조건이 확인됐을 때의 제안이다. H 보수 처리는 결제·민감정보 관련 보호 경로를 우선 적용하자는 정책이며 실제 거래 동작을 수행한다는 뜻이 아니다.

자료: [Drive 정답 CSV](https://drive.google.com/file/d/1N10Qfh3NN_WVdxdqVGXyw1ePFQ08kcLz/view), 로컬 엑셀 ‘의도정의’·‘정답라벨’ 시트. 상세 정의는 [상세 명세서](KioGuard_상세명세서_v0.2.md)의 2~3절을 따른다.

## 1. 우선 수정할 경계

| 경계 | 기존 사례 | 수정 방향 |
|---|---|---|
| 요청과 가능 여부 질문 | FD-10, FD-16, GV-15 | INFO + 이용방식/결제/혜택 주제로 분리 |

| 신규 주문과 변경 | FD-03/06/11/28, GV-08 | 현재 선택 상태를 추가해야 정답 확정 가능 |

| 의도는 알지만 대상은 모름 | GV-01/03, FD-12/23/25/27 | 의도 성공과 안내 가능 상태를 분리 |

기존 48개는 주문·발급·결제·과업 도움에 집중돼 있다. 검증된 저영향 앱 제어 발화가 충분하지 않으며, 이 자료만으로 새 Router의 실사용 호출률을 추정할 수 없다. 호출률을 기존 4%에 맞추기 위해 중간·고영향 발화를 Rule로 밀어 넣지 않는다.

추가 후보는 아래와 같다. 모두 새로 검증할 설계 예시이며 기존 점수에 합치지 않았다.

| 발화·상황 | 초기 정답·등급 | 기대 경로·반례 |
|---|---|---|
| 앱 안내 재생 중 “다시 읽어줘” | APP_CONTROL, L/C1 | 허용 패턴이면 Rule. “처음에 말한 것만”은 문맥 처리 |
| 앱 설정 화면에서 “글씨 크게” | APP_CONTROL, L/C1 | Rule. 외부 키오스크 화면이면 직접 제어 불가 |
| 앱 음성 재생 중 중지 버튼 | 로컬 제어 이벤트, L | 즉시 중지. LLM 처리 대기 없음 |
| “취소하지 마세요” | 취소 부정·현재 상태 유지 또는 문맥 확인 | CANCEL 긍정으로 승인 금지 |
| “결제하지 말고 처음으로 돌아갈래” | RESET + 결제 부정, H/C3 | LLM·상태 손실 확인 |

## 5. 라벨 확정 절차

1. 각 원문에 실제 화면·현재 단계·선택 대상·직전 발화를 추가한다.
2. 두 검수자가 의도·topic·영향도·복잡도·정답 처리 상태를 독립 작성한다.
3. 불일치 이유를 기록하고 정의표를 수정한다. 맥락을 확보할 수 없으면 조건부 라벨을 유지한다.
4. 새 정의를 동결한 뒤 새 데이터셋을 만든다. 이 표를 곧바로 정답 학습셋으로 사용하지 않는다.
5. 같은 문장과 유사 표현은 그룹 단위로 분리한다. 카페·관공서 상황이 다르면 평가 가치는 있지만 통계적으로 독립적인 문장으로 과장하지 않는다.

검토 완전성: FD-01~FD-28, GV-01~GV-20 전체 48행 포함. V1 원문·라벨과 자동 대조해 누락·변경 여부를 확인한다.

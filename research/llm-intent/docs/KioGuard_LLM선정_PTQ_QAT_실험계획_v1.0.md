# KioGuard LLM 선정·PTQ·QAT 실험 계획 v1.0


상태: **후보와 실험 절차 선정 완료 / 모델 다운로드·추론·학습·단말 측정 전**

## 1. 이번 단계의 결정

**최신 소형 모델을 비교하고 직접 PTQ를 수행한 뒤, 공개 QAT 모델 평가와 직접 QAT 실험을 구분해서 진행한다. 최종 모델·비트수는 실측 후 정한다.**

- 사용자의 결정에 따라 ‘현재 화면 새로 읽기’와 ‘도움 세션 종료’의 **음성 명령 지원은 보류**한다. 이번 모델 비교의 확정 업무 의도에 추가하지 않는다. 영구 미지원으로 결정하거나 기존 의도로 임의 매핑하지 않는다.
- 의도 기준은 [의도 정의 v1.2](KioGuard_의도정의_경계기준_v1.2.md)를 사용한다. 현재 핵심 14개 의도 외에도 정상적인 재질문·판정 보류를 평가한다. 전체 앱의 최종 의도 수를 확정한 것은 아니다.
- 1차 비교 후보는 **Gemma 4 E2B, Qwen3.5-2B, Qwen3.5-0.8B**다. 기존 Gemma 2 2B는 과거 실험과 연결되는 기준으로 보존한다. Kanana 2 1.3B는 변환·단말 호환성 확인 후 추가한다.
- 주 실행 경로는 **llama.cpp / GGUF**, 대안은 **Gemma 4 / LiteRT-LM**이다. 문서상의 지원과 우리 환경에서의 성공을 구분한다.
- 이번 계획에서는 직접 QAT를 연구 항목으로 유지한다. PTQ의 점수 하락이 작다는 이유만으로 생략하지 않는다. 다만 학습 방식과 최종 배포 형식이 맞지 않으면 본학습 전에 경로를 수정한다.

본 문서는 상세 명세 v0.2의 모델·양자화 실험 순서와 QAT 진입 기준을 갱신한다. 과거 문서는 기록으로 보존한다. 미결정 목록 v1.2의 두 음성 기능은 이제 **이번 연구 범위에서 보류**로 관리하며, 모델 연구의 선행 결정으로 요구하지 않는다.

멀티모달 후보에도 우선 **발화 텍스트와 검증된 화면·대화 상태만 입력**한다. 음성·이미지 인코더까지 이번 LLM 실험에 통합하지 않는다. 텍스트 입력만 사용한다고 모든 도구가 인코더 가중치를 자동으로 제외하는 것은 아니므로, 실제 배포 파일과 로드되는 구성요소를 확인한다.

## 4. 엔진·배포 경로

| 경로 | 목적 | 통과 조건 |
|---|---|---|
| Transformers 고정밀 | 모델 고유 형식으로 입력·출력 확인 | tokenizer·native chat template·비추론 설정·구조화 출력 확인 |
| llama.cpp 고정밀 GGUF | 변환·엔진 변경에 따른 차이 확인 | 동일 모델 revision의 변환 성공, 입력·출력 동등성 검사, raw 예측 보관 |
| llama.cpp 양자화 GGUF | PTQ 전후 및 Android 비교의 주 경로 | 고정한 commit·backend·실행 설정으로 각 정밀도 실행 |
| LiteRT-LM / `.litertlm` | Gemma 4 대안 배포 조합 | 공식 변환·Android 경로 확인 후 S24 Ultra에서 별도 측정 |
| QAT 학습·배포 경로 | 직접 QAT 수행 | 학습의 fake quantization과 최종 파일의 양자화 규격 일치, 변환 후 단말 추론 성공 |

llama.cpp는 엔진이며 Gemma·Qwen은 모델이다. GGUF와 `.litertlm`은 서로 바꿔 끼우는 파일이 아니다. llama.cpp 공식 문서에는 Android 예제와 Gemma 4 E2B 변환 예시가 있지만, 우리 단말의 성공은 별도 확인한다. [Android 문서](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md), [양자화 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md).

LiteRT-LM은 별도 후보 경로로 유지한다. 다른 기기의 공개 지연시간을 S24 Ultra 결과로 옮기지 않는다. 엔진과 양자화 산출물이 함께 달라지면 ‘배포 조합 비교’로 보고한다. [Gemma 4 LiteRT-LM 문서](https://developers.google.com/edge/litert-lm/models/gemma-4).

Android는 CPU 기준부터 확보하고 GPU 가속은 다음 비교로 둔다. 같은 모델의 정밀도 비교에서는 backend와 스레드 수를 고정한다. Snapdragon 탑재만으로 NPU 사용을 가정하지 않는다. 구체적인 도구 버전은 예비 실행에서 호환성을 확인한 뒤 commit·패키지 버전으로 고정한다.

## 5. 우선순위와 완료 기준

P0는 후속 결과의 타당성을 좌우하는 선행 작업, P1은 핵심 비교·학습, P2는 기본 비교 후 최적화다. 실행 순서와 중요도는 다르며 QAT·단말 평가는 뒤에 수행하더라도 중요도가 높다.

| 순서 | 우선도 / 중요도 | 작업 | 완료 산출물·다음 단계 조건 |
|---|---|---|---|
| 1 | P0 / 매우 높음 | 평가 입출력·정답 기준 정리 | v1.2 기반 의도·대상·부정·조건·순서·재질문 필드, 데이터 버전과 분할표 |
| 2 | P0 / 매우 높음 | Colab 자원·후보 호환성 예비 확인 | GPU/VRAM, 원본 revision, 로드·변환·짧은 추론 성공 여부와 오류 로그 |
| 3 | P0 / 매우 높음 | 고정밀 기준 측정·직접 QAT 경로 사전 점검 | 고정밀 raw 결과. QAT는 소량 학습→변환→추론 가능 여부를 본학습 전에 확인 |
| 4 | P1 / 매우 높음 | 직접 PTQ 및 LLM 단독 비교 | 같은 고정밀 원본에서 Q8_0·Q4_K_M 생성, 품질·크기·시간 비교. Gemma에는 Q4_0 추가 |
| 5 | P1 / 매우 높음 | Android 조기 실행·후보 축소 | PTQ 후보의 S24 Ultra 로딩·반복 추론·메모리 확인. 후보 1~2개로 축소 |
| 6 | P1 / 높음 | 공개 QAT 모델 평가 | Gemma 4 공식 QAT Q4_0와 직접 PTQ Q4_0 비교, 출처·형식 차이 명시 |
| 7 | P1 / 매우 높음 | 직접 QAT와 대조 학습 | 동일 데이터·예산의 일반 미세조정 대조군 포함. 학습 로그와 최종 배포 파일 평가 |
| 8 | P2 / 높음 | 토큰·backend·필요 시 대안 엔진 최적화 | 한 번에 한 변수를 바꾼 품질·자원 변화표 |
| 9 | P1 / 매우 높음 | 최종 단말·Router 통합 검증 | 반복 사용, 전체 앱 자원, 오류 대응, LLM 호출률·전체 품질 확인 후 최종 선택 |

평가셋 전체가 완성되기 전에도 2번 호환성 확인은 진행할 수 있다. 그러나 예비 입력 결과를 최종 정확도로 보고하지 않는다. 앱 전체가 완성될 때까지 Android 실행 가능성 확인을 미루지도 않는다.

## 6. PTQ: 무엇을 어떤 방식으로 양자화하는가

첫 대상은 **의도 해석에 사용하는 LLM의 가중치**다. Rule 자체는 양자화 대상이 아니다. STT·OCR·TTS, 활성값·KV cache의 정밀도 변경은 첫 비교에 섞지 않는다.

PTQ는 학습 후 양자화다. 변환과 양자화를 구분하고, 각 후보의 동일한 비양자화 원본 revision에서 아래 파일을 만든다.

| 실험 | 입력 | 출력 | 확인 목적 |
|---|---|---|---|
| P0-FP | 공식 비양자화 원본 | BF16 또는 FP16 GGUF | 변환 후 고정밀 기준. 지원되는 dtype를 명시 |
| P1-Q8 | P0-FP | Q8_0 GGUF | 낮은 압축 수준의 기준 |
| P2-Q4K | P0-FP | Q4_K_M GGUF | 더 큰 압축과 품질 변화 비교 |
| P3-Q4_0 | M1의 P0-FP | Q4_0 GGUF | 공식 Gemma QAT Q4_0와 형식을 맞춘 비교군 |
| P4-Q5 | P0-FP | 지원되는 Q5 형식 | Q4 품질과 Q8 자원 사이의 절충이 필요할 때만 추가 |

Q8 파일을 다시 Q4로 줄이지 않는다. Q4_K_M은 여러 tensor 정밀도가 혼합될 수 있으므로 ‘모든 가중치가 4비트’라고 기록하지 않는다. 최초 PTQ에는 학습이 필요하지 않다. imatrix 등 보정 정보를 추가하는 실험은 별도이며, 사용할 경우 train에서 분리한 calibration 자료만 사용한다. [llama.cpp 양자화 도구](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md).

고정밀 모델이 단말 메모리에 들어가지 않으면 실패를 기록하고, 같은 엔진·backend에서의 품질 비교는 Colab에서 수행한다. 단말에서는 실행 가능한 파일끼리 비교한다. Colab 고정밀 지연과 Android Q4 지연을 나누어 ‘양자화 가속 배수’로 보고하지 않는다.

각 산출물은 원본 revision, 변환 명령·도구 commit, 양자화 옵션, tensor 형식 분포, 파일 크기와 SHA-256을 남긴다. 비양자화 기준을 새로 확보할 수 없는 공개 양자화 파일은 ‘직접 PTQ 실험’의 대체물이 아니다.

## 7. QAT: 공개 모델 평가와 직접 수행을 구분

### 7.1 공식 공개 QAT 모델 평가

Google은 Gemma 4 E2B에 대해 Q4_0 GGUF와 QAT 후 비양자화 가중치를 제공한다. 모바일용 별도 규격도 있지만, 우선 동일 Q4_0 비교부터 진행한다. [공식 QAT GGUF](https://huggingface.co/google/gemma-4-E2B-it-qat-q4_0-gguf), [QAT 후 비양자화 가중치](https://huggingface.co/google/gemma-4-E2B-it-qat-q4_0-unquantized), [공식 형식 설명](https://ai.google.dev/gemma/docs/core).

- 비교: **일반 Gemma 4 E2B → 직접 PTQ Q4_0** 대 **공식 Gemma 4 E2B QAT Q4_0**.
- 양쪽의 tensor별 형식·예외 계층·template·runtime를 확인한다. Q4_0라는 이름만으로 모든 변환 설정이 같다고 가정하지 않는다.
- 결과 이름은 ‘공개 QAT 산출물 비교’다. 팀이 직접 QAT 학습을 수행한 성과로 쓰지 않는다.
- 공급자의 학습 데이터·예산까지 통제한 실험은 아니므로, 차이를 순수한 QAT 효과로 단정하지 않는다.
- `qat-...-unquantized`는 QAT를 이미 거친 가중치다. 일반 비양자화 원본 대조군으로 사용하지 않는다.

### 7.2 직접 QAT 경로의 사전 검증

QAT는 학습 중 양자화 오차를 모사하고, 학습 후 목표 형식으로 변환하는 과정이다. ‘INT4 학습’과 ‘Q4 GGUF 배포’라는 명칭만 맞춰서는 충분하지 않다. block/group 크기, scale·zero-point·반올림 방식, 대상 계층·예외 tensor, activation 규격을 맞춘다. QLoRA만 사용한 학습을 자동으로 QAT라고 부르지 않는다. [PyTorch QAT 설명](https://pytorch.org/blog/quantization-aware-training-in-torchao-ii/).

| 경로 | 이번 판단 | 본학습 전 확인 |
|---|---|---|
| Q4_0를 모사하는 QAT → GGUF Q4_0 | 주 엔진과 맞추기 좋은 조사 경로 | 선정 아키텍처 지원, fake quantization 규격 일치, 저장·변환 후 Android 실행 |
| TorchAO QAT → 호환되는 ExecuTorch 배포 | GGUF 경로가 맞지 않을 때 별도 연구 경로 | 모델 연산·양자화 형식·Android backend 지원. PTQ 대조군도 같은 경로로 배포 |
| 공개 QAT 가중치에 일반 미세조정만 수행 | 직접 QAT와 구분 | 실제 학습 중 fake quantization 적용 여부를 확인해야 함 |

Google Gemma 라이브러리의 QAT 예시는 Q4_0 등의 방식을 설명하지만 열람한 학습 예시는 Gemma 3 4B다. 이를 Gemma 4의 검증된 직접 QAT 레시피로 간주하지 않는다. TorchAO 문서의 지원 형식도 선정 모델의 GGUF 호환성을 자동 보장하지 않는다. [Gemma QAT 예시](https://gemma-llm.readthedocs.io/en/latest/colab_quantization_aware_training.html), [TorchAO 공식 설명](https://pytorch.org/blog/quantization-aware-training-in-torchao-ii/).

따라서 직접 QAT의 **최종 모델·프레임워크·학습률·batch·LoRA 설정은 아직 미정**이다. GPU 확인과 소량의 forward/backward·체크포인트 저장·배포 변환 검증 후 정한다. GGUF와 맞지 않는 형식을 억지로 재양자화해서 성공으로 기록하지 않는다. 최신 배포 후보의 직접 QAT가 막히면 지원되는 별도 소형 모델로 방법을 검증하되, 그 결과를 배포 후보의 개선으로 옮겨 쓰지 않는다.

### 7.3 직접 학습의 대조군

| 군 | 과정 | 구분하려는 효과 |
|---|---|---|
| A | 일반 비양자화 원본 → 목표 PTQ | 추가 학습 없는 기준 |
| B | 동일 원본 → 일반 지도 미세조정(SFT) → 목표 PTQ | KioGuard 데이터를 추가 학습한 효과 |
| C | 동일 원본 → QAT를 적용한 학습 → 목표 양자화 | B 대비 양자화 오차 모사의 추가 효과 |

B/C는 같은 학습 데이터, 초기 가중치, 데이터 순서·seed, 학습 대상 파라미터, step·길이 예산을 맞춘다. 필요한 방식별 설정 차이는 공개하고 dev에서 선택한다. QAT에 앞선 SFT가 필요하면 B와 C 모두 같은 SFT 체크포인트에서 출발하도록 실험을 다시 정의한다. 고정밀 SFT 결과도 남기면 학습 자체의 효과와 배포 손실을 구분하기 쉽다.

첫 시도는 전체 학습에 앞선 소량 검증이다. 본학습의 충분성은 학습 곡선과 dev 오류로 판단한다. 효과가 작거나 악화돼도 기록하며, fake-quant 모델의 점수만으로 끝내지 않고 **최종 변환 파일을 평가**한다.

## 8. 평가 입력·출력과 데이터 관리

### 8.1 비교 단위

입력은 발화와 필요한 상태 정보다. 현재 선택 상품, 현재 단계, 직전 질문과 유효한 확인 대상, 관찰된 화면 항목을 구분해 제공한다. 사용자 발화와 화면 OCR은 데이터이며 모델 지시문을 바꾸는 지시로 취급하지 않는다.

출력은 자유로운 긴 안내문 대신, 요청 목록·의도·대상·값·선택/해제·부정·조건·선행 관계·재질문 사유를 표현하는 공통 구조로 정의한다. 예를 들어 ‘취소하고 다시 처음부터 할게요’는 현재 주문 취소와 첫 화면 이동의 순서를 보존한다. ‘화면을 못 찾겠어요’는 어떤 화면인지 묻는 대응을 허용한다. 외부 거래를 실행하거나 완료했다고 선언하는 출력은 요구하지 않는다.

모델 간에는 같은 의미의 지시와 같은 사례를 사용하되 각 모델의 native chat template를 쓴다. 한 모델 내 정밀도 비교는 template·parser·출력 제약·길이 설정을 동일하게 고정한다. JSON 문법 제약은 구조를 돕지만 의도 정답을 보장하지 않는다. 부분 문자열로 정답 라벨을 찾거나 문법 오류를 임의의 유효 라벨로 바꾸지 않는다.

### 8.2 기존 자료와 새 평가셋

- 기존 48개는 개발·회귀 자료로 보존한다. 새 독립 test로 사용하지 않는다.
- 기존 학습 CSV 126행은 새 의미 정의로 재검수한다. 파일명에 QAT가 있다는 이유로 QAT 학습 완료로 보지 않는다.
- train / calibration / dev / test를 관리한다. 유사 문장·같은 상황의 변형은 같은 그룹으로 묶어 분할 간 누출을 막는다. calibration이 불필요한 PTQ 조건에는 이를 명시한다.
- 사용자 지정 문맥으로 정답을 정한 사례에는 모델에도 같은 문맥을 제공한다. 원문만 평가하는 조건과 분리한다.
- 정답은 단일 의도뿐 아니라 복합 요청, 거절·해제, 조건, 필요한 재질문, 범위 밖 요청, 입력 손상 사례를 포함한다. 결정 보류된 두 음성 기능은 별도 보관하고 현재 14개 업무 정답으로 강제 편입하지 않는다.
- 필요한 사례 수는 각 의도·중요 경계의 오류와 분모를 보고 보강한다. 48건이나 임의의 목표 건수만으로 일반화 충분성을 선언하지 않는다.

최종 test는 모델·프롬프트·양자화·토큰 설정을 dev에서 선택한 뒤 평가한다. test 오답을 보고 설계를 변경하면 그 세트는 다음 반복의 개발 자료로 처리하고 새로운 독립 평가가 필요하다.

## 9. 품질·메모리·지연·발열의 평가 기준

| 축 | 필수 지표 | 해석·기록 원칙 |
|---|---|---|
| 의도 | 의도별 precision/recall/F1, macro-F1, 단일 의도 정확도 | 적용 가능한 사례의 분모 명시. 복합 요청은 요청 연결과 전체 일치도 별도 평가 |
| 전체 의미 | 의도·대상·값·부정·조건·순서의 전체 일치율 | 라벨만 맞고 거절/조건을 잃으면 전체 의미는 오답 |
| 오류 영향 | 고영향 사례의 잘못된 해석·안내 가능 출력 건수/비율 | 취소/이동/초기화/확정 혼동, 부정 반전, 대상 바뀜 등을 별도 집계 |
| 대응 | 필요한 재질문 재현율·불필요한 재질문율, 검증 후 올바른 대응률 | 모든 입력에 재질문하는 방식이 유리해지지 않게 두 지표를 함께 보고 |
| 기술 실패 | 형식 오류, 출력 잘림, 미응답·timeout, 메모리 부족, 변환 실패 | 실패를 평가 분모에서 조용히 제거하지 않음 |
| 양자화 변화 | 같은 모델 고정밀 대비 품질 차이(%p), 새로 생긴/해결된 오류 | 평균 점수만 같아도 사례별 오류가 바뀔 수 있음 |
| 파일 | 배포에 필요한 전체 파일 크기, tensor 형식 | GB/GiB 구분. 모델·추가 구성요소를 누락하지 않음 |
| 실행 메모리 | 로드 전후·최대 process PSS/RSS, 가능한 backend 메모리, 전체 앱 상태 | 서로 다른 메모리 계측값을 단순 합산하지 않음. 미포착 GPU 메모리는 한계로 기록 |
| 지연 | cold load, warm 전체 판정 p50/p95, 첫 토큰·입출력 token 수 | 주 지표는 유효 판정 완료까지. STT/TTS 제외 LLM 시간과 앱 전체 시간을 분리 |
| 지속 사용 | 반복 세션 전후 지연, 열 상태·가능한 온도, 배터리 변화 | 배터리 센서 온도를 CPU 온도로 부르지 않음. 초기 조건·측정 불가 항목 명시 |
| 통합 | LLM 호출률, Rule 오처리율, 시스템 전체 올바른 대응률 | LLM 단독 비교 후 Router를 붙여 측정 |

첫 단말 측정안은 워밍업을 분리한 고정 입력 반복과 약 10분 연속 세션을 각각 3회 수행하는 것이다. 이는 예비 프로토콜이며 최종 사용 환경을 대표한다는 주장이 아니다. 충전 여부·화면 밝기·주변 온도·배터리 수준·백그라운드 앱·측정 간 냉각 조건을 기록하고, 정식 비교 전에 프로토콜을 고정한다.

정확도·허용 지연·앱 메모리의 **최종 수치 목표는 아직 확정하지 않는다**. 이전 문서의 초기 목표를 달성값으로 취급하지 않는다. 오류 검토와 단말 예비 측정, 앱의 동시 실행 구성에 근거해 dev 단계에서 수용 기준을 정하고 test 전에 고정한다. 고영향 필수 사례에서 새 위험 오류가 발생한 조합은 원인 해결 전 최종 채택을 보류한다. 테스트에서 0건이라는 사실이 실제 오류 확률 0을 뜻하지는 않는다.

## 10. 토큰 최적화와 최종 선택

첫 비교는 짧은 구조화 응답·비추론 모드로 시작하되 모델별 지원·실제 출력을 확인한다. 길이 예산은 v1.2의 복합 요청·조건을 충분히 표현할 수 있는지 dev에서 검사한 뒤 정한다. 고정밀·PTQ·QAT가 서로 다른 길이 제한 때문에 비교되지 않도록 한다.

품질 기준을 확보한 뒤 다음을 개별 비교한다: 의도 설명 압축, 무관한 이전 대화 제외, 검증된 화면 정보만 제공, 예시 수 조정, 출력 키·값 간결화. 원시 입력과 각 tokenizer의 실제 token 수를 모두 기록한다. 중요한 부정·조건·대상을 잘라서 절감하지 않는다. 길이 초과는 명시적 실패·보류 경로로 처리한다.

최종 선택은 ① 모델·배포 호환성 → ② 중요 의미와 재질문 품질 → ③ 앱 전체 자원·지연 → ④ 유지·학습 가능성 순으로 검토한다. 작은 모델·최신 모델·Q4·QAT 중 어느 하나가 무조건 우승하도록 정하지 않는다. 가중치 양자화만으로 입력·출력 토큰 수가 자동 감소하는 것도 아니다.

## 12. 보존할 과거 결과와 현재 완료 범위

과거 결과는 [Colab 실험 검토보고서](KioGuard_기존_Colab_실험_검토보고서.md)를 기준으로 보존한다. Q4 저장 예측 41/48, f16 GGUF 저장 예측 37/48, Rule+저장 Q4의 Hybrid 재구성 47/48은 각각 당시 조건의 기록이다. 기존 라벨 체계의 점수를 새 14개 의도 기준 점수와 직접 비교하지 않는다. Q8 최종값·원본 HF 일부 보고값·과거 QAT 수행 여부의 미확인 상태도 유지한다.

이번에 완료한 것은 공식 자료 확인, 모델 후보 축소, 엔진·양자화 비교 설계, 공개/직접 QAT 구분, 실험 순서·평가·기록 기준 정리다. 기존 문서·원본 발화·저장 결과는 변경하지 않았다. 모델 다운로드·추론·PTQ·QAT·Android 실측은 아직 수행하지 않았다.

다음 실제 실행은 **Colab GPU/VRAM 확인 → 작은 후보의 고정밀 로드·변환·짧은 추론 → 공통 평가 실행 경로 검증 → 직접 PTQ**다. QAT는 이와 별도로 초기에 학습·변환 호환성을 확인하고, 후보를 좁힌 뒤 본학습한다. GPU가 확정되기 전까지 학습 batch·모델 적재 방식·훈련 비용을 확정하지 않는다.
